# 자동 라벨링: 에이전트는 나르고 사람이 판정한다

> 조사 기준일 2026-09-28. 조사 노트 4편(Roboflow 자동화 · 라벨링 도구와 CLI · 모델 접근법 · VLM과 에이전트 라벨링)을 종합했다. 가격·순위표·버전은 모두 이날 기준이며 자주 바뀐다.

**결론 1: 가능하다, 단 '운반'까지만.** Claude Code는 Roboflow MCP, Roboflow SDK·CLI, Ultralytics, X-AnyLabeling 변환 CLI를 써서 「모델 실행 → 라벨 파일 생성 → 업로드 → 검토 작업 생성 → 라벨 회수」를 거의 전부 대신 돌릴 수 있다. 이 부분은 공식 문서로 확인된다.

**결론 2: 라벨 내용의 판정은 맡길 수 없다.** 글자 설명만으로 박스를 다는 모델(Roboflow Auto Label의 GPT-6 Astra·SAM 3·Gemini, Grounding DINO, autodistill)이 「분홍 B3 대 빨강 EMO」를 가르거나 19–94 px 버튼을 잡는다고 믿을 근거가 없다. Claude가 직접 봐도 마찬가지다. Roboflow 문서도 기초 모델은 「특정 변종을 구분하지 못한다」고 적어 두었다.

**결론 3: 맞는 방식은 반자동이다.** 우리 모델(console_v2·tool_v3)이 로컬에서 무료로 프리라벨을 만든다. 에이전트는 「같은 버튼이 두 번」「배치 순서가 모순」 같은 일관성 검사로 의심 박스를 검토 순서 맨 앞에 세운다. 확정은 사람이 X-AnyLabeling(또는 Roboflow 검토 작업)에서 한다. test 셋은 이 흐름 밖에서 사람이 처음부터 단다.

**결론 4: 가장 중요한 수치는 아직 아무도 재지 않았다.** 7월의 약 92%는 프리라벨이 박스를 '덮은' 비율이지 '맞힌' 비율이 아니다. 사람 라벨 50장과 대조하는 작은 실험 하나로 임계값, 검토 범위, VLM이 필요한지가 함께 정해진다.

## 이 보고서를 읽는 법

출처 링크가 붙은 문장은 문서·논문·공식 페이지에 적힌 사실이다. **〔추론〕** 은 조사자나 작성자의 판단이며 측정한 적이 없다. **〔미확인〕** 은 검색 요약에서만 본 주장이라 원문을 확인하지 못했다. **〔상충〕** 은 출처끼리 말이 다른 곳이다. **〔프로젝트 기록〕** 은 이 프로젝트가 직접 잰 값이나 내린 결정이며(7월 약 92%, 색 규칙 122건, Grounding DINO 자동 라벨 실패 등) 외부 출처가 아니다.

### 용어 풀이

| 용어 | 쉬운 뜻 |
|---|---|
| 객체 검출, 바운딩 박스 | 사진 속 물체의 위치를 네모(박스)로 표시하고, 그 물체가 무엇인지(클래스) 이름을 붙이는 일 |
| 라벨, YOLO 형식 | 라벨은 정답으로 확정된 박스다. YOLO 형식은 이미지마다 txt 파일을 하나 두고, 한 줄에 「클래스 번호, 박스 중심 x·y, 너비, 높이」를 쓴다(이미지 크기에 대한 0–1 비율) |
| 클래스맵(labelmap) | 클래스 번호와 이름의 대응표(0=B1 …). 순서가 어긋나면 라벨이 통째로 뒤바뀐다 |
| 프리라벨(사전 라벨) | 모델이 먼저 그려 둔 초안. 사람이 고치거나 승인해야 정답이 된다 |
| 자동 라벨링 | 초안 생성부터 사람 확인 없는 확정까지 두루 가리키는 넓은 말. 이 보고서는 '초안 생성'과 '확정'을 나눠 쓴다 |
| 신뢰도, 임계값 | 신뢰도는 모델이 박스마다 붙이는 확신 점수(0–1)이고, 임계값은 이 점수 이상인 박스만 남기는 기준선이다. 낮추면 놓치는 박스가 줄고 가짜 박스가 는다 |
| 제로샷 | 우리 데이터로 한 번도 학습하지 않은 모델을 그대로 쓰는 것 |
| 개방 어휘 검출기, 텍스트 프롬프트 | 「pink button」처럼 찾을 대상을 글자로 알려 주면 찾아 주는 검출기. Grounding DINO, OWLv2, YOLO-World, YOLOE, Florence-2, SAM 3 등이 있다 |
| 시각 프롬프트, 예시 박스, 네거티브 예시 | 글자 대신 「이런 것」이라는 예시 박스를 그려 주면 닮은 것을 찾는 방식. 네거티브 예시는 「이런 것은 빼라」는 반대 예시다 |
| 퓨샷, 파인튜닝 | 적은 수(예: 클래스당 10개)의 정답만으로 모델을 추가 학습시키는 것 |
| VLM(시각-언어 모델) | 이미지와 글을 함께 읽고 글로 답하는 대형 AI(Claude, GPT, Gemini, Qwen-VL 등). 박스 좌표를 글로 내놓을 수 있다 |
| 에이전트 | 명령을 실행하고 파일을 다루며 여러 단계를 스스로 이어 가는 AI. 여기서는 Claude Code다 |
| MCP | AI 에이전트가 외부 서비스 기능을 '도구'로 불러 쓰게 하는 연결 규격. Roboflow MCP는 Roboflow 기능을 Claude Code의 도구로 내놓는다 |
| API, SDK, CLI | API는 프로그램끼리 서로 부르는 창구, SDK는 그 창구를 쉽게 쓰도록 만든 파이썬 라이브러리, CLI는 터미널 명령어다. 셋 다 에이전트가 스크립트로 돌릴 수 있다 |
| 헤드리스 | 화면(GUI) 없이 명령만으로 끝까지 도는 것 |
| OAuth | 비밀번호나 키를 넘기지 않고, 브라우저 로그인으로 권한을 빌려주는 인증 방식 |
| 크레딧 | Roboflow 기능을 쓸 때 차감되는 사용량 단위 |
| Universe, Public 플랜 | Universe는 Roboflow의 공개 데이터 저장소다. 무료 Public 플랜의 데이터와 모델은 여기에 공개된다 |
| Auto Label, Label Assist, Box Prompting | Roboflow의 AI 라벨 기능들. Auto Label은 이미지 묶음 전체를 뒤에서 일괄로 라벨한다. Label Assist는 편집기에서 이미지를 열 때마다 모델이 초안을 띄운다. Box Prompting은 예시 박스를 그리면 닮은 것을 찾아 주며 웹 화면에서만 된다 |
| Workflow | Roboflow에서 모델 블록과 규칙 블록을 이어 붙여 만든 처리 흐름 |
| mAP, mAP@50 | 검출 정확도 점수(0–100 또는 0–1). mAP@50은 박스가 정답과 절반 이상 겹치면 맞았다고 치는 기준이다 |
| 도메인 차이 | 모델이 학습한 사진(주로 일상 사진)과 실제로 쓸 사진(우리 1인칭 콘솔 영상)이 다른 정도. 클수록 제로샷 성능이 떨어진다 |
| 영상 전파 | 한 프레임에 표시한 물체를 다음 프레임들로 자동으로 따라가며 표시하는 것(SAM 2 등) |
| 가림 | 손 같은 것이 물체를 가리는 것 |
| 라벨 오류 4종 | 클래스를 틀리게 붙임(분류 오류), 있는 물체를 빠뜨림(누락), 없는 물체에 박스를 침(가짜 박스), 박스 위치가 어긋남 |
| 확인 편향 | 모델이 만든 초안으로 다시 학습하면, 그 모델의 버릇(예: 어두우면 B3를 EMO로 봄)이 정답처럼 굳어 버리는 현상 |
| 순환 평가 | 평가받는 모델이 정답 만들기나 재검 대상 고르기에 관여하는 것. 그러면 채점이 실제 정확도가 아니라 모델 자신과의 일치도를 재게 된다 |
| K-fold, out-of-sample | 데이터를 K조각으로 나누고, 조각마다 '그 조각을 학습에서 보지 않은 모델'로 예측하는 방법. cleanlab이 이것을 요구한다 |
| ONNX | 학습한 모델을 여러 프로그램이 읽을 수 있게 바꾼 공용 파일 형식. X-AnyLabeling이 요구한다 |
| Blackwell, sm_120, CUDA | Blackwell은 RTX 50 시리즈의 GPU 세대 이름이고 sm_120은 그 내부 번호다. CUDA는 NVIDIA GPU 계산 플랫폼이다. 오래된 라이브러리는 sm_120을 몰라서 GPU를 못 쓴다 |
| JPEG 품질, 재압축 | JPEG는 화질(0–100)을 낮춰 용량을 줄인다. 이미 압축된 사진을 다시 압축하면 손상이 겹친다 |
| 레이아웃 규칙 | 「EMO는 아래 가운데, B3는 오른쪽 위」처럼 고정된 배치를 근거로 버튼 이름을 정하거나 검사하는 규칙 |

## 에이전트는 라벨 작업의 거의 전 구간을 명령으로 돌릴 수 있다

「에이전트가 사람 대신 라벨을 단다」는 말에는 성격이 다른 세 가지 일이 섞여 있다. 첫째는 **운반**으로, 모델을 돌리고 파일 형식을 바꾸고 업로드하고 검토 작업을 만들고 결과를 내려받는 일이다. 둘째는 **판정**으로, 이 박스가 B3인지 EMO인지, 여기에 버튼이 있는지 없는지를 정하는 일이다. 셋째는 **검수**로, 이미 달린 라벨이 맞는지 확인하는 일이다. 조사 결과 운반은 문서로 뒷받침된다. 판정은 이 프로젝트 조건에서 믿을 근거가 없다. 검수는 train/val에서 '어디부터 볼지 줄 세우기'까지만 맡길 수 있고, test에서는 아예 맡길 수 없다.

운반 쪽 도구는 충분히 성숙했다. **Roboflow는 호스팅형 MCP 서버(`https://mcp.roboflow.com/mcp`)를 공식으로 제공하고, API 키 없이 OAuth 로그인으로 인증한다** ([Roboflow MCP 문서](https://docs.roboflow.com/agents/mcp-server)). 문서에 나열된 도구는 **141개**다. 여기에는 이미지 업로드(`image_upload`), 이미 올린 이미지에 라벨 저장(`annotations_save`), 자동 라벨 작업 시작·조회(`autolabel_start`·`autolabel_job_get`), 검토 작업 생성·배정·반려·승인(`annotation_jobs_*`, 승인은 `annotation_jobs_accept_into_dataset`), 버전 내보내기(`versions_export`), 호스팅 추론(`models_infer`)이 들어 있다(같은 문서). 〔상충〕 Roboflow 블로그는 같은 서버를 「67개 도구」로 소개한다 ([Roboflow MCP 블로그](https://blog.roboflow.com/mcp-server/)). 문서가 더 최신 숫자일 가능성이 크다〔추론〕.

한계도 문서에 적혀 있다. 첫째, MCP 업로드는 **이미지만 담은 zip이고, 라벨은 두 번째 단계에서 이미지마다 따로 저장**한다 ([Roboflow 업로드 문서](https://docs.roboflow.com/datasets/create-and-upload/upload-a-dataset)). 둘째, OAuth 권한이 특정 폴더로 좁혀져 있으면 **우리 모델이나 저장된 Workflow로 자동 라벨 작업을 시작할 때 403 오류가 난다**. 이때는 워크스페이스 API 키를 쓰라고 안내한다 ([Auto Label 문서](https://docs.roboflow.com/datasets/annotate/annotate/ai-labeling/auto-label)). 이 세션에는 Roboflow MCP가 **등록만 되어 있고 아직 인증 전**이다. 문서 안내대로 첫 사용 때 사람이 브라우저에서 한 번 로그인해야 한다. 무료 플랜에서 어떤 도구가 막히는지는 문서에 없다〔미확인〕.

MCP 없이 파이썬 SDK와 CLI만으로도 같은 일을 할 수 있다. `roboflow` 패키지(1.5.1, 2026-09-24 출시, [PyPI](https://pypi.org/project/roboflow/))의 `project.upload(image_path, annotation_path, ..., is_prediction=...)`는 이미지와 YOLO 라벨을 함께 올린다. `project.save_annotation(..., annotation_labelmap=..., annotation_overwrite=True)`는 이미 올린 이미지에 라벨을 붙인다 ([Roboflow 이미지 관리 문서](https://docs.roboflow.com/datasets/manage/manage-images)). 이 두 옵션은 프로젝트가 이미 겪은 함정 두 가지와 정확히 맞물린다. labelmap을 빼면 클래스가 숫자로 올라가고, overwrite를 빼면 기존 라벨이 있는 이미지를 건너뛴다. 같은 문서에 따르면 REST로 `prediction=true`를 주면 그 라벨은 **확정 라벨이 아니라 '예측'으로 저장되고 이미지가 검토(Review) 작업으로 넘어간다.** 사람이 승인하기 전에는 정답이 아니라는 뜻이라 우리 원칙과 잘 맞는다. 단, **zip 일괄 업로드는 예측 표시를 지원하지 않는다** ([Roboflow 업로드 문서](https://docs.roboflow.com/datasets/create-and-upload/upload-a-dataset)). CLI는 에이전트용 구조화 JSON 출력과 일관된 종료 코드(0 성공, 1 오류, 2 인증 오류, 3 없음)를 명시한다 ([Roboflow CLI 문서](https://docs.roboflow.com/reference/platform/cli)). 자동 라벨 작업도 SDK·CLI·REST로 시작할 수 있다. 다만 **기본값이 기존 라벨을 덮어쓰는 것**(API 기본 `preserveExistingAnnotations=false`)이라 옵션을 명시해야 한다 ([Auto Label 문서](https://docs.roboflow.com/datasets/annotate/annotate/ai-labeling/auto-label)).

Roboflow 밖의 CLI도 역할이 분명하다. 가장 직접적인 무인 프리라벨러는 Ultralytics의 `yolo predict ... save_txt=True save_conf=True`다. 한 줄에 클래스, 중심, 너비, 높이, 신뢰도를 쓴다 ([Ultralytics predict 문서](https://docs.ultralytics.com/modes/predict/)). 함정이 두 개 있다. 검출이 없는 이미지에는 빈 txt를 만들지 않고 ([Ultralytics Results 문서](https://docs.ultralytics.com/reference/engine/results)), 파일명이 같은 이미지들의 결과가 한 txt에 이어 붙는 문제가 보고됐다 ([ultralytics 이슈 #22531](https://github.com/ultralytics/ultralytics/issues/22531)). `auto_annotate()`는 이름과 달리 박스가 아니라 다각형(분할) 라벨을 만든다 ([Ultralytics annotator 문서](https://docs.ultralytics.com/reference/data/annotator/)).

X-AnyLabeling의 CLI는 `help·checks·version·config·convert`가 전부이고, **무인 자동 라벨 명령은 없다.** `convert --task yolo2xlabel`과 `xlabel2yolo`로 형식만 바꾼다 ([X-AnyLabeling CLI 문서](https://github.com/CVHub520/X-AnyLabeling/blob/main/docs/en/cli.md)). 우리 모델로 일괄 라벨을 돌리려면 GUI에서 ONNX 파일과 YAML 설정으로 모델을 등록한 뒤 Ctrl+B를 눌러야 한다 ([사용자 모델 문서](https://github.com/CVHub520/X-AnyLabeling/blob/main/docs/en/custom_model.md), [사용자 가이드](https://github.com/CVHub520/X-AnyLabeling/blob/main/docs/en/user_guide.md)).

CVAT는 `cvat-cli task auto-annotate <작업번호> --function-file 내함수.py` 명령으로 **우리 모델을 로컬에서 돌려 그 결과를 검토 화면에 곧바로 올리는 유일한 도구**다 ([CVAT CLI 문서](https://docs.cvat.ai/docs/api_sdk/cli/), [CVAT 자동 주석 API](https://docs.cvat.ai/docs/api_sdk/sdk/auto-annotation/)). Label Studio는 `label-studio-converter import yolo --out-type predictions`로 YOLO 결과를 예측으로 가져온다. 하지만 예측은 읽기 전용이라 검토자가 복사해서 확정해야 한다 ([가져오기 튜토리얼](https://labelstud.io/blog/tutorial-importing-local-yolo-pre-annotated-images-to-label-studio/), [예측 가이드](https://labelstud.io/guide/predictions)). Label Studio와 FiftyOne도 공식 MCP 서버를 낸다 ([Label Studio MCP 블로그](https://labelstud.io/blog/integrating-label-studio-with-model-context-protocol-mcp/), [FiftyOne MCP](https://github.com/voxel51/fiftyone-mcp-server)).

| 경로 | 에이전트가 대신하는 것 | 사람이 남는 곳 | 라벨링 크레딧 |
|---|---|---|---|
| 우리 모델 로컬 실행 → SDK·CLI로 `is_prediction=True` 업로드 → 검토 작업 | 추론, 변환, 업로드, 작업 생성, 회수 | 검토 화면에서 확정 | 0 (업로드·저장 크레딧만) |
| 위와 같은 흐름을 MCP로 | 위와 같음 (업로드는 zip, 라벨은 장별 저장) | 최초 OAuth 로그인, 검토 | 0 |
| Roboflow Auto Label + Roboflow 안에서 학습한 모델 | 작업 시작·조회 | 검토 | 1,000장당 1 |
| Roboflow Label Assist | 불가 (편집기에서 이미지를 열 때 실행됨) | 전부 | 100장당 1 |
| Roboflow Box Prompting | 불가 (웹 UI 전용, API를 찾지 못함) | 전부 | 문서에 없음 |
| X-AnyLabeling | ONNX 변환, YAML 작성, `convert` | Ctrl+B 실행, 검토 | 해당 없음 |
| CVAT Community | `cvat-cli`로 추론·업로드 | 검토 | 해당 없음 |

크레딧 요율은 Roboflow 크레딧 페이지 기준으로 **자동 라벨 1,000장당 1크레딧, 대화형 AI 라벨 100장당 1크레딧, 직접 운영하는(자가 호스팅) 추론은 무료**다 ([Roboflow 크레딧](https://roboflow.com/credits)). Label Assist가 편집기에서 이미지를 열 때 돈다는 것과 Box Prompting이 예시 박스로 동작한다는 것은 각 기능 문서에 있다 ([Label Assist 문서](https://docs.roboflow.com/datasets/annotate/annotate/ai-labeling/model-assisted-labeling), [Box Prompting 문서](https://docs.roboflow.com/datasets/annotate/annotate/ai-labeling/box-prompting-ai-labeling)). Auto Label에 쓸 수 있는 자체 모델은 「Annotation Batch와 같은 데이터셋에서 학습한 모델만」이다 ([Auto Label 문서](https://docs.roboflow.com/datasets/annotate/annotate/ai-labeling/auto-label)). 밖에서 학습해 올린 YOLOv8 가중치가 여기에 해당하는지는 문서에 없다〔미확인〕. 게다가 올리는 가중치는 `ultralytics==8.0.196`으로 학습해야 한다는 버전 조건이 붙는다 ([사용자 가중치 업로드 문서](https://docs.roboflow.com/models/model-weights/upload-custom-weights)).

〔추론〕 `annotations_save`는 한 장씩 처리하므로 수천 장 프리라벨을 올릴 때는 SDK·CLI가 효율적이고, MCP는 작업 생성, 상태 조회, 내보내기처럼 호출 수가 적은 일에 편하다. 우리 모델을 Roboflow로 옮겨 Auto Label을 돌리는 것보다 로컬에서 돌려 결과만 올리는 편이 버전 조건과 크레딧 문제를 모두 피한다. Roboflow 자신도 MCP를 「보고, 라벨하고, 결과를 판단하는 건 사람이, 나머지는 에이전트가」 하는 분업으로 소개한다 ([Roboflow MCP 문서](https://docs.roboflow.com/agents/mcp-server)).

## 글자 설명으로 라벨을 다는 모델은 분홍 B3와 빨강 EMO를 가르지 못한다

가장 분명한 증거는 Roboflow 자신의 문서다. 2026년 9월 현재 Auto Label이 쓰는 모델은 **GPT-6 Astra(물체 검출 프로젝트의 기본값), SAM 3, Gemini 3.7 Flash, Roboflow에서 같은 데이터셋으로 학습한 모델, 저장된 Workflow**다. 그리고 문서는 이렇게 쓴다. 「특정 변종을 구분해야 한다면 SAM 3 같은 기초 모델을 쓰지 말라. 예컨대 Auto Label은 균열 종류를 구분하지 못한다.」 「알루미늄 캔의 브랜드 구분 같은 특정 요구대로는 라벨하지 못한다.」 ([Auto Label 문서](https://docs.roboflow.com/datasets/annotate/annotate/ai-labeling/auto-label)) 우리 버튼 5개는 물체 종류가 아니라 **정체성**으로 이름이 붙은 '변종'이다. 〔프로젝트 기록〕 Roboflow의 Grounding DINO 자동 라벨이 B3와 EMO를 가르지 못한 것도 이 한계와 들어맞는다. 참고로 **현재 Auto Label 목록에는 Grounding DINO가 없고**, 조사자는 공식 폐기 공지를 찾지 못했다(같은 문서).

같은 문서에 따르면 GPT-6 Astra와 Gemini는 **모든 박스를 신뢰도 만점으로 돌려주므로 임계값을 걸 수 없다.** 〔추론〕 따라서 「애매한 박스만 사람에게 보내기」 같은 선별이 원리적으로 불가능하다. 〔상충〕 문서는 클래스 설명이 프롬프트로 쓰인다고 하지만, Roboflow의 Gemini 블로그는 「Gemini는 클래스 이름만 읽고 설명 칸은 읽지 않는다」고 쓴다 ([Roboflow Gemini 블로그](https://blog.roboflow.com/how-to-auto-label-image-data-with-gemini-3-7-in-roboflow/)). GPT-6 Astra에는 「물체 사이의 관계」를 읽는다는 공지가 있다 ([Roboflow 2026년 9월 변경기록](https://docs.roboflow.com/reference/changelog/changelog/september-2026/gpt-6-astra-in-auto-label-automate-data-annotation-with-plain-language-prompts)). 이것이 「패널 오른쪽 위의 분홍 버튼」 같은 위치 설명을 제로샷으로 쓸 수 있는 유일한 후보다. 그러나 우리 영상에서 시험된 적이 없고, OpenAI 토큰 비용이 따로 붙는다〔추론〕.

학술 벤치마크도 같은 방향을 가리킨다. 색·재질 단어만 바꾼 함정 문장으로 검출기를 시험한 OVDEval(AAAI 2024)에서 **색 과제 점수는 Grounding DINO 9.4, 가장 높은 모델도 22.9(100점 만점)**였다. 저자들은 「모든 모델이 색과 재질 과제에서 성적이 나쁘다」고 결론지었다 ([OVDEval](https://arxiv.org/html/2308.13177v2)). 반대 증거도 있다. FG-OVD(CVPR 2024)는 두 후보 문장 중 하나를 고르게 한 쉬운 조건에서 「색은 대부분의 검출기에 가장 쉬운 속성」이라고 보고했고, OWLv2가 53.3 mAP를 얻었다 ([FG-OVD](https://arxiv.org/html/2311.17518)). 그러나 이것은 일상 사진에서 두 문장 중 하나를 고르는 과제이고, 가장 쉬운 속성이라는 색도 절반가량만 맞혔다. VLM 쪽 ColorBench에서는 **미세한 색 비교 과제의 최고 모델이 71.3%, 사람은 79.8%**였다. 저자들은 「단일 물체의 이상적 조건에서도 미세한 색을 믿을 만하게 구분하지 못한다」고 썼다(Claude는 평가 대상에 없었다) ([ColorBench](https://arxiv.org/abs/2504.10514)).

도메인 차이는 더 크다. 공개 데이터셋 100개를 모은 RF100-VL에서 **제로샷 mAP는 Grounding DINO 15.7, OWLv2 13.6, Gemini 2.5 Pro 11.6, Qwen2.5-VL-72B 5.6**이었다. **산업 분야만 보면 Grounding DINO 10.3, OWLv2 7.8**이었다. 반면 정답으로 제대로 학습한 **YOLOv8n은 54.9**였다 ([RF100-VL](https://arxiv.org/pdf/2505.20612)). 같은 논문에서 클래스 설명을 자세히 넣어 주는 것도 도움이 들쭉날쭉했다. Gemini 2.5 Pro는 오히려 11.6에서 4.5로 떨어졌다(같은 논문).

「예시를 몇 개 보여 주면 닮은 것을 찾는」 방식은 낯선 분야에서 글자 프롬프트보다 낫다. 예로 T-Rex2는 Roboflow100에서 시각 프롬프트 18.5 대 텍스트 10.5 AP였다 ([T-Rex2](https://arxiv.org/pdf/2403.14610)). 하지만 이런 모델은 **한 개념의 모든 사례를 찾도록** 설계되어 있지, 닮은 물체 가운데 딱 하나를 골라내도록 설계되지 않았다. Ultralytics 문서도 YOLOE 시각 프롬프트에 대해 「제로샷 정확도는 당신의 클래스로 학습한 모델보다 한참 낮다」, 결과는 `object0`·`object1` 같은 이름으로 나오니 직접 대응시키라고 적는다 ([Ultralytics YOLOE](https://docs.ultralytics.com/models/yoloe/)).

이 무리에서 가장 유망한 것은 SAM 3다. **「이런 것은 빼라」는 네거티브 예시 박스**를 받는다 ([Roboflow SAM 3 문서](https://docs.roboflow.com/models/supported-models/sam3)). 또 「흰 옷 선수」와 「빨간 옷 선수」처럼 가까운 개념을 가르려는 존재 토큰(presence token)을 넣었다 ([SAM 3 GitHub](https://github.com/facebookresearch/sam3)). 그러나 논문 스스로 「극히 드물거나 세밀한 개념」에서 성능이 떨어진다고 적는다. RF100-VL 제로샷도 15.2로 Grounding DINO(15.7)보다 낫지 않다. 1인칭 스마트안경 영상 점수도 일반 영상보다 낮았다(36.4 대 50.8) ([SAM 3 논문](https://arxiv.org/html/2511.16719v1)). 몇 장으로 추가 학습하는 퓨샷이 가장 확실히 오르기는 한다. 클래스당 10개로 파인튜닝한 Grounding DINO는 33.6 mAP까지 올랐다. 그래도 완전 학습한 YOLOv8n(54.9)에는 한참 못 미친다 ([RF100-VL](https://arxiv.org/pdf/2505.20612)). 오픈소스 autodistill은 바로 이 제로샷 모델들을 기반으로 하는 틀이다. 마지막 PyPI 릴리스가 2024-11-26이라 사실상 멈춰 있다 ([PyPI autodistill](https://pypi.org/project/autodistill/)).

| 텍스트 제로샷 (Grounding DINO, OWLv2, YOLO-World, Florence-2) | 「단추」「드라이버」 같은 일반 명사 | 색 과제 9.4–22.9점. 산업 분야 제로샷 7.8–10.3 mAP | 버튼 안 맞음. 공구는 미측정 |
| Roboflow Auto Label 기초 모델 (GPT-6 Astra, SAM 3, Gemini) | 대량 일괄, 미리보기 무료 | 「특정 변종 구분 불가」. 신뢰도 만점이라 임계값 없음 | 버튼 안 맞음 |
| 시각 프롬프트 (YOLOE, T-Rex2, GeCo) | 낯선 분야에서 텍스트보다 나음 | 한 개념의 모든 사례를 찾게 설계됨. 〔추론〕 B3와 EMO를 한 개념으로 묶을 위험 | 공구 후보, 버튼 안 맞음 |
| SAM 3 예시 + 네거티브 예시 | 닮은 것 배제 기능이 유일하게 있음 | 세밀한 개념에서 약하다고 스스로 명시. 쌍 구분 측정 없음 | 실험 후 판단 |
| 퓨샷 파인튜닝 (Grounding DINO, SAM 3) | 제로샷의 2배 이상 | 완전 학습 YOLOv8n보다 낮음. 데스크톱 GPU 필요 | 우리 모델보다 나을 근거 없음 |
| 우리 모델 (완전 학습) | 같은 논문에서 가장 높음 (YOLOv8n 54.9) | 〔프로젝트 기록〕 B3→EMO, 흰 장갑→B2, 빨간 손잡이 조각→EMO | 주력 |

〔추론〕 왜 이렇게 되는지는 우리 클래스의 성격에서 나온다. B3와 EMO는 **모양이 같은 둥근 버튼이고, 차이는 색과 위치뿐**이다. 색은 9 ms 어두운 노출과 JPEG 품질 약 53에서 흔들린다. 색상(hue) 규칙이 122건을 틀린 것〔프로젝트 기록〕도, 텍스트 제로샷이 약한 것도 같은 원인이다. 반면 **위치(배치)는 노출이 바뀌어도 변하지 않는다.** 벤치마크에서도 위치는 색보다 쉬웠다. OVDEval의 위치 과제에서 Grounding DINO는 67.5점으로 색 과제(9.4)보다 훨씬 높았다 ([OVDEval](https://arxiv.org/html/2308.13177v2)). 엘리베이터 버튼 인식 연구도 버튼 격자를 맞추고, 그 격자로 시점 왜곡을 보정한다 ([엘리베이터 패널 격자 연구](https://arxiv.org/abs/1912.11774)). 〔미확인〕 격자로 놓친 버튼을 되찾고 잘못 읽은 버튼을 배치 규칙으로 고친다는 후속 연구의 문장은 검색 요약으로만 확인했다. 배치 규칙으로 **학습 데이터를 자동 라벨한** 뒤 라벨 정확도를 잰 연구는 조사자가 찾지 못했다. 그래서 이 보고서는 배치 규칙을 라벨을 '다는' 도구가 아니라 **의심을 '표시하는'** 도구로만 권한다. 버튼이 둘 이하로 보이거나 손이 버튼을 가린 프레임에서는 기준이 없어 규칙이 무너지기 때문이다〔추론〕.

영상 전파도 같은 곳에서 무너진다. SAM 2 논문은 한계로 「긴 가림 뒤나 붐비는 장면에서 물체를 놓치거나 혼동」, 「빠르게 움직이는 가는 물체」, 「가까이 있는 닮은 물체」를 적는다 ([SAM 2 논문](https://arxiv.org/pdf/2408.00714)). 1인칭 추적 벤치마크 EgoTracks는 「잦은 큰 카메라 움직임과 손 상호작용이 가림이나 화면 이탈을 부른다」며 최신 추적기의 점수가 낮다고 보고했다 ([EgoTracks](https://arxiv.org/abs/2301.03213)). 〔추론〕 누르는 순간 손에 가려지는 버튼은 SOP 사건에서 가장 중요한 박스인데, 바로 그 프레임에서 전파 라벨이 가장 약하다. 버튼은 이미 우리 모델이 프레임마다 잡으므로 전파가 필요 없다. 전파는 손에 든 공구에 한해, 실패한 프레임마다 다시 지정해 주는 조건으로만 고려할 만하다. CVAT 무료판(Community)은 키프레임 사이를 직선으로 보간하는 것만 되고, SAM 2 추적기는 유료판(Enterprise·Online) 기능이다 ([CVAT AI 모델 문서](https://docs.cvat.ai/docs/annotation/auto-annotation/ai-models/)).

## Claude가 직접 박스를 그리는 것은 가능하지만 이 데이터에는 맞지 않는다

Anthropic은 박스·점 좌표 출력을 공식 지원 기능으로 문서화한다. 권장 방식은 **절대 픽셀 `[x1, y1, x2, y2]`**이고, 0–1000 정규화 좌표는 「잘 안 된다」고 쓴다. 좌표가 어긋나는 가장 흔한 원인으로는 서버 쪽 자동 축소를 든다. 작은 대상은 축소되면 정밀도를 잃으니 관심 영역을 잘라 보내라고 권한다 ([Claude 좌표 문서](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates)). 한계 절에는 「좌표와 위치 출력은 근사치이니 확인하고 쓰라」, 「저화질, 회전, 200 픽셀 미만의 아주 작은 이미지에서는 환각이나 실수를 할 수 있다」, 「강한 JPEG 압축은 성능에 해로운 흔적을 남긴다」가 적혀 있다 ([Claude 비전 문서](https://platform.claude.com/docs/en/build-with-claude/vision)).

〔추론〕 이 문서를 우리 데이터에 대 보면 결과가 엇갈린다. 좋은 쪽부터 보자. 768×1024 프레임은 문서의 토큰 공식(28×28 픽셀당 1토큰)으로 28×37 = **1,036토큰**이다. 한도 안이라 축소가 일어나지 않으므로, 좌표 어긋남의 가장 큰 원인은 피할 수 있다. 나쁜 쪽은 대상 크기다. 19–94 px 버튼은 1–16토큰짜리 조각이고, 문서가 경고하는 200 px 한참 아래다. 여기에 품질 약 53의 JPEG, 모션 블러, 어두운 노출이 겹친다.

외부 측정값은 우리 조건과 거리가 멀다. Roboflow Vision Evals(2026-09-22 갱신)의 검출 점수(대표 지표 mAP@50)는 **Claude Opus 5.5 74.4%, Sonnet 5 36.1%, GPT-6 Astra 82.1%, Gemini 3.5 Flash 70.6%**다. 그러나 **데이터셋의 구성, 이미지 수, 물체 크기가 공개되지 않았다** ([Roboflow Vision Evals](https://playground.roboflow.com/evals)). 같은 곳의 비교에서 Claude Opus 5는 '이게 무엇인가' 식별 과제에서 90.6%를 받았지만 검출은 54.4%에 그쳤다 ([Opus 5 대 Gemini 3.1 Pro 비교](https://playground.roboflow.com/models/compare/claude-opus-5-vs-gemini-3-1-pro)). ICLR 2026 논문도 대형 멀티모달 모델이 「의미 과제를 기하 과제보다 눈에 띄게 잘한다」고 결론지었다 ([arXiv 2507.01955](https://arxiv.org/abs/2507.01955)). RF100-VL에서는 VLM이 클래스당 10개 예시를 받고도 7.5–9.2 mAP에 머물렀다. 전문 검출기를 파인튜닝하면 약 33 mAP였다 ([RF100-VL](https://arxiv.org/html/2505.20612)). Roboflow는 Opus 4.7 평가에서 **개수 세기가 30%에 그친 것을 「큰 사각지대」라고 불렀다.** 그리고 Claude를 실시간 추론용이 아니라, 작은 배포용 검출기와 짝지은 학습 단계의 라벨 도구로 권했다 ([Roboflow Opus 4.7 평가](https://blog.roboflow.com/claude-opus-4-7/)). 작은 물체에서 Claude의 박스 정확도를 잰 공개 자료는 찾지 못했다.

돈은 걸림돌이 아니다. 문서 가격표(Opus 5.5 입력·출력 100만 토큰당 $4·$20, Haiku 4.5 $1·$5, 배치 50% 할인)로 계산하면 다음과 같다 ([Claude 가격](https://platform.claude.com/docs/en/about-claude/pricing)). 프레임 5,000장을 Haiku 4.5로 처리하면 약 $11(배치 약 $5.5)이다. 항상 사고(thinking) 과정을 거치는 Opus 5.5는 약 $129(배치 약 $64)다〔추론, 프레임당 입력 약 1,450토큰·출력 150–1,000토큰 가정〕. 배치 API는 요청 10만 건까지 받고 대부분 1시간 안에 끝난다 ([Claude 배치 처리](https://platform.claude.com/docs/en/build-with-claude/batch-processing)). 〔추론〕 반대로 Claude Code 세션에서 이미지를 한 장씩 직접 읽게 하는 방식은 가장 비효율적이다. 이미지가 대화 맥락에 쌓이고, 배치 할인도 없고, 정확도 측정도 없다. VLM을 쓴다면 에이전트가 배치 API 스크립트를 짜서 돌리게 하는 편이 낫다.

그래서 남는 쓰임은 **박스를 그리는 사람**이 아니라 **박스를 의심하는 사람**이다. 〔추론〕 우리 모델의 오검출 중 「흰 장갑을 B2로」, 「빨간 손잡이 조각을 EMO로」는 '이게 버튼이냐 장갑이냐'라는 의미 문제라 VLM이 강한 영역이다. 반면 「B3를 EMO로」는 VLM이 가장 약한 미세 색 구분이다. 게다가 어두운 노출에서는 우리 모델과 VLM이 **같은 이유로 함께 틀릴** 수 있다. 둘이 합의했다고 정답이라는 보장이 없다는 뜻이다. Roboflow가 소개한 「Gemini가 제안하고 GPT와 Claude가 판정해 3표 중 2표면 기록」 방식에는 정확도·비용 수치도, 사람 검토 단계도 없다 ([Roboflow 다중 모델 자동 라벨](https://blog.roboflow.com/multi-model-auto-labeling/)). 따라서 VLM은 실험 3에서 사람 라벨과 비교해 볼 때까지 **자동 확정권이 없는 표시 도구**로만 다룬다. 프레임을 외부 API로 보내는 일은 프로젝트 기준상 외부 전송이라 따로 승인이 필요하다.

## 20% 오류에서 틀린 클래스는 빠진 박스보다 1.8배 성능을 깎았다

「틀린 라벨은 없는 라벨보다 해롭다」는 프로젝트 원칙은 연구로 뒷받침된다. COCO에 인공 오류를 넣고 Faster R-CNN을 학습시킨 UNA 연구(오류 없을 때 37.4 AP)의 결과가 아래 표다 ([UNA](https://arxiv.org/pdf/2312.13822)).

| 오류 비율 | 클래스 틀림 | 위치 어긋남 | 누락 | 가짜 박스 | 네 가지 동시 |
|---|---|---|---|---|---|
| 5% | −0.9 | −0.4 | −0.3 | −0.2 | −1.7 |
| 10% | −1.4 | −0.8 | −0.6 | −0.5 | −4.3 |
| 15% | −1.7 | −1.7 | −1.0 | −0.8 | −7.5 |
| 20% | **−2.4** | −2.0 | **−1.3** | −0.9 | **−10.8** |

저자들은 「클래스 오류가 가장 큰 악영향을 주며, 깨끗한 라벨의 학습까지 방해하는 적대적 잡음처럼 작용한다」고 썼다. 20%에서는 네 가지를 함께 넣었을 때의 하락(10.8)이 각각의 하락을 더한 값보다 컸다. 오류끼리 서로 증폭한다는 뜻이다(같은 논문). YOLOv5·YOLOv8·Faster R-CNN을 COCO·VOC·ExDARK로 시험한 2024년 연구도 해로움을 **클래스 오류 > 가짜 박스 > 누락** 순으로 매겼다 ([Beyond clean data](https://www.sciencedirect.com/science/article/abs/pii/S095070512401178X)).

〔추론〕 이 순위에 우리 모델의 알려진 오류를 대 보면 이렇다. B3→EMO는 가장 해로운 클래스 오류다. 흰 장갑→B2와 빨간 손잡이 조각→EMO는 두 번째로 해로운 가짜 박스다. 둘 다 '빠뜨린 박스'보다 해롭다. 게다가 벤치마크의 오류는 무작위로 흩뿌린 것인데, 우리 B3↔EMO 오류는 어두운 노출에서 특정 쌍에만 **체계적으로** 일어난다. 모델에 일관된 잘못된 경계를 가르치므로 벤치마크 수치보다 더 해로울 가능성이 있다(측정된 연구는 없음). 따라서 사람도 B3와 EMO를 가를 수 없는 프레임에서는 추측으로 라벨을 붙이지 않는 편이 낫다. 그런 프레임을 뺄지 표시만 할지는 라벨링 기준에서 정할 문제다.

반대 방향의 증거도 공정하게 봐야 한다. Voxel51과 미시간대의 2025년 연구(학습 445회)는 YOLO-World로 자동 라벨한 데이터로 학습해도 사람 라벨과 크게 다르지 않았다고 보고했다. VOC에서 YOLO11n 기준 0.715 대 0.756 mAP50이다. 또 **신뢰도 임계값을 낮춰 놓침을 줄이는 쪽이 오히려 좋았다** ([Voxel51 자동 라벨 연구](https://arxiv.org/pdf/2506.02359)). 하지만 같은 논문에서 운전 영상 BDD는 0.271 대 0.434로 크게 벌어졌고, 드물거나 분포 밖인 클래스에서 자동 라벨이 무너졌다(같은 논문). 〔추론〕 「임계값은 낮게」는 일반 명사 클래스의 결론이다. 클래스 오류가 주된 위험인 우리 정체성 클래스에 그대로 옮기면 안 된다. 우리 임계값은 실험 1의 수치로 정해야 한다.

자기 초안으로 다시 학습하는 반복에는 **확인 편향**이라는 이름이 붙은 위험이 있다. 반지도 학습 검출 연구는 「가짜 라벨 편향」을 핵심 문제로 꼽았다 ([Unbiased Teacher](https://arxiv.org/abs/2102.09480)). VLM 가짜 라벨을 거르지 않고 YOLOv5m을 학습하면 KITTI에서 31.12%였다. 두 모델이 서로 걸러 주는 방식을 쓰면 46.61%로 오르고, 정답 10%를 더하면 57.97%가 됐다 ([VLM 가짜 라벨 공동학습](https://arxiv.org/abs/2511.09955)). 의심 라벨을 골라 사람에게 보내는 도구는 효과가 있다. CLOD는 인공으로 흐트러뜨린 박스의 약 80%를 오경보율 0.1 미만으로 찾아냈고, 가장 확실한 제안부터 고치자 mAP가 16–46% 올랐다 ([CLOD](https://arxiv.org/abs/2211.13993)). 로컬에서는 cleanlab(`find_label_issues`, 단 **K-fold로 만든 out-of-sample 예측이 필요**, [cleanlab 튜토리얼](https://docs.cleanlab.ai/stable/tutorials/object_detection.html))과 FiftyOne 오픈소스판의 mistakenness(누락·가짜·위치 의심 표시, [FiftyOne Brain](https://docs.voxel51.com/brain/index.html))를 쓸 수 있다. FiftyOne의 「Verified Auto-Labeling」 승인 화면은 유료판 전용이다 ([FiftyOne 자동 라벨](https://docs.voxel51.com/enterprise/verified_auto_labeling.html)).

test 셋 규칙은 이 연구들의 거울상이다. RF100-VL도 test 라벨은 「전수 검증하고 다시 단 것」을 썼다 ([RF100-VL](https://arxiv.org/pdf/2505.20612)). 〔추론〕 이 프로젝트에서 test를 지키는 조건은 두 가지다. 첫째, 어떤 모델이나 VLM도 test 라벨을 그리지 않는다. 둘째, **평가 대상 모델(console_v2 등)이 test에서 무엇을 재검할지 고르지 않는다.** cleanlab·FiftyOne 순위나 신뢰도 순 정렬은 모두 모델의 시각으로 재검 대상을 고르는 일이라 test에서는 쓸 수 없다. test 재검은 무작위 표본을 다른 사람(또는 같은 사람이 다른 날)이 다시 달아 대조하는 방식이어야 한다. VLM이 검증한 라벨로 YOLO를 학습한다면 val 점수도 VLM과의 일치도를 일부 재게 되므로, **사람만 단 val 조각**을 따로 두는 것이 안전하다.

표의 근거는 다음과 같다. X-AnyLabeling의 버전·배포판은 [릴리스 페이지](https://github.com/CVHub520/X-AnyLabeling/releases)(v4.0.6, 2026-09-05. CPU·CUDA 11/12/13용 Windows·Linux 빌드와 macOS arm64만 있고 Linux aarch64는 없다), 라이선스와 지원 모델은 [README](https://github.com/CVHub520/X-AnyLabeling)에 있다. YOLOE 시각 프롬프트가 「일괄 모드에서는 안 된다」는 제한은 [YOLOE 예제](https://xanylabeling.com/examples/grounding/yoloe)에 있다. CVAT 설치는 x86_64 Ubuntu와 WSL2 + Docker Desktop 기준으로만 문서화되어 있고 ARM64 언급이 없다 ([CVAT 설치 문서](https://docs.cvat.ai/docs/administration/community/basics/installation/)). Label Studio YOLO 백엔드는 `.pt` 모델을 받는다 ([LS YOLO 백엔드](https://github.com/HumanSignal/label-studio-ml-backend/tree/master/label_studio_ml/examples/yolo)). FiftyOne은 Ultralytics 모델을 바로 적용하고 YOLO 형식으로 내보낸다 ([FiftyOne Ultralytics 연동](https://docs.voxel51.com/integrations/ultralytics.html)). Roboflow Inference는 오픈소스이고 「직접 돌리는 추론은 크레딧을 쓰지 않는다」 ([Roboflow Inference](https://github.com/roboflow/inference)). T-Rex Label은 브라우저 기반이며 시각 프롬프트를 여러 이미지로 퍼뜨린다 ([T-Rex Label](https://trexlabel.com/en/)). 〔추론〕 상용 클라우드는 모두 영상을 올려야 하고, 무료 등급 정보는 리뷰 사이트에만 있어 확인되지 않았다. 로컬 대안이 있으니 쓸 이유가 없다.

하드웨어로 나눠 보면 역할이 갈린다. **파이 5**는 Ultralytics·cleanlab 같은 라이브러리 경로만 현실적이다. 이미 있는 파이썬 3.12 venv(CPU torch + ultralytics)로 YOLOv8n 프리라벨을 돌릴 수 있다. 속도는 재지 않았다. **데스크톱**에서는 이미 설치된 X-AnyLabeling-CPU.exe가 검토 화면으로 충분하다. YOLOv8n ONNX 추론에는 GPU가 필요 없다〔추론〕. GPU는 SAM 3, 영상 전파, K-fold 재학습에만 필요한데, 여기에는 Blackwell 문제가 걸린다. **PyTorch 2.7이 Blackwell을 지원하는 첫 안정판이고 CUDA 12.8(cu128) 빌드가 필요하다** ([PyTorch 2.7](https://pytorch.org/blog/pytorch-2-7/)). 그 이전 빌드에서는 「sm_120은 현재 PyTorch와 호환되지 않는다」 오류가 난다 ([PyTorch 포럼](https://discuss.pytorch.org/t/pytorch-support-for-sm-120-nvidia-geforce-rtx-5060/220941)). onnxruntime-gpu는 RTX 50 계열에서 PTX 컴파일 실패 보고가 있다 ([onnxruntime 이슈 #26177](https://github.com/microsoft/onnxruntime/issues/26177), 닫혔지만 해결 내용은 보이지 않음). 〔미확인〕 「1.28 이상은 sm_120을 기본 지원한다」는 말은 검색 요약에서만 나왔다. X-AnyLabeling GPU 빌드는 onnxruntime 버전을 CUDA 12용 1.27 미만, CUDA 13용 1.27.x로 고정한다 ([X-AnyLabeling 설치 문서](https://github.com/CVHub520/X-AnyLabeling/blob/main/docs/en/get_started.md)). Grounding DINO는 자체 CUDA 연산이 RTX 5090에서 「커널 이미지 없음」으로 실패했다가 다시 빌드해서 해결됐다 ([Grounded-SAM-2 이슈 #114](https://github.com/IDEA-Research/Grounded-SAM-2/issues/114)). SAM 3는 파이썬 3.12 이상, PyTorch 2.7 이상, CUDA 12.6 이상이 필요하다 ([SAM 3 GitHub](https://github.com/facebookresearch/sam3)). 가중치는 Hugging Face에서 수동 승인을 받아야 하고 자체 SAM License를 따른다 ([Hugging Face facebook/sam3](https://huggingface.co/facebook/sam3), [Ultralytics SAM 3](https://docs.ultralytics.com/models/sam-3/)). RTX 5060의 VRAM 용량은 조사하지 않았다.

Roboflow를 계속 쓴다면 **이미지는 로컬 원본이 정본이고 Roboflow에서는 라벨만 가져온다**는 기존 규칙이 문서로도 뒷받침된다. 버전 다운로드는 「학습 속도를 위해 의도적으로 압축한다」고 되어 있다 ([다운로드 문서](https://docs.roboflow.com/datasets/create-and-upload/download-a-dataset)). 원본 바이트를 그대로 받으려면 `search_export`(roboflow 1.2.14 이상)를 쓴다 ([내보내기 문서](https://docs.roboflow.com/datasets/versions/dataset-versions/exporting-data)). 중요한 단서가 하나 있다. **SDK 1.3.6(2026-04-27) 이전 버전은 업로드할 때 Pillow로 이미지를 다시 인코딩했다** ([이미지 관리 문서](https://docs.roboflow.com/datasets/manage/manage-images)). 그러니 옛 SDK로 올린 이미지는 Roboflow 쪽 '원본'부터가 재압축본일 수 있다. Workflow의 데이터셋 업로드 블록도 JPEG로 다시 압축한다(v2 기본 품질 95, v1 75) ([업로드 블록 문서](https://docs.roboflow.com/workflows/blocks/blocks/data-storage/roboflow-dataset-upload)). 〔추론〕 〔프로젝트 기록〕으로 잰 '환산 품질 75'는 옛 SDK의 Pillow 재인코딩 때문일 수도 있고, 버전 다운로드 압축 때문일 수도 있다. Pillow 기본 저장 품질이 75라는 것은 일반 지식이며 이번에 출처로 확인하지 않았다. 어느 쪽인지는 실험 5에서 해시 비교로 가린다. 라벨만 내보내는 옵션은 문서에 없다. 대신 이미지 상세 API가 박스 목록을 돌려준다 ([이미지 관리 문서](https://docs.roboflow.com/datasets/manage/manage-images)).

무료 플랜 조건도 확인해 둘 것이 있다. 가격 페이지 기준 **Public 플랜은 무료, 월 15크레딧, 프로젝트 10개이며, 「데이터와 모델이 Roboflow Universe에 오픈소스로 공개」**된다 ([Roboflow 가격](https://roboflow.com/pricing)). 〔추론〕 사람이 단 test 셋을 올리면 그것도 공개된다. 프레임에 이름이나 소속이 비치지 않는지는 업로드 전에 확인할 일이다.

재지 않은 것은 따로 기억해 둘 가치가 있다. 어떤 공개 벤치마크도 **같은 모양에 색만 다른 두 물체(분홍 대 빨강)의 구분**, **19–94 px 물체**, **JPEG 품질 약 50에서 VLM의 판별력**, **VLM 박스 출력이 실행할 때마다 얼마나 흔들리는지**를 재지 않았다. Roboflow Vision Evals는 반복 실행 평균만 내고 분산은 공개하지 않는다 ([Roboflow Vision Evals](https://playground.roboflow.com/evals)). 배치 규칙으로 학습 데이터를 라벨했을 때의 정확도, 사람 검토 표본을 몇 %로 잡아야 하는지에 대한 권장치도 찾지 못했다. 도구 쪽에서는 네 가지가 문서에 없었다. 무료 플랜에서 어떤 MCP 도구와 Auto Label 모델을 쓸 수 있는지(`available` 표시), 밖에서 학습한 YOLOv8 가중치를 Auto Label이 받는지, X-AnyLabeling `yolo2xlabel`이 신뢰도 열이 붙은 6열 txt를 받는지, Ctrl+B가 이미 라벨이 있는 이미지를 건너뛰는지다. 무엇보다 **우리 프리라벨의 클래스별·노출별 오답률**이 측정되지 않았다. 아래 실험들이 이 빈칸을 채운다.

## 추천 파이프라인: 우리 모델이 제안하고, 에이전트가 나르고, 사람이 정한다

| 단계 | 누가 | 무엇을 | 도구 | 근거 |
|---|---|---|---|---|
| 0. test 먼저 떼기 | 사람 | 세션 단위로 test를 먼저 분리한다. **모델 출력을 보지 않고** 처음부터 라벨한다. 재검은 무작위 표본을 다른 사람(또는 다른 날)이 다시 달아 대조한다. 평가 대상 모델은 재검 대상을 고르지 않는다 | X-AnyLabeling 수동, 또는 Roboflow 수동(자동 라벨 작업을 절대 걸지 않는 별도 배치) | 프로젝트 규칙. RF100-VL도 test 전수 재검증 |
| 1. 초안 생성 | 에이전트 | console_v2·tool_v3를 로컬에서 파이썬 루프로 돌린다. 8클래스 번호로 합쳐 YOLO txt를 만들고, 검출 없는 이미지도 빈 txt를 만들고, 같은 파일명 충돌을 막고, 모델 버전과 임계값을 함께 기록한다 | Ultralytics (파이 venv, CPU) | 문서 (빈 txt 미생성, 이어붙기 이슈) |
| 2. 의심 목록 | 에이전트 | 한 프레임에 같은 버튼 2개, 배치 순서 모순(버튼이 3개 이상 보일 때만), B3·EMO 박스 전부, 낮은 신뢰도 박스를 표시해 검토 순서 맨 앞으로 보낸다 | 짧은 스크립트 | 〔추론〕 → 실험 2로 검증 |
| 3. 사람 검토 | 사람 | 모든 프레임을 보되 의심 목록부터 본다. B3·EMO가 확신이 안 서면 추측하지 않고 표시한다 | 1순위: X-AnyLabeling-CPU.exe (`yolo2xlabel` → 편집 → `xlabel2yolo`). 2순위: Roboflow 검토 작업(`is_prediction=True`로 업로드) | 문서 + 원칙 |
| 4. 회수 | 에이전트 | 라벨만 받아 로컬 원본과 파일명으로 짝짓는다. labelmap과 overwrite를 명시한다. 내려받은 이미지로는 학습하지 않는다 | 로컬 그대로, 또는 Roboflow SDK·CLI (`search_export`, 이미지 API) | 문서 + 프로젝트 기록 |
| 5. 학습 후 재점검 | 에이전트 → 사람 | train/val에서만 의심 라벨 순위를 내고 사람이 다시 확인한다. 사람만 단 val 조각은 유지한다 | FiftyOne mistakenness 또는 cleanlab (K-fold) | 문서 |
| 6. 다음 라운드 | 반복 | 새 모델로 1단계부터 다시 한다. 채택된 초안이 오답을 굳히지 않는지 실험 1의 수치를 라운드마다 다시 잰다 | — | 확인 편향 연구 |

Roboflow MCP는 3–4단계를 대화로 조작하고 싶을 때 선택적으로 붙인다. 사람이 OAuth 로그인을 한 번 하고 나면 검토 작업 생성, 진행 조회, 내보내기를 에이전트가 맡을 수 있다. 수천 장의 초안 업로드는 SDK·CLI가 맡는다. 일부러 뺀 대안은 다섯 가지다. 텍스트 제로샷 자동 라벨(버튼 구분 불가가 문서화됨), 색 규칙 자동 라벨러(122건), Claude가 전체 프레임에 직접 박스 그리기(작은 물체 근거 없음), 사람 없는 자동 확정(틀린 라벨이 더 해로움), 무료 플랜에서의 Label Assist 대량 사용(크레딧 초과)이다. 공구 쪽 초안 개선(SAM 3 예시 박스 등)과 VLM 검증자는 실험 결과가 나온 뒤 2단계에 끼워 넣을지 정한다.

## 결판을 낼 작은 실험 6개

| # | 실험 | 방법 요약 | 푸는 질문 | 준비와 비용 |
|---|---|---|---|---|
| 1 | **프리라벨 오답률** | train/val 후보에서 50장을 고른다(어두운 9 ms 노출, 손이 가린 프레임, 장갑 낀 손의 공구가 섞이도록). 사람이 **프리라벨을 보지 않고** 라벨한 뒤, console_v2·tool_v3 결과와 겹침 50% 기준으로 대조한다. 클래스별로 맞음, 클래스 틀림, 가짜 박스, 놓침을 세고, B3↔EMO 뒤바뀜은 노출별로 센다. 임계값 3–4개에서 반복한다 | 92%가 실제로 몇 % 정답인가. 임계값은 얼마로 할까. 어느 클래스를 전수 검토할까 | 사람 라벨 50장, 파이 CPU, 0원 |
| 2 | **일관성 검사 적중률** | 실험 1에서 찾은 오류에 「같은 버튼 2개」와 「배치 순서」 규칙을 돌린다. 오류를 몇 건 잡는지, 정상 박스를 몇 건 잘못 잡는지 센다 | 배치가 색과 달리 노출에 강한가. 의심 목록으로 쓸 만한가 | 스크립트만, 0원 |
| 3 | **VLM 검증자** | 같은 50장에서 B3·EMO 박스와 장갑·손잡이 오검출을 모은다. 모델과 설정을 고정한 Claude API에 박스를 그린 전체 프레임, 200 px 이상으로 키운 크롭, 버튼별 기준 크롭을 보내 {B1, B2, B3, B4, EMO, 버튼 아님} 중에서 고르게 한다. 사람 라벨과 대조하고, 같은 입력을 2회 돌려 흔들림도 본다 | 실험 2가 못 잡는 오류를 VLM이 잡는가 | 외부 전송 승인 필요. 몇 달러 이하〔추론, 앞 절 가격 기준〕 |
| 4 | **공구 예시 기반 모델** | 공구 50장에서 tool_v3와 SAM 3 예시 박스(또는 YOLOE `refer_image`)를 사람 라벨과 비교한다 | tool_v3의 약점을 메울 수 있는가 | 데스크톱 GPU, PyTorch 2.7 이상 cu128, SAM 3 가중치 접근 승인 |
| 5 | **Roboflow 연결 점검** | (가) 사람이 OAuth 로그인한 뒤 `autolabel models` 목록으로 무료 플랜에서 쓸 수 있는 모델과 장당 크레딧을 확인한다. (나) 프레임 1장을 SDK 1.3.6 이상으로 올리고 `search_export`로 받아 로컬 원본과 SHA-256을 비교한다. 버전 다운로드본과도 비교한다 | 무료 플랜에서 무엇이 되나. 품질 75 재압축은 어디서 생기나 | 로그인 1회, 크레딧 거의 0 |
| 6 | **X-AnyLabeling 왕복** | console_v2를 ONNX로 바꿔 YAML로 등록하고 5장에 Ctrl+B를 돌린다. 신뢰도 열이 있는 6열 txt를 `yolo2xlabel` → `xlabel2yolo`로 왕복시킨 뒤 원래 txt와 비교해 클래스 순서가 보존되는지 본다 | 문서에 없는 두 가지(6열 수용, 클래스 순서 보존) | 데스크톱, 짧은 작업 |

순서는 1 → 2 → 6이 먼저다. 셋 다 로컬에서 무료로 끝나고, 실험 1의 오류 목록이 실험 2의 재료가 된다. 실험 3·4·5는 실험 1의 결과를 보고 필요할 때만 한다. 예를 들어 B3↔EMO 오류가 드물고 실험 2가 그것을 거의 잡는다면 VLM 실험은 할 이유가 없다. 실험 1의 사람 라벨 50장은 test가 아니라 train/val 후보에서 뽑는다. 그래야 실험이 끝난 뒤 학습 데이터로 다시 쓸 수 있고 test 규칙도 지켜진다.

## 맺음

이 조사로 질문이 바뀌었다. 「어떤 도구가 라벨을 자동으로 달아 주나」에 대한 답은 이미 나와 있다. 운반은 에이전트가 문서화된 명령으로 하고, 초안은 우리 모델이 로컬에서 무료로 만든다. 남은 질문은 「**어떤 라벨을 사람 없이 믿어도 되나**」다. 이 답은 외부 벤치마크에서는 나오지 않는다. 그 어떤 벤치마크도 작은 버튼, 품질 53의 JPEG, 어두운 노출, 정체성 클래스라는 우리 조건을 잰 적이 없기 때문이다. 답은 우리 프리라벨의 클래스별·노출별 오답률이라는, 50장이면 잴 수 있는 수치에서 나온다. 한 가지 더 새로 보인 것이 있다. 이 프로젝트에는 범용 도구에 없는 무료 검증 장치가 있다. 버튼마다 하나뿐이고 배치가 고정이라는 사실이다. 색 규칙이 실패한 자리에 배치 규칙을 쓰되, 라벨을 '다는' 데가 아니라 '의심을 표시하는' 데 쓰면 「틀린 라벨이 더 해롭다」는 원칙과 부딪히지 않고 사람의 검토 시간을 가장 위험한 박스에 모을 수 있다.

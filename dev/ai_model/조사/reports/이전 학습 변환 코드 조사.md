## 결론

1. **버튼 모델 `console_v2`**(현행)는 데스크톱(RTX 5060 + WSL2)에서 `dev/ai_model/train_console_v2.py` 로 학습했다 — Ultralytics 8.4.96, `yolov8n.pt` 전이학습, 200에폭·patience 40·batch 16·imgsz 640·seed 0, `hsv_h=0`(색 동결) + 저조도 중심의 Albumentations 6종. 데이터는 7월 모조 콘솔 ESP32 **VGA 가로** 652장을 Roboflow 에서 **Stretch 640×640** 으로 구운 것이다.
2. **변환(.pt → ONNX → .hef)은 스크립트가 아니라 문서에 적힌 명령**으로 했다(저장소 전체에 `.alls` 파일 0개, `hailomz`·ONNX 내보내기 코드 0개). v2 는 기본 alls 에 `optimization_level=1`·`calibset_size=652` 두 줄을 더하고 헤드 conv 6곳에서 그래프를 잘랐다. **alls·onnx·pt·캘리브 폴더·model zoo 패치·HAR 은 저장소에 없다.**
3. **공구 모델 `tool_v1`~`v4`** 는 Colab T4 에서 `yolov8n`·640·100에폭·patience 20·색 증강 켬(`hsv_h 0.015`/`s 0.7`/`v 0.4`)·`degrees 30`·`flipud 0.5` 로 **같은 값**을 썼다(v2 만 `degrees 10`·`flipud 0`). 현행 `tool_v3.pt` 는 **30에폭에서 끊은 체크포인트**이고, `.hef` 로 바꾼 적 없이 **파이 CPU(별도 프로세스)** 에서 `.pt` 그대로 돈다.
4. **지금 런타임 입력은 console_v2 학습 데이터와 여러 면에서 다르다** — 해상도(VGA 가로 → XGA 세로 768×1024), 640 맞추기 방향(세로 1.33배 늘림 → 가로 1.33배 늘림), 왜곡보정(학습 없음 → 실행 켬), 노출 상한(공장값 → 약 9ms), JPEG 압축 횟수(Roboflow 재압축 포함 2회 → 1회). 색 순서(RGB)·dtype(uint8)·클래스 순서는 일치한다(§7).
5. 부수 발견 — `Rpi5/Demo/models/best.pt` 는 문서(`Rpi5/Demo/docs/TESTING_FSM.md:72` 「console_v1 5클래스」)와 달리 **`person_v1`(사람 1클래스)** 이다(체크포인트 직접 확인, §5.5).

## 용어 풀이 (처음 한 번만)

| 용어 | 쉬운 뜻 |
|---|---|
| 전이학습 | 이미 다른 사진(COCO 80종)으로 배운 모델(`yolov8n.pt`)을 출발점으로 삼아 우리 클래스만 새로 가르치는 것 |
| 에폭 / patience | 에폭 = 학습 데이터를 한 바퀴 다 보는 단위. patience = 검증 점수가 이 에폭 수만큼 안 오르면 학습을 일찍 멈춤 |
| 증강 | 학습 중 사진을 일부러 어둡게·흐리게·돌리게 바꿔 보여 주는 것. 새 정보를 만들지는 않고 강건성을 가르친다 |
| 늘림(Stretch) / 레터박스(letterbox) | 사진을 640×640 정사각형으로 맞추는 두 방법. 늘림 = 가로세로 비율을 무시하고 잡아 늘림(동그라미가 타원이 됨). 레터박스 = 비율을 지키고 남는 곳을 회색 여백으로 채움 |
| 양자화 | 모델의 계산을 소수(float)에서 8비트 정수로 줄이는 것. Hailo 칩은 정수로만 계산한다 |
| 캘리브레이션(캘리브) | 양자화할 때 「값이 어느 범위에 들어오나」를 재기 위해 넣는 대표 사진 묶음. 라벨은 필요 없다 |
| ONNX / opset | 여러 도구가 읽는 모델 파일 형식 / 그 형식의 연산 규격 버전 |
| DFC · hailomz · HAR · HEF | DFC = Hailo 의 변환기(Dataflow Compiler). hailomz = Hailo Model Zoo 의 명령줄 도구(DFC 를 감싼 것). HAR = 변환 중간 산출물. HEF(`.hef`) = Hailo 칩에서 도는 최종 파일 |
| NMS | 같은 물체에 겹쳐 나온 박스들 중 점수 높은 하나만 남기는 후처리. 우리 `.hef` 는 이것을 **칩 쪽 후처리로 포함**한다 |
| IoU | 두 박스가 겹친 넓이 ÷ 합친 넓이. 1 이면 완전히 같은 박스 |
| mAP50 / mAP50-95 | 정답과 IoU 0.5 이상이면 맞다고 칠 때의 평균 정밀도 / IoU 기준을 0.5~0.95 로 올려 가며 평균낸 값 |
| conf 임계 | 모델이 낸 점수(0~1)가 이 값 이상인 검출만 쓴다는 문턱 |
| pHash | 사진을 64비트 지문으로 줄인 것. 두 지문이 다른 비트 수(해밍거리)가 작으면 거의 같은 사진 |
| 누출(leakage) | 학습용과 시험용에 거의 같은 사진이 갈라져 들어가 점수가 거짓으로 높아지는 것 |
| 네거티브 | 찾을 물체가 없는(빈 라벨) 사진. 「이건 아니다」를 가르친다 |
| 프리라벨 | 기존 모델의 검출 결과를 초벌 라벨로 쓰는 것. 사람이 고쳐야 한다 |
| 체크포인트 | 학습 중간·끝에 저장한 `.pt`. Ultralytics 는 그 안에 `train_args`(학습 인자 전체)를 함께 저장한다 |

**`data.yaml` 경로 교정 함수** — Roboflow 가 `train: ../train/images` 로 적어 Ultralytics 가 못 찾는 문제를, 받을 때마다 절대 `path:` + 상대 `train:/val:` 로 고친다(`download_dataset.py:42-58`, 호출 `:82`).

```python
def fix_data_yaml(location: str) -> None:
    root = Path(location).resolve()
    y = root / "data.yaml"
    lines, out = y.read_text(encoding="utf-8").splitlines(), []
    for line in lines:
        key = line.split(":", 1)[0].strip()
        if key in ("train", "val", "test", "path"):
            continue                      # 기존 경로 줄은 버리고 아래에서 다시 씀
        out.append(line)
    out += [f"path: {root}", "train: train/images", "val: valid/images"]
    if (root / "test" / "images").is_dir():
        out.append("test: test/images")
    y.write_text("\n".join(out) + "\n", encoding="utf-8")
```

**분할 방법의 약점(문서가 스스로 적은 것)**
- valid 130장은 train 과 **같은 4세션·같은 날·같은 조명**에서 시간순으로 자른 옆 프레임이다 → valid 점수는 낙관적이고 변별력이 거의 없다(`성능검증-저널.md:2315-2318`).
- 652장에 **버튼 없는 배경 사진이 0장**(학습 로그 `0 backgrounds`)(`console_v2_학습가이드.md:154`).
- pHash 중복 제거는 **세션 폴더 안에서만** 비교한다(`dedupe_raw.py:63-72`) — 세션 간 비교는 하지 않는다.

```python
def split_by_source(items, valid_ratio=0.10, seed=0):
    by_source = collections.defaultdict(list)
    for it in items:
        by_source[it.source].append(it)
    target = len(items) * valid_ratio
    sources = sorted(by_source)
    random.Random(seed).shuffle(sources)
    assign, n_valid = {}, 0
    for s in sources:
        size = len(by_source[s])
        if n_valid < target and size <= max(1, target * 0.5):
            assign[s] = 'valid'; n_valid += size
        else:
            assign[s] = 'train'
    return assign
```

### 4.5 `.alls` 에 더한 두 줄과 그 이유 (v2)

```
model_optimization_flavor(optimization_level=1)
model_optimization_config(calibration, calibset_size=652)
```
(`가이드:170-172` · `성능검증-저널.md:2334`)

- DFC 소스(`mo_config.py`) 직독 결과 — `if dataset_length < 1024: opt=1` **다음에** `if not has_gpu: opt=0` 이 덮어써 **GPU 가 없으면 장수와 무관하게 level 0**. `CalibrationConfig.calibset_size` 기본값은 **64** 이고 `min(calibset_size, 장수)` 라 더 넣어도 64장만 쓴다(v1 이 122장 넣고 64장만 쓴 원인)(`가이드:135-138`).
- 해법 = 레벨을 명시하면 `get_flavor_config` 가 사용자 값을 그대로 쓴다. level 1 = equalization + **bias_correction**, 경사학습 코드가 없어 **GPU 불필요**. level 1 이하면 압축(4bit)도 0 으로 유지(`가이드:140-147`).
- 먹었는지 확인할 로그 — `Reducing compression level to 0 because requested optimization level equal or less than 1`(성공) · `Using dataset with 652 entries for calibration` · 🔴 `Reducing optimization level to 0 ... no available GPU` 가 뜨면 실패(`가이드:183`).
- 소요 = bias_correction 이 CPU 라 블록당 약 24초 × 73블록, 전체 약 35분(`성능검증-저널.md:2338-2345`).

### 5.2 HailoRT 호출과 NMS 출력 해석

- 장치: `VDevice` 를 **프로세스당 하나** 만들어 공유(`HAILO_OUT_OF_PHYSICAL_DEVICES` 방지), 스케줄러 `ROUND_ROBIN`, `HEF` 를 `ConfigureParams.create_from_hef(interface=PCIe)` 로 올림(`Rpi5/Demo/hailo_device.py:50-86`). `network_group.activate()` 는 부르지 않음(`detector.py:100-101`).
- 스트림 인자: `InputVStreamParams.make` / `OutputVStreamParams.make` 기본값(`detector.py:94-95`) — 형식은 HEF 의 입력 UINT8 · 출력 FLOAT32 NMS 를 따른다(§4.7).
- 해석(`detector.py:116-130`):

```python
raw = list(output.values())[0][0]          # 배치 0 → 클래스별 목록
for cls_id, cls_dets in enumerate(raw):    # cls_id 0..4 = B1,B2,B3,B4,EMO (detector.py:103)
    arr = np.array(cls_dets)
    if arr.ndim != 2 or arr.shape[0] == 0:
        continue
    for det in arr:
        ymin, xmin, ymax, xmax, score = det            # 0~1 정규화, y 가 먼저
        if score < config.YOLO_CONF_LOW:               # 0.50 (config.py:130)
            continue
        detections.append((cls_id, float(score),
                           int(xmin * w), int(ymin * h), int(xmax * w), int(ymax * h)))
```
  - 거르는 문턱이 두 겹이다: 칩 NMS 0.2(§4.7) → 코드 `YOLO_CONF_LOW 0.50`.
  - 좌표는 **원래 프레임(768×1024) 크기**를 곱해 되돌린다. 늘림은 축별 선형이라 정규화 좌표를 곱하면 정확히 되돌아간다(`score_hef.py:14` 도 같은 논리).
  - 클래스 순서는 `.hef` 의 클래스 인덱스 = 학습 `data.yaml` `names` 순서(`[B1,B2,B3,B4,EMO]` — 확인 문구 `download_dataset.py:84` · 업로드 매핑 `upload_roboflow.py:45`)다.

### 8.2 바꿔야 하거나 결정이 필요한 것 (문서가 이미 지적한 것만)

1. **640 맞추기 방식** — 학습(Roboflow Stretch)과 실행(`cv2.resize` 늘림)의 방향이 세로 프레임에서 어긋났다(`통합문서.md:464`). 이론 문서는 「Stretch 쓰지 말고 비율 유지」와 `imgsz=(640,480)` 직사각 입력을 선택지로 적었고(`학습이론.md:116,136,384`), 데이터확보 설계는 이 문제를 ④ 학습 설계로 넘겼다(`specs/2026-09-16-비전모델-데이터확보-design.md:136`). **학습·캘리브·런타임 `detector.py:110` 을 한 방식으로 맞춰야 한다.**
2. **압축 조건** — 「파일 형식이 아니라 모델이 보는 픽셀 조건을 맞춘다」: 한 번 압축(≈53)·XGA·같은 가공 코드·640 방식 · JPEG 원본 보관 → 로컬 가공본과 라벨만 짝짓기 · JPEG 압축 증강(`성능검증-저널.md:3028-3031`). 현 AUGS 의 q60~100 은 53 을 덮지 않는다(§7.1-5).
3. **해상도 기준 px 값** — `export_labels.py` 의 폭 15~100px 는 VGA 실측값(`:49-51`). 런타임에는 `frame_orient.px_scale`(긴 변 ÷ 640)이 있다(`frame_orient.py:92-94`).
4. **중복 제거 임계** — 도구 기본 10·폴더별(`dedupe_raw.py:54-55,63-72`) vs 설계 = 해밍 **6**·세션 전체를 합쳐(`specs/2026-09-16-…:98,114`).
5. **라벨 규칙** — v2(Modal)와 현행 가이드(버튼 전체)가 다르다. 두 정의를 눌림 근처 프레임에서 실측하기로 함(`specs/2026-09-16-…:49`). 옛 `console_v2-mjefr`·`tool-holdout` 은 섞지 않는다(`:117`).

## Ⅰ. 프로젝트 개요

| ※ 평가항목 : 기획력 (필요성, 차별성) |
|---|

### 1. 프로젝트 소개

**프로젝트 정의**

- 1인칭 Vision AI 웨어러블 기반 작업 순서 위반 감지·차단 시스템
- 스마트 글라스가 버튼·손끝·공구 인식 → 미리 정의된 정비 순서와 대조
- 위반 시 시청각 경고 / 강행 시 인터락 차단 — 조작이 설비에 전달되지 않음

**기획 의도**

- 순서 검증을 사람의 주의력이 아니라 AI가 한 번 더 확인
- 눌린 뒤가 아니라 행동 직전에 개입
- 기존 콘솔 대체 없이 감지·차단 레이어만 부가
- 인식과 판정 분리 — 비전은 위치만, 정오 판단은 FSM

**시스템 동작 — 인식 · 판정 · 개입**

- 인식 — 1인칭 비전으로 버튼 위치 · 손끝 좌표 · 쥔 공구 검출
- 판정 — FSM 6단계 상태머신이 기대 단계와 대조 → 정상/위반 분기
- 개입 — 화면·타워램프 경고 → 강행 시 인터락 차단

### 2. 개발 배경 및 필요성

**정비 작업의 사고 위험**

- 반도체 공정 = 실란·아르신·포스핀·불산 등 유해가스 취급. 불산은 반도체 제조에 가장 많이 사용
- 정비 = 설비 정지 후 사람이 직접 손대는 작업 → 위험에 가장 근접
- 제조업 끼임 사망사고 272건 중 54%가 수리·정비·청소 등 비정형 작업 중 발생 (산업안전보건연구원, 2016~2019)
- 2022년 제빵공장 배합기 이물질 제거 중 끼임 사망
- 2026.06 국내 반도체 현장 가스 누출·화재 연속 발생

**유해 가스 누출 후 대응 시간 부재**

- 불산 — 뼈·폐 손상, 체내 침투로 전신 마비·심실세동
- 외관상 무증상 상태에서도 진행 → 노출 사실 인지가 늦음
- 응급처치는 즉시 세척뿐. 사고 후 보고·조사로는 예방 불가
- → 사람의 행동 이전 차단 필요

**기존 수단으로 미포착되는 정비 중 순서 위반**

- 설비는 자기가 아는 조작의 순서만 강제 — 허가(permissive) 인터락 · 트랩키 인터락
- 강제 대상 = 정비에 들어가는 순서 (에너지 차단 여부 · 접근 허용 여부)
- 정비 안에서의 순서는 미강제 — 쥔 공구 · 손이 닿는 지점은 설비에 신호로 유입되지 않음
- 정비 중 인터락 일부 우회
- 남는 방어선 = 작업자의 절차서 준수뿐 → 사람 의존 통제의 한계 (NIOSH 통제의 위계)

**목적 및 적용 범위**

- 목적 — 반도체 장비 정비 시퀀스의 순서 위반을 행동 이전에 감지·차단
- 반도체 장비 정비(PM) — 시연 시나리오는 PECVD 정비로 가정
- 클린룸 형광등 계열 조명 환경
- 휴먼 에러 중 순서 위반(누락·역순) 1종 · 단일 콘솔의 공정 시퀀스 1종으로 한정
- 콘솔은 시연용 모조품 — 가스 차단·펌프·냉각·벤트 등 실제 반도체 장비 동작 없음.
- 검증 대상 = “순서 준수 여부를 비전 AI가 감지·차단하는가”

### 3. 프로젝트 특·장점

**차별점 ① — 상태를 보는 기존 안전장치 / 행위의 순서를 보는 본 시스템**

- 인터락 = 설비 상태 감시(문 열림·접근·온도). 순서 강제 수단(허가·트랩키)도 설비에 신호로 들어오는 조작만 대상
- 기존 산업안전 비전 AI = 보호구 착용·침입·쓰러짐 등 상태·사건 감지 → 관리자 통보
- 양쪽 모두 쥔 공구 · 손을 뻗는 버튼은 인지 불가
- 본 시스템 = 1인칭 비전으로 행위의 순서 판정 → 작업자 본인 피드백 → 차단
- 비전 AI의 순서 검증 적용 사례는 미확인

**차별점 ② — 3인칭이 아닌 1인칭**

- 산업안전 비전 AI = 3인칭 고정 CCTV가 표준
- 3인칭은 손·공구가 작업자 몸에 가림 — 정비는 손끝에서 발생
- 작업자 시점 = 손·버튼·공구가 항상 화면 내

**기술적 장점**

- 인식·판정 분리 → 모델과 순서 로직의 독립 교체 가능
- 엣지 온디바이스 추론 → 설비 레시피·작업 지시의 외부 유출 없음. 폐쇄망(FAB) 적합
- 커스텀 데이터셋 — 일반 형광등·클린룸 환경 포함해 직접 촬영·라벨링

**통신 경로**

- 핵심 경로 : 글라스 → RPi5 → Arduino
- 글라스 → RPi5 : WiFi TCP 스트리밍 (대역폭 확보)
- RPi5 → Arduino : 유선 Serial + ACK (명령 유실 방지)
- 버튼 → RPi5 : GPIO 직결 (지연 최소화)

**전체 동작 흐름**

- 착용한 글라스가 작업자 시야를 실시간 촬영 · 무선 전송
- 엣지 장치가 프레임마다 버튼·손·공구를 검출하고 손끝이 머문 버튼 구역을 확인
- 기대 단계와 대조 — 일치하면 다음 단계 진행, 어긋나면 화면·경고등으로 즉시 경고
- 강행 시 인터락 차단, 해제 후 순서 확인부터 다시 반복

### 3. 주요 적용 기술

**정비 시나리오**

- 시연 시나리오는 반도체 장비 정비(웻클린 make-safe)로 가정한다
- 네 단계가 모두 안전 임계다 — 한 단계라도 누락·역순이면 사고로 이어진다

| 단계 | 작업자가 하는 일 | 시스템이 보는 것 |
|---|---|---|
| 1. 클린·가스차단 | B1 누름 → 10초 대기 | 손끝이 어느 버튼 구역에 있나 |
| 2. 펌프/퍼지 | B2 누름 → 10초 대기 + 렌치 지참 | 손끝이 어느 버튼 구역에 있나 · 쥔 공구가 요구 공구인가 |
| 3. 전극 냉각 | B3 누름 → 10초 대기 | 손끝이 어느 버튼 구역에 있나 |
| 4. 챔버 벤트 | B4 누름 → 공정 완료 | 손끝이 어느 버튼 구역에 있나 |

- 버튼을 누르는 것만으로 단계가 넘어가지 않는다 — 뒤따르는 대기까지 끝나야 한 단계다
- 그 사이에 다른 버튼을 누르면 순서 위반이다
- 대기 시간은 시연을 위해 10초로 잡은 값이다 — 실제 공정 시간이 아니다
- 비상정지는 판정을 거치지 않고 즉시 차단 · 해제 시 첫 단계로 되돌린다

**버튼 검출 - YOLOv8n**

- 1인칭 영상에서 버튼 5종(B1~B4·비상정지)을 실시간 검출
- YOLO는 이미지를 격자로 나눠 상자와 클래스 확률을 한 번의 연산으로 함께 예측하는 1단계 방식 — 2단계 방식(R-CNN 계열)보다 빨라 엣지 실시간 추론에 맞다
- 경량 모델 YOLOv8n(nano) 채택 — 저전력 엣지 장치에서 동작
- 클린룸·콘솔 환경을 직접 촬영·라벨링한 커스텀 데이터셋으로 학습

**손 추적 - 21점 손 랜드마크**

- 손바닥 검출 + 21점 관절 회귀의 2단 구조 — 가림과 회전에 강건
- 손 모델을 NPU용으로 변환해 엣지에서 실행
- 검지 끝 좌표를 판정 입력으로 쓴다

**공구 검출**

- 드라이버·렌치·플라이어 3종을 1인칭 영상에서 검출
- 공개 데이터 2종을 출처 다양성을 기준으로 병합해 직접 학습
- 서브 작업에서 요구 공구를 쥐었는지 확인한다

**손-객체 융합(HOI)과 체류 타이머**

- 버튼 상자와 손끝 좌표를 겹쳐 어느 버튼 구역에 들어왔는지 판단
- 구역을 두 단계로 나눈 사각 도넛 — 바깥 링은 접근, 안쪽 상자는 위험
- 링에서는 타이머만 쌓이고 경고는 안쪽 상자에서만 발화 — 구역을 넓히되 오경보를 늘리지 않는 구조
- 체류 0.3초로 스침과 의도적 접근을 가른다
- 갭메우기 0.3초 — 누르는 순간 손이 버튼을 가려 인식이 끊기는 것을 메운다

**순서 판정 - FSM(유한 상태 머신) 6단계**

- IDLE · READY · PROCESS RUN · MONITOR · WARNING · BLOCK 6상태
- 기대 단계 N을 상태로 들고 있다가, 해당 버튼이면 정답 / 그 외 공정 버튼이면 오답
- 규칙 하나로 누락(뒤 단계 건너뜀)과 역순(앞 단계 되돌림)이 모두 잡힌다
- 오답은 단계를 진전시키지 않는다 — 차단 후 해제해도 기대 단계는 그대로다

**개입 - 2단계 대응과 인터락**

- 오답 구역에 체류하면 경고 — 화면 팝업 + 타워램프·부저
- 경고를 무시하고 누르면 차단
- 차단 명령은 수신 확인(ACK)까지 받아야 성립한다 — 응답이 없으면 이상을 알린다
- 해제는 작업자 본인이 화면에서 한다

**엣지 가속 - NPU + INT8 양자화**

- 학습한 모델을 NPU용으로 변환해 엣지 장치에서 실행
- INT8 양자화 — 32비트 실수 가중치를 8비트 정수로 바꿔 연산량과 메모리를 줄인다
- 버튼·손바닥·손 3개 모델이 한 장치를 공유한다
- 클라우드를 거치지 않아 통신 지연이 없고, 작업 영상이 밖으로 나가지 않는다

**생성형 AI - 엣지 LLM**

- 작업 안내를 음성으로 주기 위한 기술 선정 근거를 확보했다
- 소형 LLM 6종을 같은 조건에서 속도·첫 응답 지연·메모리로 비교
- 온디바이스 전용 설계 모델이 전 항목 1위 — 후보를 확정했다

### 5. 기타 사항 [본문에서 표현되지 못한 프로젝트의 가치(Value) 및 제작 노력]

**알고리즘의 창작성 - 왜 이렇게 설계했나**

- 인식과 판정을 두 계층으로 나눴다 — 비전은 위치만 내고, 옳고 그름은 상태 기계가 판단한다
- 관심사의 분리 — 두 층은 바뀌는 이유가 다르다. 모델을 바꿔도 순서 로직은 그대로 쓴다
- 상태 기계는 결정론적이라 같은 입력에 같은 판정이 나온다 — 회귀 테스트로 검증할 수 있다
- 버튼 구역을 고정 좌표로 지정하지 않는다 — 검출한 버튼 상자 자체를 구역으로 삼는다
- 1인칭이라 화면이 흔들려도 구역이 버튼을 따라간다
- 버튼과 공구를 한 모델에 합치지 않았다 — 버튼은 색이 클래스를 정의해 색상 증강을 막았고, 공구는 형태로 구분해 같은 제약을 걸 이유가 없다
- 눌림 간격의 경계가 시간이 아니라 프레임 수라는 것을 실측으로 확인했다 — 처리 속도가 곧 허용 눌림 속도다
- 이론 배경 — 손-객체 상호작용 검출 · 체류 시간을 이용한 시간 필터링 · 안전 불변식을 유한 상태 기계로 표현하기

**프로그램의 가치 - 핵심 소스코드와 측정 구조**

- recipe.json — 정답 순서의 런타임 정본. 정비 순서를 코드가 아니라 데이터로 둔다
- ※ 넣을 코드 이미지: 단계 정의와 서브 작업 부분
- roi_zones.py — 판정 규칙의 단일 출처. 두 단계 구역과 되돌림 스위치가 한 파일에 있다
- ※ 넣을 코드 이미지: 구역 판정 함수 전문
- fsm.py (감시) — 누르기 전에 판정한다. 접근 구역에서는 시간만 쌓고 위험 구역에서만 경고한다
- ※ 넣을 코드 이미지: 비전 갱신 함수의 발화 조건
- fsm.py (판정) — 오답은 단계를 진전시키지 않는다
- ※ 넣을 코드 이미지: 버튼 눌림 처리와 단계 진전 부분
- interlock.py · console_interlock.ino — 차단 명령과 응답 확인의 왕복
- ※ 넣을 코드 이미지: 응답 확인·재시도 부분과 제어 보드의 응답 회신 부분
- safety_console.py — 비상정지가 복귀하지 않으면 해제를 거부한다
- ※ 넣을 코드 이미지: 해제 거부 부분
- 판정 규칙을 의존성 없는 별도 모듈로 뺐다 — 런타임과 측정 도구가 같은 규칙을 쓰도록 구조로 보장했다
- 규칙이 두 곳에 복제되면 측정값이 실제 동작을 대표하지 못한다. 문서상의 약속이 아니라 구조로 막았다
- 측정 체계 — 오프라인 재생기 · 체류 프로브 · 원자료 데이터베이스(22세션 19.2분)
- 봉인 홀드아웃(위반 61건 · 정상 85건)을 따로 두었고, 한 번 열면 소진되므로 아직 열지 않았다

**데이터의 가치와 라이선스**

- 버튼 데이터셋은 클린룸·콘솔 환경에서 직접 촬영·라벨링했다
- 평가용 113장은 전량 수동 라벨링했다 — 평가 대상 모델로 정답을 만들면 채점이 순환논리가 된다
- 학습과 평가 사이 누출 0
- 공구 데이터셋은 공개 데이터 2종을 병합해 29,809장으로 재구성했다 (학습 26,817 · 검증 2,992 · 누출 0)
- 재현성을 실증했다 — 엣지 장치와 클라우드에서 독립적으로 만든 결과물의 체크섬이 일치했다
- 라이선스 — 원본 2종 모두 CC BY 4.0. 저작자 표시 · 라이선스 명기 · 변경 사실 표기 세 가지가 의무이며 전부 이행했다
- 저작자 표시 — karthi-zqreo · ruri-binnw (Roboflow Universe)
- 변경 사실 — 두 데이터셋을 병합·재분할하고 네거티브 표본을 15% 보강했다

**안전 설계 - 고장이 나도 안전한 쪽으로**

- 비상정지를 평상시 닫힘 접점으로 배선했다 — 선이 끊어져도 비상으로 읽힌다
- 차단 명령은 보내고 끝내지 않는다 — 제어 보드의 응답으로 실행을 확인한다
- 응답이 없으면 재시도하고, 그래도 없으면 이상을 알린다. 보냈다와 차단됐다를 구분한다
- 연결이 끊겨도 프로그램이 죽지 않는다 — 재연결하면 마지막 명령을 다시 보내 릴레이 상태를 판정부와 맞춘다
- 비상정지가 물리적으로 복귀하지 않으면 해제와 초기화를 거부한다 — 입력이 순간 신호만 주므로 현재 상태를 다시 읽어 확인한다
- 오답은 단계를 진전시키지 않는다 — 단계를 올리는 코드가 파일 전체에 한 줄뿐이고 정답 분기에서만 도달한다
- 고장 시나리오 3종을 실물로 검증했다 — 제어 보드 분리 중 위반 / 비상정지 단선 상태 부팅 / 복귀 후 응답 회귀
- 이론 배경 — 실수 방지 설계(포카요케) · 다중 방어선(스위스 치즈 모델) · 고장이 안전한 쪽으로 나게 하는 fail-safe 원칙

**사용성의 근거**

- 경고가 잦으면 작업자가 경고를 무시하게 된다 — 경보 피로. 안전 장치가 있으나 마나가 되는 지점이다
- 그래서 구역을 두 단계로 나눴다. 접근 구역에서는 시간만 쌓고 경고는 위험 구역에서만 낸다
- 접근은 위반이 아니다 — 이 판단을 알고리즘으로 표현한 것이다
- 신호와 잡음을 가르는 문제로 보면, 접근 구역과 위험 구역에 서로 다른 판단 기준을 둔 것이다
- 화면은 지각·이해·예측 세 층으로 짜여 있다 — 무엇이 보이는가 · 지금 옳은가 · 다음에 무엇을 하는가

**수치를 다루는 규율과 정직성**

- 성능 수치는 측정 조건과 함께만 쓴다 — 조건을 쓸 수 없으면 수치를 뺀다
- 한 번의 촬영에서 나온 값을 성능으로 쓰지 않는다
- 데이터를 본 뒤 구간을 좁혀 얻은 값을 성능으로 쓰지 않는다
- 작업 완료 화면에 오탐지 건수를 넣지 않기로 했다 — 정답 라벨 없이는 셀 수 없다
- 만들지 못한 것이 아니라 만들지 않기로 결정한 것이다
- 유색 조명 아래에서 특정 버튼이 사실상 검출되지 않는 것을 발견했다. 안전 기능이 조용히 무력화되는 조건이라, 감추지 않고 적용 범위에서 제외했다
- 폐기된 결론을 지우지 않고 폐기 표시를 달아 남긴다 — 지우면 같은 오류를 되풀이한다

**AI 활용과 기록 관리**

- 설계와 기술 판단은 팀이 하고, 구현·디버깅을 가속하는 데 AI 코딩 도구를 썼다
- 프로젝트 지침과 현황을 단일 문서로 두어 두 개발 환경이 같은 맥락을 읽는다
- 세션을 시작할 때 두 환경의 동기화 상태와 이어서 할 작업을 표로 브리핑하는 훅을 만들었다
- 데이터셋·학습 결과 조회를 연결해 데이터에 근거한 판단을 지원했다
- 결선도와 핀맵까지 문서로 관리한다

### 2. 프로젝트 추진 과정에서의 문제점 및 해결방안

**프로젝트 관리 측면**

*① 물품 배송 지연으로 인한 하드웨어 착수 지연*

- 문제: 2차 물품이 예상보다 약 7주간 지연 도착(04.04 신청 → 05.20 도착)하여 하드웨어 통합 착수 지연
- 해결: 소프트웨어(AI 모델 학습·FSM 코드)를 먼저 병행 개발해 하드웨어 대기 시간을 흡수, 물품 도착 후 통합 일정을 재수립

*② 초기 범위 과다로 인한 핵심 시나리오 확정 지연*

- 문제: 초기 기획 범위가 방대해 핵심 시나리오 확정·문서화 지연
- 해결: 멘토 피드백을 반영해 "단일 반도체 공정 콘솔의 순서 위반 1종"으로 명시적 한정, 분리된 기능은 폐기가 아니라 '향후 확장'으로 보존

*③ 부품 성능 부족으로 인한 재발주*

- 문제: 초기 확보한 AI 가속기의 성능이 부족
- 해결: 성능 검토 후 Hailo-8(26 TOPS) 가속기를 추가 발주(3차)해 주 사양으로 확정

*④ 개발 시간, 장소 경합*

- 문제: 학사 또는 개인 일정으로 인한 개발 가용 시간 감소
- 해결: GitHub·Tailscale·NoMachine 기반 원격 협업 체계를 구축해 시간·장소 제약 없이 분산 개발이 가능하도록 정비

**프로젝트 개발 측면**

*① YOLO → Hailo HEF 변환 시 객체 미탐지·오라벨*

- 문제: 모델을 Hailo HEF로 변환한 뒤 객체 미탐지·오라벨 발생. 원인은 NMS 방식 불일치, 입력 형식 불일치(FLOAT32 vs UINT8), 클래스 수 불일치
- 해결: 입력 형식을 UINT8로 통일, 클래스 재맵핑, Python 직접 처리 파이프라인으로 전환, 검증된 YOLO 기본 모델 적용하여 변환 문제 해결

*② console_v1 실추론에서 B4(검정 버튼) 완전 미탐지*

- 문제: 학습 단계에서는 정상 탐지(console_v1 학습값 mAP50 0.987)·양자화 에뮬레이션도 정상. 그런데 실추론에서 B4만 0회 탐지
- 해결(원인 추적): ⓐ 학습 .pt에서 B4 정상 검출 → 학습·데이터 문제 배제 → ⓑ 양자화 .hef도 정상 검출(0.95) → 양자화 원인 반증 → ⓒ 고장 지점을 모델 변환이 아니라 배포·입력 단계로 좁힘
- 원인: 검정 버튼이 검정 배경 위에 있어 모델이 색이 아니라 경계(고주파)에만 의존하도록 학습됐고, 저해상도·압축 경로가 그 경계를 뭉갰다
- 대조: 카메라만 바꿔 촬영하니 B4가 살아났다. 다만 고정 카메라는 1인칭 웨어러블이라는 전제를 무너뜨려 채택할 수 없었다
- 조치: 카메라가 아니라 대상을 바꿨다 — 검정 버튼 면에 파랑 원 스티커를 붙여 색으로 구분되는 클래스로 만들었다. 재학습 결과 B4가 정상 검출된다(AP50 0.997, 모조 콘솔·클린룸 형광등 조건)

*③ fps 병목 (실시간성 목표 미달)*

- 문제: 목표 30fps에 대해 실측 평균 약 13fps. 초기에는 원인을 ESP32-S3의 WiFi TCP 전송 경로 상한으로 지목하고 목표를 15fps로 하향
- 해결: 전송이 병목이라면 대역폭이 포화되어야 하나 실사용률은 1.2%에 불과했다. 자원 사용률부터 다시 확인해 재조사한 결과, 병목은 네트워크가 아니라 카메라 내부 프레임 버퍼(fb_count=1)로 캡처와 전송이 겹치지 못하는 구조임을 규명. 펌웨어 3줄 수정으로 HOI 포함 23.96fps를 확보해 NFR-1(15fps)을 충족. 단 이 값은 손이 없는 정지 장면·단일 조건 측정치이며 최저 5.1fps 구간이 남아 있다

*④ MediaPipe 환경 호환성 충돌*

- 문제: hailo_platform은 Python 3.13 전용, MediaPipe는 aarch64/Python 3.13 미지원 → 공존 불가
- 해결: hailo_platform이 Python 3.13 전용이라 MediaPipe 프레임워크 자체는 설치할 수 없으나, 구글 MediaPipe의 손 모델(BlazePalm·BlazeHandLandmark)을 Hailo .hef로 포팅해 의존성을 hailo_platform+numpy+cv2로 줄임으로써 버전 충돌을 원천 제거. 2026년 7월 HOI(손-객체 융합) 경로 통합을 완료해 현재 버튼·팜·핸드 3개 모델이 하나의 Hailo 장치를 공유한다

*⑤ 순서 인식 오탐(스침) 억제*

- 문제: 손이 버튼을 스치기만 해도 위반으로 오탐될 수 있고, 누름 순간 손이 버튼을 가려 인식이 끊기는 채터 발생
- 해결: 체류 타이머와 갭메우기를 도입해 스침을 걸렀다. 체류 임계는 1.5초에서 시작해 실측으로 낮춰 0.3초로 확정했고, 갭메우기 0.3초로 누름 순간의 인식 끊김을 메운다

*⑥ 공구 인식 모델이 우리 실물 공구를 다른 종류로 오분류*

- 문제: 공개 데이터셋으로 학습한 공구 검출 모델이 우리가 보유한 오픈엔드 렌치를 렌치·스패너·드라이버 사이에서 오가며 분류. 위치 검출은 정상이고 클래스만 틀려, 공구 3종을 구별한다는 전제를 채우지 못함
- 해결: 증강·하이퍼파라미터를 조정한 재학습은 오히려 우리 도메인 성능을 악화시켜 원인이 아님을 확인. 데이터셋을 파일 단위가 아니라 출처 단위로 계수한 결과, 5,203장이지만 실질 출처는 118개뿐(렌치는 영상 3편)이라 다양성이 부족함을 규명. 출처 다양성을 관문으로 둔 데이터셋(약 29,800장, 최대 출처 점유 16% 이하)으로 재구성하자 같은 카메라·같은 프레임에서 검출이 0/8 → 4/8(운용 임계 conf 0.65)로 개선. 장수가 아니라 다양성임을 통제 실험으로 확인

*⑦ 음성 안내 도입을 위한 엣지 LLM 선정 근거 부재*

- 문제: 작업자에게 음성으로 안내하려면 라즈베리파이에서 대형 언어 모델(LLM)을 직접 구동해야 하는데, 어떤 모델이 이 하드웨어에서 실사용 가능한지에 대한 근거가 없었음
- 해결: 소형 LLM 6종(Gemma 3종·LFM2.5·Qwen3.5 2종)을 같은 조건에서 실측 비교(초당 토큰·첫 토큰 지연·콜드 적재 시간·적재 메모리). 최상위 후보는 2~3초 내 응답이 성립함을 확인했고, 모델 적재에 수 초~수십 초가 걸려 상주 구동이 사실상 필수임도 드러남. 또한 생각 과정을 출력하는 모델은 생성 예산을 모두 소진해 답을 내지 못하는 함정이 있어, 속도표만으로는 걸러지지 않고 응답을 직접 확인해야 함을 파악

### 3. 프로젝트를 통해 배우거나 느낀 점

**범위를 좁히는 것이 곧 완성도라는 것을 배웠다**

- 처음에는 여러 종류의 휴먼 에러를 모두 막는 시스템을 구상했다
- 멘토 피드백을 계기로 순서 위반 1종·단일 콘솔로 범위를 좁혔다
- 범위를 한정하자 검증·문서화·구현이 모두 명확해졌다
- 무엇을 하지 않을지 정하는 것이 완성의 핵심임을 체감했다
- 뺀 기능은 폐기가 아니라 향후 확장으로 남겨 두었다

**문제의 원인을 끝까지 추적하는 태도를 익혔다**

- B4 미탐지를 양자화 탓으로 성급히 결론짓지 않았다
- 학습 모델·에뮬레이션·실환경을 단계별로 대조했다
- 가설을 데이터로 하나씩 반증하며 원인을 좁혀 갔다
- 추측과 검증은 다르다는 것을 배웠다
- 반증 순서를 기록으로 남기니 다음 문제에도 같은 절차를 쓸 수 있었다

**원인을 단정하기 전에 자원 사용률부터 확인해야 한다는 것을 배웠다**

- 추론 자체는 약 11ms로 충분한데 전체 처리 속도가 낮았다
- 원인을 무선 전송 경로로 지목하고 하드웨어 한계라고 단정했다
- 대역폭 사용률이 1.2%뿐인 것을 확인하고 다시 조사했다
- 진짜 병목은 카메라 내부 프레임 버퍼였고 펌웨어 3줄로 해결됐다
- 상한을 측정한 것과 원인을 규명한 것은 다르다
- 자원 사용률을 먼저 보지 않으면 오진이 다음 결정까지 끌고 간다

**AI 성능은 데이터의 양이 아니라 다양성이 만든다는 것을 배웠다**

- 공구 인식이 실패했을 때 학습 설정을 의심해 증강과 하이퍼파라미터를 바꿔 재학습했다
- 결과는 오히려 나빠졌다 — 원인이 아니었다
- 데이터셋을 파일 수가 아니라 서로 다른 장면이 몇 개인가로 다시 셌다
- 수천 장이 사실은 백여 개 출처의 반복이었다
- 데이터를 바꾸자 같은 모델·같은 카메라에서 결과가 달라졌다
- 모델을 붙잡기 전에 데이터를 의심해야 한다는 것을 실험으로 배웠다

**소프트웨어·하드웨어·AI의 융합이 주는 어려움과 보람을 느꼈다**

- 비전 AI·상태 기계·시리얼 제어·릴레이·경보·웨어러블 카메라를 하나의 폐루프로 통합했다
- 통신 형식과 타이밍을 맞추는 일이 각 부분을 만드는 것만큼 오래 걸렸다
- 인터페이스 정합이 융합 시스템의 실제 난이도임을 배웠다
- 한 부분을 고치면 다른 부분이 흔들려 변경마다 전체를 다시 돌려 봐야 했다
- 각 부분이 맞물려 처음 끝까지 동작했을 때 큰 성취감을 느꼈다

**협업과 기록의 힘을 배웠다**

- 두 개발 환경을 오가며 작업했다
- 형상관리와 단일 정본이 없으면 팀 작업이 쉽게 어긋난다
- 같은 수치가 두 곳에 적히면 어느 쪽이 맞는지 알 수 없게 된다
- 기록을 남기니 몇 주 전 판단의 근거를 다시 찾을 수 있었다
- 꾸준한 기록과 공유가 프로젝트 지속성에 결정적임을 배웠다

**AI 도구를 쓰는 법을 배웠다**

- 설계와 기술 판단은 팀이 하고, 구현·디버깅을 가속하는 데 AI 코딩 도구를 썼다
- 프로젝트 지침과 현황을 단일 문서로 두니 두 개발 환경이 같은 맥락을 읽었다
- 반복 절차는 훅과 명령으로 코드화해 사람이 잊어도 도구가 챙기게 했다
- AI가 낸 결론도 근거를 대조해야 한다는 것을 배웠다 — 문서에 남아 있던 옛 서술을 근거로 잘못된 정정을 제안한 일이 있었다
- 도구가 빨라질수록 무엇이 사실인지 확인하는 일이 더 중요해졌다

### 1. 프로젝트의 기대효과

**사고 예방 패러다임 전환 (사후 대응 → 사전 차단)**

- 사후 반응 → 버튼 입력 직전 차단. 오작동·설비 손상·안전사고를 발생 이전에 예방

- 저가 엣지 디바이스(Pi5+Hailo)+웨어러블 글라스 → 대규모 설비 교체 없이 도입
- 기존 콘솔을 대체하지 않고 감지·차단 레이어만 더하는(＋α) 구조

**엣지 온디바이스의 보안·독립성**

- 클라우드 전송 없이 온디바이스 추론 완결 → 설비 레시피·작업 지시 등 사내 정보가 외부로 나가지 않음
- 외부망이 제한된 반도체 FAB 폐쇄망에 그대로 적용 가능

**작업자 중심 안전 문화 강화**

- 관리자 알림이 아닌 작업자 본인에게 1인칭 즉시 피드백 → 실수를 스스로 인지·교정
- 주의력에 의존하던 순서 검증을 AI가 보조 → 피로·반복에 따른 인지 오류 보완

### 2. 프로젝트의 활용분야

**반도체 공정 설비 정비(PM) 현장**

- 유독가스·고온·잔압을 다루는 설비 정비 작업의 순서 위반 감지·차단
- 클린룸 형광등 계열 조명 환경에서 비전 인식 신뢰성 확보

**순서가 안전과 직결되는 여타 제조 공정**

- 반도체 증착·식각, 화학·정유 플랜트 밸브·차단 시퀀스 등 선행 단계가 안전 임계인 모든 순차 작업

**위험물·화학물질 취급 작업**

- 화학물질 투입 순서·밸브 개폐 순서 등 역순·누락이 곧 사고로 이어지는 작업

**신입·비숙련 작업자 교육·훈련**

- 정해진 순서를 벗어나면 즉시 피드백 → 작업 표준 학습 보조 도구
- (확장 기능) 오류 유형을 '망설임 vs 절차 위반'으로 분류·기록하면 맞춤형 재교육 자료로 활용 가능

**웨어러블 기반 산업 안전 플랫폼**

- 스마트 글라스 1인칭 비전 + 엣지 AI 구조는 다양한 현장 안전 감시(보호구 착용 확인, 위험구역 접근 경고 등)로 발전 가능한 확장형 플랫폼

## 1. 화면 기하

| 항목 | 값 | 근거 |
|---|---|---|
| 디스플레이 | **1920×1080** (16:9) | `xrandr` 실측 (HDMI-1) |
| 카메라 | 640×480 (4:3) | ESP32-S3 OV3660 |
| 영상 표시 | **1440×1080**, 화면 가운데 | 높이를 꽉 채운 4:3 |
| 레터박스 | **좌우 각 240px, 검정** | 사이드바 UI는 채택 안 함(§10) |

**모든 UI는 영상 위 오버레이**다. 레터박스에는 아무것도 두지 않는다.

### 오버레이 배치 (화면 폭·높이 기준 %)

| 요소 | 위치 | 크기 |
|---|---|---|
| 상태 + 공정 단계 패널 | `left 14%` · `top 5%` | `width 24%` (높이는 내용에 따라, 약 42%까지) |
| 대기 게이지 | `left 41%` · `top 5%` | `width 17%` |
| 메뉴 버튼 ☰ | `right 14%` · `top 5%` | 아이콘 |
| 메뉴 패널(열림) | `right 14%` · `top 5%` ~ `bottom 5%` | `width 13%` |
| 알림 버튼 🔔 | `left 14%` · `bottom 5%` | 아이콘 + 뱃지 |
| 알림 패널(열림) | `left 14%` · `top 48%` ~ `bottom 5%` | `width 27%` |
| 경고 배너 | 가로 중앙 · `bottom 13%` | `width 44%` |
| 차단 패널 | 가로 중앙 · `top 47%` | `width 46%` |
| 작업 시작 버튼 | 화면 정중앙 | 내용에 맞춤 |

- 공정 단계 패널 `14%~38%`, 게이지 `41%~58%` — **3%p 간격으로 이어져 한 덩어리로 읽힌다.**
- 알림 패널 상단이 `48%`인 이유 = **공정 단계 패널(~42%)을 가리지 않기 위해.**
- 메뉴(우상단)와 알림(좌하단)은 **대각선 대칭**.

## 2. 폰트 — Pretendard 단일

### 2.1 🔴 먼저: 지금 코드가 잘못돼 있다

`safety_console.py`의 **7곳**이 `QFont("Consolas", ...)`인데 **이 파이에 Consolas가 없다.** Qt가 조용히 `WenQuanYi Zen Hei Mono`(중국어 폰트)로 대체하고 있었다. **지금 화면의 글꼴은 아무도 의도한 적이 없는 것**이다. Consolas는 윈도우 기본 폰트라 개발 환경 값이 남은 것으로 보인다.

### 2.2 확정

| 항목 | 값 |
|---|---|
| 폰트 | **Pretendard 1.3.9** (단일) |
| 굵기 | 400 본문 / 600 강조 / 700 제목 / 800 현재 단계 |
| 숫자 | **`tnum`(고정폭 숫자) 켠다** |
| 라이선스 | SIL OFL 1.1 — 상업 이용·수정 자유 |
| 설치 위치 | `~/.local/share/fonts/Pretendard/` (사용자 폴더, `sudo` 불필요) |
| 설치 파일 | `Pretendard-{Regular,SemiBold,Bold,ExtraBold}.otf` 4벌, 각 약 1.6MB |

**선정 이유** — ①라틴·숫자가 또렷하다(`PROCESS RUN`·`18/45s`·`14:22:07`이 화면에 상시 노출) ②한글과 라틴의 높이·굵기가 맞아 섞인 줄이 안정적 ③굵기가 4단계라 600/700/800 구분이 정확(나눔스퀘어는 2단계뿐).

### 2.3 고정폭 숫자 — Qt에서는 명시적으로 켜야 한다

기본값이 아니다. 켜지 않으면 게이지가 `18/45s → 19/45s`로 바뀔 때 **폭이 흔들린다.**

```python
f = QFont("Pretendard")
f.setFeature(QFont.Tag("tnum"), 1)
```

| | 숫자 0~9 폭 |
|---|---|
| 기본 | `11, 8, 11, 12, 12, 11, 12, 10, 12, 12` |
| `tnum` 켬 | `12` × 10 — **균일** (`18/45s`·`19/45s` 둘 다 62px) |

> ⚠️ `QFont.setFeature`는 **Qt 6.7 이상**이다. 이 파이는 6.11.0이라 동작을 확인했다. **데스크톱·sop-pi-2에서는 Qt 버전을 먼저 확인할 것.**
> 이 기능 덕분에 **별도 숫자 폰트(D2Coding 등)가 필요 없어졌다.**

### 2.4 다른 환경에 설치하는 법

```bash
FD=~/.local/share/fonts/Pretendard && mkdir -p "$FD"
B=https://cdn.jsdelivr.net/npm/pretendard@1.3.9/dist/public/static
for w in Regular SemiBold Bold ExtraBold; do
  curl -sfL -o "$FD/Pretendard-$w.otf" "$B/Pretendard-$w.otf"
done
fc-cache -f "$FD"
```

### 2.5 🔴 재발 방지 — 폰트를 config로 모으고 실제 적용을 로그에 남긴다

Consolas가 조용히 바뀐 일이 데스크톱·sop-pi-2에서 재발할 수 있다. 구현 시:
1. 폰트 이름을 `config.py` **한 곳**에 둔다(현재는 7곳에 흩어져 있다)
2. 기동 시 `QFontInfo`로 **실제 적용된 폰트를 로그에 남긴다** — 요청과 다르면 즉시 보인다

### 3.2 화이트 (테마 반전)

> 🔴 **단순 반전이 아니다.** 색을 그대로 뒤집으면 **경고·위험이 안 보이게 된다** — 밝은 판 위의 밝은 주황·빨강은 대비가 사라진다. 안전 표시라 여기가 가장 중요하다.

| 토큰 | 다크 | **화이트** |
|---|---|---|
| 오버레이 배경 | `rgba(0,0,0,0.60)` | **`rgba(255,255,255,0.30)`** |
| 오버레이 테두리 | `rgba(255,255,255,0.22)` | `rgba(0,0,0,0.26)` |
| 글자 그림자(3겹) | 어두운 후광 | **밝은 후광** — `0 1px 2px #fff`, `0 0 5px rgba(255,255,255,.98)`, `0 0 12px rgba(255,255,255,.9)` |
| 본문 글자 | `#e6e8ea` | `#0b0f12` |
| 부가 라벨 | `#c3c9cf` | `#39424a` |
| 완료 | `#7dffa8` | `#009a42` |
| 현재 단계 | `#ffd75c` | `#cc6f00` |
| 예정 단계 | `#c3c9cf` | `#49525a` |
| **경고** | `#ff8f2e` | 🔴 **`#b34700`** (더 어둡게) |
| **위험** | `#ff5252` | 🔴 **`#a80000`** (더 어둡게) |
| 작업/정보 | `#5aa8ff` | `#0b5cad` |
| 게이지 빈 부분 | `rgba(0,0,0,0.65)` + 흰 테두리 | `rgba(255,255,255,0.80)` + `inset 0 0 0 1px rgba(0,0,0,.3)` |
| 게이지 채움 | `#e8a000 → #ffd75c` | `#cc6f00 → #ffb300` |

#### 화이트가 30%인 이유 — 채도와 후광으로 벌었다

처음엔 72%로 잡았다(흰 판이 검은 판보다 배경이 더 비쳐 보여서). 그런데 **글자 쪽을 두 번 손보자 30%까지 낮출 수 있었다**:

1. **색 글자의 채도 상향** — 완료 `#0a7a3d→#009a42`, 현재 `#8a5200→#cc6f00`
2. 🔴 **흰 후광 3겹** — **채도만으로는 안 된다.** 본문("스패너를 가져오세요")은 **검정에 가까워 채도를 올릴 수가 없다.** 어두운 배경 위에서 그 글자를 살리는 것은 **후광뿐**이다. 다크의 검은 후광 3겹을 **그대로 뒤집은 것**이며, 두 테마가 대칭이 된다

⚠️ **채도를 더 올리면 명도도 같이 올라가** 밝은 배경 위에서 오히려 흐려진다. 지금이 양쪽을 다 만족하는 근처다.

#### 판정은 「어두운 배경 위」를 기준으로 한다

같은 화면에 두 조건이 공존한다 — 공정 단계 패널은 **밝은 책상 위**(14~38%), 게이지·공구 패널은 **어두운 콘솔 위**(41~65%). 밝은 쪽만 보고 정하면 어두운 쪽에서 무너지므로 **어두운 쪽이 기준**이다.

#### 전환 규칙

- 기본값 **다크**. 설정 메뉴에서 전환
- **작업 중에도 바꿀 수 있다** — 보이는 것만 바뀌고 판정에 영향이 없다(공구 선택과 다름)
- 저장하지 않는다 — 다시 켜면 다크

> ⚠️ 목업 배경은 **모조 콘솔·클린룸 형광등** 한 조건이다. 실콘솔(포맥스판)·다른 조명에서 적정값이 바뀔 수 있다. 최종 확인은 실기동.

### 3.3 유리 느낌 — (a)만 적용

**(a) 단순 반투명만 구현한다.** **(b) 배경 블러는 보류** — Qt에 `backdrop-filter`에 해당하는 기능이 없어 매 프레임 `cv2.GaussianBlur`가 필요하다. 예비 측정에서 **800×400 영역 4.92ms**(25fps 기준 +12.3%p)로 무시할 수 없다. (a)를 만들어 보고 판단한다.

## 4. 화면 상태

### 4.1 IDLE — 작업 시작 전
- 상태 `STANDBY`, 모든 단계 회색 `○`
- **작업 시작 버튼을 화면 정중앙에 크게.** 누르면 사라지고 다시 나오지 않는다
- 게이지 자리는 비어 있음 (서브 작업 없음)
- 좌하단 알림 위로 **「점검 완료」 토스트**

### 4.2 점검 중 — 작업 시작 직후
- 중앙에 점검 패널 + 진행 막대. 통과하면 자동으로 닫힘
- 🔴 **실패하면 작업을 시작하지 않는다.** 실패 항목을 빨갛게 남기고 「다시 점검」을 띄운다
- ⚠️ **「1차」·「2차」를 화면에 쓰지 않는다** — `점검 완료` / `점검 중`으로만. 차수는 내부 구분이다
- ⚠️ **「레시피 적재」는 점검 항목이 아니다** — 기동 시 이미 읽고, 실패해도 기본 순서로 돈다

#### 점검 항목 (확정)

두 점검은 **묻는 것이 다르다** — 1차는 *"부품이 다 있나"*, 2차는 *"지금 실제로 되나"*.

| | 1차 (기동, 백그라운드) | 2차 (작업 시작 시) |
|---|---|---|
| 1 | 카메라 연결 (ESP32 TCP) | 영상 수신 — 최근 프레임이 실제로 들어오나 |
| 2 | 검출 모델 로드 (`console_v2.hef`) | 🔴 **버튼 검출 — B1~B4 4개** |
| 3 | 손 검출 모델 로드 | 손 검출 **추론 동작** |
| 4 | 인터락 연결 (Arduino 시리얼) | 인터락 **ACK 응답** |
| 5 | GPIO 입력 준비 | — |

- 🔴 **버튼 검출이 2차의 핵심이다.** 카메라가 연결돼 있어도 **콘솔이 화면 밖이면 아무것도 감지하지 못한다.** §10.24~§10.29가 밝힌 대로 구도가 감지 성능을 지배하는데, 지금은 그것을 **작업 시작 전에 확인할 방법이 없다.** 2차 점검은 *"장비가 켜졌나"* 가 아니라 **"지금 이 자세로 감지가 되나"** 를 묻는다.
- 🔴 **EMO는 점검에서 뺀다** — 실콘솔에서 **카메라 화각 밖**이라 비전에 잡히지 않는다(2026-08-03 사용자 확인). 안전에는 영향이 없다: EMO 누름은 **GPIO 물리 입력**으로 들어오지 비전으로 판정하지 않는다.
- **손 검출은 「추론이 돌기만 하면 통과」**(느슨). 손을 보여 달라고 요구하지 않고, 안내 문구도 두지 않는다.
  - 이유: `detect()`는 **모델 없음·손 없음·추론 실패를 전부 `None`으로** 돌려주므로 밖에서 구분이 안 된다. 프레임 하나를 넣어 **예외 없이 끝나고 시간이 정상 범위인지**까지가 손 없이 확인할 수 있는 최선이다.
  - 이것으로 **모델 파일 없음·Hailo 미탑재·추론 중 예외·장치 충돌**이 걸러진다. 실제로 위험이 있다: 손 모델·소스가 **repo 밖(`~/hoi_probe/`)** 이라 **클론·sop-pi-2에서 자동 비활성**된다.
  - 손 검출이 안 되면 **첫 단계에서 바로 보인다**(랜드마크가 안 그려진다). 반면 버튼 검출이 안 되면 **끝까지 아무 일도 안 일어나** 모른다 — 그래서 엄격도를 다르게 둔다.

### 4.3 PROCESS RUN — 정상 진행
- 좌측 패널에 상태·단계, 상단 중앙에 서브 작업 게이지. 시야 가운데는 비어 있다

#### 서브 작업 화면 (신설)

| 상황 | 화면 |
|---|---|
| **대기 중** | 게이지 패널(`width 17%`)에 진행률. 진행 버튼 없음 |
| **대기 완료** | 🔴 **화면 정중앙에 「▶ 다음 단계 진행」 버튼** — 「작업 시작」과 같은 자리. 게이지는 「완료」 초록으로 남는다 |
| **대기 + 공구** | 게이지 패널이 **`width 17% → 24%`**, 아래로 한 칸 늘어나 공구 지시를 담는다. 확인되면 `○ 대기` → `✓ 스패너 확인됨` |
| **잘못된 공구** | WARNING 등급 — 배너에 *「다른 공구입니다 / 가져온 것: 드라이버 — 스패너로 바꿔 주세요」* |

- 🔴 **공구 경고에는 해제 버튼을 두지 않는다.** 올바른 공구로 바꾸면 **스스로 풀린다.** 순서 위반은 *"손을 뗐다"* 를 시스템이 알 수 없어 해제 버튼이 필요하지만, 공구는 다시 보면 안다. 해제 버튼을 두면 **잘못된 공구를 든 채 넘어갈 수 있다.**
- 공구 오선택도 **BLOCK(전기 차단)까지 가지 않는다.** 잘못된 공구로 전기를 끊는 것은 과하다.
- 발광은 순서 위반과 **동일**하게 적용한다.

### 4.4 설정 (신설)

메뉴 → ⚙ 설정. **메뉴 패널 폭(13%)에는 라디오가 안 들어가므로 중앙 패널**로 띄운다.

| 항목 | 내용 | 변경 가능 시점 |
|---|---|---|
| 4단계 지정 공구 | 스패너 / 드라이버 / 렌치 | 🔴 **IDLE일 때만** — 진행 중에 바뀌면 판정이 흔들린다 |
| 화면 테마 | 다크(기본) / 화이트 | **언제나** — 판정에 영향 없음 |

🔴 **바꾼 값은 저장하지 않는다.** 이 세션에만 적용되고 다시 켜면 `recipe.json` 값으로 돌아간다. 레시피가 **정답 순서의 단일 출처**라, UI가 파일을 고치기 시작하면 정본이 흐려진다.

### 4.5 WARNING
- **영상 영역(가운데 75%)에만** 주황 테두리 발광 `9px` + `inset 0 0 60px`. **레터박스는 빛나지 않는다**
- 다른 오버레이 전부 `opacity 0.40`
- 중앙 하단 경고 배너: 제목 「순서가 다릅니다」 + 안내 2줄
  - 2번째 줄은 **아래로 내리고 `padding-left:14px` 들여쓴다**
  - 배너 안에 **「경고 해제」 버튼** — 평소엔 화면에 없다
- 알림 뱃지가 주황으로 바뀌고 수가 오른다

### 4.6 BLOCK
- 같은 규칙, 빨강 `12px` + `inset 0 0 90px`. 영상은 `brightness .55`
- **중앙을 가린다** — 이 순간엔 시야보다 멈추게 하는 것이 우선
- 「차단 해제」 버튼 포함. 🔴 **EMO 미복귀 시 거부**하는 기존 안전 장치 유지

### 4.7 메뉴 (열림)
- 세로형, 항목: **로그 · 캘리브레이션 · CCTV 전환 · 설정**
- 아래에 **추후 항목 자리 3칸**(점선)
- 🔴 **시스템 종료는 맨 아래로 분리 + 구분선** — 비가역 동작이라 다른 항목과 섞지 않는다. 확인창 유지
- 열리면 영상을 어둡게 하고 다른 오버레이를 흐린다
- ⏸ 「공정 단계」를 메뉴에 넣을지는 **보류** (좌측 패널에 상시 표시되어 중복)

### 4.8 알림 (신설)
- **좌하단 🔔 + 안 읽은 수 뱃지.** 새 알림은 그 위로 떠올랐다 몇 초 뒤 사라진다
- 누르면 위로 패널이 펼쳐진다 (`top 48%` ~ `bottom 5%`, `width 27%`)
- **메신저 방식** — 최신이 맨 아래, 열면 최신이 보이는 위치에서 시작, **과거는 위로 스크롤**
- 종류 4가지: **점검(✓ 초록)** · **이벤트-작업(▶ 파랑)** · **이벤트-경고(⚠ 주황)** · **이벤트-위험(⛔ 빨강)**
- 🔴 **프로그램을 종료하면 초기화** — 메모리에만 두고 파일로 남기지 않는다
- ⏸ **알림 기록(파일 저장)은 보류** — 통합문서 §13 확장의 「작업 로그 기록」과 성격이 같아, 지금 만들면 나중에 둘이 겹친다

> **로그와 알림은 역할이 다르다** — 로그(메뉴 안)는 **전부**를 시간순으로 담고, 알림은 **알려야 할 것만** 골라 띄운다. 둘 다 유지한다.

## 5. 시나리오 (확정, 2026-08-03)

> **작업 = PECVD 설비 정비(PM)** — 특정 작업(샤워헤드 교체 등)으로 좁히지 **않는다.** 통합문서 §6 그대로.

### 왜 좁히지 않았나 — 물리적으로 할 수 있는 것만 넣는다

**실제 장비가 없다.** 콘솔에 있는 것은 버튼 5개뿐이고, 그 옆에 공구를 놓을 수 있다.

| 동작 | 가능? |
|---|---|
| 버튼을 누른다 · 기다린다 | ✅ |
| 공구를 찾는다·집는다·옮긴다·내려놓는다 | ✅ |
| **밸브를 잠근다 · 볼트를 푼다 · 챔버를 연다** | ❌ **대상이 없다** |

→ **공구의 의미를 「사용」이 아니라 「준비」로** 잡았다: *"곧 챔버를 열고 정비할 것이므로, 대기 시간 동안 필요한 공구를 챙겨 작업 위치에 둔다."* 실제 사용 시점은 **챔버를 연 다음 = 시연 범위 밖**이라 **가정할 것이 없어진다.**

> ⏸ 검토했으나 **채택 안 함** — LOTO(가스 라인 수동 밸브 잠금). 주제 정합성은 가장 좋았으나 **잠글 밸브가 없다.**

### 흐름

| 순서 | 종류 | 내용 | 진행 조건 |
|---|---|---|---|
| 1 | 🔵 버튼 | **B1** 클린·가스차단 | 누름 |
| 2 | ⏱ 대기 | 플라즈마 클린 진행 — **30초** | 시간 경과 → **「다음 단계 진행」 누름** |
| 3 | 🔵 버튼 | **B2** 펌프/퍼지 | 누름 |
| 4 | ⏱🔧 대기+공구 | N₂ 퍼지 **30초** + **지정 공구를 콘솔 앞에 가져다 놓기** | 시간 경과 **AND** 공구 확인 → **버튼 누름** |
| 5 | 🔵 버튼 | **B3** 전극 냉각 | 누름 (빈손) |
| 6 | ⏱ 대기 | 전극 온도 하강 — **30초** | 시간 경과 → **버튼 누름** |
| 7 | 🔵 버튼 | **B4** 챔버 벤트 | 누름 (빈손) |
| — | | 챔버 개방 → 정비 작업 (시연 범위 밖) | |

- ⏸ **6번은 임시다** — 2번과 그림이 겹친다. **추후 아이디어가 생기면 내용을 바꾼다**(사용자 결정).
- **4번에서 공구를 내려놓으므로 5·7번은 빈손**이다. 공구를 쥔 손은 팜 검출이 나빠질 수 있는데(§10.21에서 맨손도 미검출 21.8%) **그 위험을 피한다.**
- 🔴 **대기가 끝나도 자동으로 넘어가지 않는다.** 화면의 **「다음 단계 진행」**을 눌러야 한다.

### 공구

- **3종을 콘솔 옆에 둔다**: 스패너 · 드라이버 · 렌치
- **화면이 하나를 지정**하고, 다른 것을 가져오면 **경고**(§4.3)
- 지정 공구는 `recipe.json`에 기본값, **설정 메뉴에서 세션 한정 변경**(§4.4)
- 🎁 **공구 감지가 없어도 시연이 성립한다** — 「다음 단계 진행」 버튼이 자연스러운 폴백이다. 사람이 눈으로 확인하고 누르면 된다. **UI를 먼저 만들고 감지를 나중에 붙일 수 있다.**

### 대기 중 다른 버튼을 누르면

**순서 위반 경고.** 근거: **"B1 누름(메인) + B1 후 대기(서브) = 하나의 B1 작업"** 이므로, 그 작업이 끝나기 전에 다른 버튼을 누르면 위반이다.

→ 이 정의 덕분에 **FSM에 새 상태를 만들지 않고** *"B1 작업이 아직 안 끝났다"* 로 다룰 수 있어, 순서 위반 판정 논리가 현 구조 그대로 유지된다.

```json
{

  "dwell_threshold_sec": 1.0,
  "emo_button": "EMO",
  "steps": [
    { "order": 1, "button": "B1", "name": "클린·가스차단",
      "sub": { "type": "wait", "sec": 30, "label": "플라즈마 클린 진행" } },

    { "order": 2, "button": "B2", "name": "펌프/퍼지",
      "sub": { "type": "wait_tool", "sec": 30, "label": "N₂ 퍼지",
```

| `type` | 「다음 단계 진행」이 켜지는 조건 |
|---|---|
| `wait` | 시간 경과 |
| `wait_tool` | 시간 경과 **AND** 지정 공구 확인 |
| 없음 | 서브 작업 없음 — 바로 다음 버튼 |

## 8. 구현 방침

- 🔴 **기존 `safety_console.py`를 수정한다** (새 파일 아님). 전면 수정이 닿는 곳은 레이아웃 계열 **약 160줄**(`_init_ui` 96 + `StepFlowWidget` 65)이고, 나머지 약 560줄(FSM·인터락·GPIO 배선, 안전 3종, 녹화·캘리브레이션)은 화면이 바뀌어도 그대로 필요하다. **화면은 전면이지만 파일은 전면이 아니다.**
- 🔴 **안전 UI 3종은 건드리지 않는다** — ①BLOCK 해제 거부(EMO 미복귀) ②인터락 폴트 경고창 ③종료 확인창. **전부 사고를 겪고 만든 방어물**이다.
- **작업 브랜치는 `feature/fsm-interlock`에서 딴다.** ⚠️ Rpi5의 `origin/main`은 `075f6db "Ver 1.1"`에 멈춰 있고 실제 트렁크가 `feature/fsm-interlock`(87커밋 앞섬)이다.
- **성능 대응은 아무것도 넣지 않고** 만든 뒤 측정한다(사용자 결정). `FastTransformation`도 지금은 적용하지 않는다.
  - 근거: 예비 측정에서 Full Screen + FPS25 최악이 **GUI 스레드 점유 24.5%** — 여유가 있다. 조건·한계는 아이디어 문서 §4.
- **녹화는 지금 정책 유지**(창 전체, 15fps). Full Screen이면 녹화본이 1920×1080이 되는데 **시연 영상 품질이 오르는 것**이다. 예비 측정에서 창 캡처가 5.25ms/프레임 = **초당 7.9%** 로 여유가 있다.
- 🔴 **폰트와 색을 `config.py` 한 곳으로 모은다.** 지금 폰트는 7곳, 색은 9곳에 `setStyleSheet` 문자열로 흩어져 있다. **테마 전환은 이 정리 없이는 불가능**하다. 부담이 아니라 원래 했어야 할 일이며, 테마 기능이 그것을 강제한다.
- **기동 시 실제 적용된 폰트를 로그에 남긴다**(§2.5).

## 8.5 🔴 2026-08-04 실기동으로 뒤집힌 것

설계 때 정한 것이 실기동에서 세 개 뒤집혔다. **문서를 실제 코드에 맞춘다.**

| 항목 | 설계 원안 | 실제 | 이유 |
|---|---|---|---|
| **글자 그림자 3겹** | 넣는다(§3) | 🔴 **넣지 않는다** | `QGraphicsDropShadowEffect` 를 패널 안 라벨마다 걸자 Qt 가 `QPainter::begin: A paint device can only be painted by one painter at a time` 를 끝없이 뱉으며 **화면이 안 그려지고 클릭도 안 먹었다**(CPU 60%). 효과 위젯 안에 효과 자식이 있으면 페인터가 충돌한다. → 대비는 **색으로만** |
| **흐림 처리 `opacity 0.40`** | 오버레이별 opacity(§3.1) | **반투명 판(scrim) 한 장** | 같은 페인터 충돌. 위젯 하나면 겹칠 일이 없고, 영상과 뒤쪽 오버레이가 함께 어두워져 목업과 같은 그림이 된다 |

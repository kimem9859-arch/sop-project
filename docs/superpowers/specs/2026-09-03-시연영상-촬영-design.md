---

## 1. 무엇이 필요한가

공모전 시연영상을 편집하려면 **같은 연기 한 번에서 여러 각도의 소재**가 동시에 나와야 한다.
따로 찍으면 연기가 매번 달라 편집에서 붙지 않는다.

사용자가 요구한 소재는 다섯이다.

| # | 영상 | 쓰임 |
|---|---|---|
| ① | GUI 전체 (1인칭 영상이 보이는 상태) | 제품이 실제로 도는 모습 |
| ② | GUI UI만 (카메라 자리 검정) | UI 동작만 보여주는 컷 |
| ③-a | 1인칭 풀스크린 · 오버레이 O | AI가 무엇을 보는지 |
| ③-b | 1인칭 풀스크린 · 오버레이 X | 작업자 시점 원본 |
| ④ | USB 웹캠 3인칭 | 작업자 전체 동작 |

시나리오는 **정상 1회 · 오답(순서 위반) 1회**. 제일 잘 나온 것을 채택하고 NG는 지우지 않고 보관한다.

🔄 **한 번 실행에 다섯이 다 나오지는 않는다**(§3.1b) — 회차가 둘로 갈린다.

| 회차 | 나오는 파일 |
|---|---|
| **영상 회차** (오버레이 켬/끔) | ① · ③-a · ③-b · ④ |
| **UI만 회차** | ② · ③-a · ③-b · ④ |

### 이미 있는 것 / 없는 것

- **있음** — 녹화 기능 1개(`safety_console.py` §녹화). 한 번에 한 파일, 메뉴에서 수동 시작.
  `run_scenario.sh` 가 `ffmpeg` 로 화면·웹캠을 동시에 찍는 길을 이미 검증해 뒀다.
- **없음** — 동시 다중 녹화 · UI만/검정 영상 · 오버레이 유무 두 벌 · 한국어 파일명 · 채택/NG 보관.

---

## 2. 요구사항 (사용자 제시, 2026-09-03)

1. **한 번 실행 = 5개 파일이 동시에** 저장된다.
2. **촬영 시작은 「GUI가 실행된 이후」** — 로딩 화면·바탕화면이 앞에 찍히면 안 된다.
3. **작업표시줄·제목표시줄이 찍히면 안 된다.**
4. **오버레이 = 객체 박스 + 손 랜드마크 둘 다**를 뜻한다.
5. **④ USB 3인칭은 검출을 일절 하지 않는다** — 순수 촬영본.
6. **③만 오버레이 유/무 두 벌.** GUI(①②)는 나누지 않고 **회차를 두 번**으로 얻는다.
7. **파일명은 한국어 + 날짜·시간.**
8. **NG는 삭제하지 않고 보관.**
9. 🔴 **버벅임 대책은 이번에 넣지 않는다** — 먼저 그대로 만들어 실제로 얼마나 버벅이는지 본다.

## 3. 왜 이렇게 나눴나

### 3.1 인코딩은 전부 ffmpeg · 촬영 중에는 최소한만 (🔄 실측으로 두 번 바뀜)

> 🔴 **초안은 「GUI 밖 2개 · GUI 안 3개」였다. 실측이 두 번 뒤집었다.**
> 경위·수치 = `docs/작업로그.md` 2026-09-03 블록.

| 시도 | 구성 | 촬영 중 GUI FPS |
|---|---|---|
| 1차 | GUI 안에서 `cv2.VideoWriter` 3개 | 13.1 → **0.5~1.9** |
| 2차 | 인코딩 전부 ffmpeg, 1080p 5벌 | 여전히 **0.6~0.8** |
| **3차(채택)** | 촬영 중엔 원본만·규격은 촬영 뒤·기본 720p | 15.6 → **9.7** |

2차에서 `top` 을 보니 **ffmpeg 둘이서만 CPU 250%/400%** 를 먹고 있었다(4코어).
→ 병목은 「누가 인코딩하느냐」가 아니라 **1080p 인코딩 개수** 자체였다.
Pi 5 에는 하드웨어 인코더가 없어 전부 소프트웨어다.

**채택한 구성 — 촬영 중 4개 프로세스**

| 영상 | 찍는 주체 | 촬영 중 |
|---|---|---|
| ①GUI전체 / ②GUI화면만 | `ffmpeg` x11grab (창 영역만) | 회차에 따라 하나 |
| ④USB 3인칭 | `ffmpeg` v4l2 직접 | 1920×1080 **15fps**(30 → 절반) |
| ③-a/③-b 1인칭 | GUI → 파이프 → `ffmpeg` | **원본 480×640 그대로** |

**촬영 뒤(`demo_postprocess.py`)** — ③ 을 규격 캔버스에 레터박스로 얹는다.
사람이 연기하는 동안 CPU 를 아끼는 것이 전부이고, **최종 파일은 같다.**

④를 ffmpeg 가 잡으므로 GUI 의 `UsbCameraThread` 는 띄우지 않는다(`SOP_USB_CAMERA=0`).
장치가 하나뿐이라 둘이 동시에 열 수 없고, 이러면 요구사항 5(검출 없음)도 자동으로 지켜진다.
🔴 OpenCV 로 열면 MJPG 지정이 무시돼 1080p 5fps 로 떨어진다(2026-07-22 실측).

### 3.1b 🔴 ②GUI화면만은 ①에서 파생할 수 없다 (실측으로 발견)

초안은 「같은 화면 캡처를 둘로 갈라 한쪽만 카메라 영역을 검게 칠한다」였다. **틀렸다.**
이 UI 는 **모든 UI 가 영상 위에 떠 있는 글라스 구조**라(영상이 배경, UI 는 오버레이),
녹화본에서 영상 영역을 덧칠하면 **UI 까지 함께 지워진다.**
실측에서 거의 새까만 영상(0.0MB)이 나와 확인됐다.

→ **회차를 나눈다.** `SOP_DEMO_HIDE_VIDEO=1` 이면 GUI 가 카메라 자리를 **직접 검정으로
그리고**, 그 화면을 그대로 담은 것이 곧 ②다. 🔴 **표시만 바뀐다** — 검출·판정·
1인칭 녹화는 그대로 돈다. 오버레이 유/무를 회차로 나눈 것과 같은 방식이다.

### 3.2 오버레이를 「표시」와 분리한다

지금은 **화면에 켤 때만 그린다**(`camera_thread._process_frame`).
그러면 오버레이 OFF 회차에서 ③-a 가 빈 영상이 된다.

→ **그리기는 항상 하고, 화면에는 회차 설정대로 보여준다** 로 뒤집는다.
깨끗한 사본을 뜨는 자리는 이미 있다 — 공구 추론용 `tool_frame = frame.copy()`.
같은 자리에서 한 벌 더 뜬다.

### 3.3 영상 길이를 실제 시간과 맞춘다

ESP32 프레임 간격은 일정하지 않다(§10.34 조건 참조).
오는 대로 고정 fps 파일에 쓰면 **영상 길이가 실제와 어긋난다.**

→ ③ 은 **15fps 전용 스레드가 「지금 최신 프레임」을 파이프에 민다.** 새 프레임이 없으면
직전 것을 한 번 더 민다. 1분 촬영이 정확히 1분 영상이 된다. ①②④ 는 ffmpeg 가 같은 일을 이미 한다.
🔴 **GUI 스레드가 아니라 전용 스레드다** — GUI 스레드에서 하면 §3.1 의 1차 실패로 돌아간다.

### 3.4 시작·종료를 GUI 가 쥔다

요구사항 2 때문이다. 런처가 ffmpeg 를 먼저 띄우면 GUI 로딩 화면이 앞에 찍힌다.

```
런처 → main.py(촬영 모드) 실행
          ↓
GUI: 창 표시 → 첫 카메라 프레임 도착 → 🔴 녹화 동시 시작 (ffmpeg 전부 GUI 가 띄운다)
          ↓
GUI 종료 → 동시 정지 (🔴 파이프를 먼저 닫아 ffmpeg 가 스스로 마무리하게 한다)
          ↓
런처: 촬영 뒤 마무리(demo_postprocess) → 채택/NG 질문 → 폴더 이동
```

**시작 기준 = 첫 카메라 프레임 도착.** 창만 떴을 때 시작하면 1인칭 영상이 검은 화면으로 시작한다.
⚠️ ESP32 가 안 붙으면 영영 시작 못 하므로 **10초 안에 프레임이 없으면 그냥 시작**한다.
🔴 **한 번 끝난 촬영은 다시 켜지지 않는다**(`_demo_done`) — 종료 중에 들어온 프레임이
   촬영을 재시작시킨 일이 실제로 있었다.
🔴 **촬영 모드에서 SIGINT/SIGTERM 은 창 닫기로 바꾼다** — 없으면 런처에서 Ctrl+C 를
   누르거나 프로세스가 죽었을 때 파일이 깨진다(`moov atom not found`, 실측).

### 3.5 작업표시줄·제목표시줄을 빼는 법

- 지금 `SOP_FULLSCREEN=1` 은 진짜 전체화면이 아니라 **최대화**다(`main.py`).
  일부러 그렇다 — 진짜 전체화면은 제목표시줄이 없어져 창을 닫을 수 없고,
  녹화 종료가 GUI 종료에 묶여 있어 위험하다.
- → 화면 전체가 아니라 **창의 내용 영역만 잘라서** 찍는다. GUI 가 자기 좌표·크기를 넘긴다.
- 촬영 모드에서는 창을 **`DEMO_CAPTURE_SIZE`(기본 1280×720)** 로 띄운다.
  16:9 라 편집 규격 그대로이고, 잘라낼 좌표가 딱 떨어진다.
  🔴 **해상도는 부하와 맞바꾸는 값이다** — 1920×1080 이면 촬영 중 FPS 가 9.7 → 5.9 로 떨어진다.
  `SOP_DEMO_SIZE=1920x1080` 으로 올릴 수 있다.
- 🔴 **창을 「항상 위」로 고정한다** — 겹친 창이 있으면 **그 창이 그대로 찍힌다.**
  검증 중 실제로 터미널이 찍혔고, `raise_()` 만으로는 부족했다.
- ⚠️ **「항상 위」를 켜면 창 관리자가 `move()` 를 무시한다** — 창이 엉뚱한 자리로 가
  x11grab 이 `outside the screen size` 로 즉시 죽었다. **`move` 는 `show` 뒤에** 두고,
  캡처 영역은 `demo_ffmpeg` 가 화면 안으로 물린다(이중 방어).

### 3.6 실행 진입점 — 기존 GUI 를 그대로 쓴다

시연영상에 찍혀야 하는 것은 **실제 제품 화면**이다. 촬영용 GUI 를 따로 만들면 그것은 실제와 다른 화면이다.
새로 만드는 것은 **얇은 셸 런처와 바탕화면 바로가기 하나뿐**이고, GUI 는 촬영 모드일 때만 녹화가 켜진다.
평소 실행(`SOP 가디언 Demo` 바로가기)은 **지금과 완전히 동일**하다.

## 6. 관문

- 🔒 **중단 규칙** — 5개 파일 중 하나라도 안 생기거나, 영상 길이가 실제 시간과 **10% 넘게** 어긋나면 촬영을 시작하지 않는다.
- ⭐ **`run_demo.sh` 실기동 확인 필수** — `@pyqtSlot` 시그니처 불일치처럼 **import 검사로 못 잡는 런타임 오류**가 있다(실제로 GUI 가 기동 즉시 죽은 적 있음).
- ⭐ **평소 실행 회귀 확인** — 촬영 모드가 아닐 때 GUI 가 지금과 동일하게 뜨고 녹화가 켜지지 않는지.
- ⭐ **부하 실측** — 촬영 중 CPU·프레임률·1인칭 프레임 수를 기록한다. **대책은 이 수치를 본 뒤에 정한다**(요구사항 9).
- 🔴 **대조군 없이 원인을 말하지 않는다.** 2026-09-03 에 「촬영이 GUI 를 멈췄다」고 단정했다가,
  촬영을 안 켠 대조군도 FPS 0.8 이 나와 뒤집혔다 — 진짜 원인은 **파이의 Wi-Fi 로밍**이었다
  (ESP32 는 핫스팟에, 파이는 다른 AP 에 붙어 있었다). 촬영 부하는 그와 **별개로** 존재한다.

## 7. 곁가지로 함께 고친 것 — 박스 중복

촬영 중 **한 프레임에 같은 버튼 박스가 둘 그려지는** 현상을 사용자가 지적했고, 코드에서 원인이 확인됐다.

`camera_thread._update_tracks` 는 ①짝을 못 찾은 옛 트랙을 최대 `YOLO_MAX_MISS` 프레임 더 살려두고
②짝을 못 찾은 새 검출을 **같은 클래스가 이미 있는지 보지 않고** 새 트랙으로 추가한다.
박스가 크게 튀면 둘이 동시에 일어나 중복이 된다.

→ 실물 콘솔에 B1~B4·EMO 는 각각 하나뿐이므로 **클래스당 트랙 1개**로 강제한다(`_one_per_class`).
남길 하나는 **이번 프레임에 검출된 것(miss == 0) 우선**, 동률이면 점수 우선.
점수만 보면 갱신이 멈춘 옛 트랙이 이겨 박스가 뒤처진다.

판정(FSM)에는 영향이 없고 표시와 ROI 판정이 오히려 안정된다.

# 음성 비서(가디언) 설계 — 소형 LLM 기반 작업 에이전트

> **전제** — "소형 LLM을 사용하여 작업 에이전트 비서(안내·경고)를 만든다."
> 작성 2026-08-13. 설계 = Claude Opus 5 / 결정 = 사용자.
> 🔴 **이 문서는 설계 근거다.** 확정 측정값은 여기 두지 않는다 — 통합문서 §10 `[CURRENT]` 표가 정본이고, 이 문서는 포인터만 둔다.

---

## 1. 무엇을 만드는가

작업자가 착용한 스마트 글라스에서 **말로 안내·경고하고, 물으면 답하는 비서**를 만든다. 이름(호출어) = **"가디언"**.

기존 시스템은 **화면(GUI 오버레이)과 물리 인터록**으로만 작업자에게 말을 건다. 그런데 정비 작업자는 **손이 장비에 가 있고 시선이 콘솔에 고정돼 있지 않다.** 소리는 시선을 뺏지 않고 도달하는 유일한 채널이다.

### 1.1 범위

| 담는 것 | 안 담는 것 |
|---|---|
| 순서위반·위험 **즉시 경고** (음성) | 콘솔 GUI 변경 |
| 공구·단계 **안내** (LLM 생성 문장) | 인터록 로직 변경 |
| 작업 종료 후 **결과 요약** | SOP 문서 검색(RAG) — §2.2에서 거부 |
| 호출어 기반 **질의응답** | 비서에 의한 **판정·차단** — §3.1에서 금지 |
| 글라스 스피커·앰프 **하드웨어 추가** | 글라스 외장 재제작 (여유 공간 있음 — 사용자 확인) |

### 1.2 이 설계가 지켜야 하는 프로젝트 제약

- **프레이밍 B** (통합문서 §1·§3) — 핵심은 비전 AI 순서위반 감지·차단이고 안전은 그 효과다. 음성 비서는 **감지·차단을 돕는 보조 채널**이지 그 자체가 목적이 아니다.
- **NFR-1 = 15fps** (통합문서 §10.6 주석) — 음성 기능이 이 선을 깨면 기능을 포기한다. §7의 관문 G1.
- **사전 차단** — "누르기 직전에 막는다"가 핵심 주장이다. LLM 지연을 경고 경로에 넣지 않는다(§3.1).

## 2. 확정된 결정과 그 근거

> 이 절은 **왜 그렇게 정했는가**의 기록이다. 나중에 "왜 이렇게 했지?"를 되묻지 않도록, **거부한 대안과 거부 사유**를 함께 남긴다.

### 2.1 비서는 양방향이다 — 물으면 답한다

**결정**: 비서가 먼저 말하기도 하고, 작업자가 물으면 답하기도 한다.

**근거**: 글라스의 XIAO ESP32-S3 Sense에 **PDM 마이크가 이미 달려 있다**(GPIO41/42). 카메라 핀(GPIO10~18, B2B 커넥터)과 겹치지 않아 **부품을 하나도 더 사지 않고** 음성 입력을 얻는다.

**거부한 대안** — 일방향(비서가 말만 함): 구현이 단순하나, 장갑 낀 손으로 조작할 수 없는 상황에서 작업자가 정보를 얻을 길이 없다.

### 2.2 비서가 아는 것은 "지금 이 작업의 상황"뿐이다

**결정**: `recipe.json`과 FSM이 이미 가진 사실(현재 단계, 다음 버튼, 검출된 공구, 위반 이력, 경과 시간)만 답한다. 범위 밖은 **"제가 알 수 없습니다"** 로 닫는다.

**거부한 대안** — SOP 문서 전체 검색(RAG):
- 문서 준비·색인·검색기 구축이 통째로 추가된다(작업량 배증)
- **틀린 답을 확신 있게 말할 위험**이 커진다. 정비 절차에서 잘못된 답은 화면 오탐보다 위험하다
- 시연에서 보여줄 가치 대비 비용이 맞지 않는다

### 2.3 경고는 LLM을 거치지 않는다 — "즉시 경고 후 비서가 설명"

**결정**: 두 단계로 말한다.

1. **즉시(0.3초 이내)**: 미리 만들어 둔 경고 음성 — *"멈추세요."*
2. **뒤이어(2~3초)**: LLM이 만든 설명 — *"B3를 먼저 눌러야 하는데 B2로 손이 가셨어요."*

**근거**: Gemma 3 4B는 Pi5 8GB에서 **초당 8~11토큰**이다. 짧은 문장 하나에도 최소 2초가 걸린다. 경고를 LLM에 태우면 **버튼이 눌린 뒤에 경고가 나온다** — 프로젝트의 핵심 주장(사전 차단)과 정면 충돌한다.

**거부한 대안**
- *경고도 전부 LLM 생성*: 인격은 일관되나 위 이유로 기각
- *경고는 비프음만*: 구현은 가장 쉬우나 "무엇이 잘못됐는지"를 못 전달해 음성 채널의 값어치가 줄어든다

**중요**: 경고 음성도 **Piper TTS로 미리 합성**해 비서와 **같은 목소리**로 만든다. 듣는 사람에게는 하나의 존재로 들리고, 급할 때만 기다리지 않는다.

### 2.4 호출어는 Pi에서 검출한다 — 글라스가 아니라

**결정**: 글라스는 마이크 소리를 상시 전송하고, **sop-pi-2가 openWakeWord로 "가디언"을 검출**한다.

**근거**: ESP32에서 한국어 커스텀 호출어는 사실상 불가능하다.
- Espressif ESP-SR의 커스텀 호출어 학습은 **500명 이상(아동 100명 포함) × 각 15회 발화** 코퍼스를 요구한다
- **한국어는 아직 지원 예정 상태**다 (TTS Pipeline V3 지원 언어: 중·영·일·불)
- 반면 openWakeWord는 **웹 도구로 20분이면 커스텀 호출어를 학습**하고, Pi4에서 80ms 조각을 5ms 안에 처리할 만큼 가볍다

**통신량 검토**: 음성 16kHz·16bit·모노 = **32KB/s**. 영상(640×480 JPEG q15 · 24fps ≈ 400~600KB/s)의 **약 6%**다. §10.34 시점 WiFi 대역폭 사용률이 1.2%였으므로 대역폭은 제약이 아니다.

⚠️ **선정 과정에서 정정된 사항** — 초기 검토에서 "글라스에서 호출어를 검출해 음성을 밖으로 내보내지 않는다"고 적었으나, 위 근거로 **성립하지 않는다.** 음성은 상시 전송된다.

### 2.5 LLM·STT·TTS는 sop-pi-2에서 돈다

**결정**: Pi#1은 영상·FSM·인터록만, **sop-pi-2가 호출어 검출·STT·LLM·TTS를 전담**한다.

**근거**: Gemma 4B는 Pi5의 CPU 4코어를 전부 쓴다. 그런데 Pi#1은 이미 **MediaPipe 손 추적을 CPU로** 돌리고 있다(현행 E2E 23.96fps, §10.34 — 손 없는 정지 장면·단일 조건). 한 대에서 둘 다 돌리면 **영상 추적이 느려져 사전 차단이 망가진다.**

sop-pi-2는 Pi#1의 복제본이라 환경 구성이 이미 같다.

**거부한 대안**
- *Pi#1 한 대 + 코어 제한*: 구성은 단순하나 FPS 저하를 실측해야 하고, 저하되면 되돌릴 곳이 없다
- *Pi#1 한 대 + 더 작은 모델(1B)*: 부담은 줄지만 문장 품질이 떨어져 "비서 느낌"이 약해진다

**대가**: 시연 시 기계가 두 대 필요하다.

### 2.6 sop-pi-2가 만든 음성은 Pi#1을 거치지 않고 글라스로 직접 간다

**근거**: Pi#1이 중계하면 그만큼 Pi#1의 네트워크·CPU를 쓴다. 영상 처리 성능을 지키는 것이 이 설계의 최우선이므로, **Pi#1이 하는 일은 "사건을 알리는 것"으로만 제한**한다.

## 3. 안전 원칙 — 비서가 넘으면 안 되는 선

### 3.1 🔴 LLM은 판정하지 않는다

**판정(무엇이 위반인가, 다음이 무엇인가)은 전적으로 FSM과 YOLO가 한다.** LLM은 **이미 확정된 사실을 사람 말로 바꾸는 일**만 한다.

이유는 책임 소재다. LLM이 "눌러도 됩니다"라고 말할 수 있으면, 그 말이 틀렸을 때 **시스템 전체의 판정 신뢰도가 무너진다.** 물리 인터록은 그대로 동작하므로 안전 자체는 유지되지만, **비서의 말과 시스템의 동작이 어긋나는 것**이 사용자 신뢰를 가장 크게 해친다.

구현상 이 원칙은 세 가지로 나타난다.

1. LLM에게는 **판정 결과가 이미 담긴 사실 묶음**만 준다. 판단을 요구하는 질문을 던지지 않는다
2. LLM 출력은 **설명·안내 문장으로만** 쓰고, **지시(멈춰라/눌러라)는 고정 문구가 담당**한다
3. 출력 검증기(§3.3)가 사실에 없는 내용을 걸러낸다

### 3.2 입력 = 구조화된 사실 묶음

LLM에게 자유 텍스트를 주지 않고, **FSM이 만든 사실만** 넘긴다.

```json
{
  "현재단계": 4,
  "전체단계": 8,
  "단계이름": "챔버 압력 확인",
  "기대버튼": "B3",
  "발생사건": "순서위반",
  "실제손위치": "B2",
  "검출공구": null,
  "경과초": 312,
  "이번작업_위반횟수": 1
}
```

프롬프트는 **"주어진 사실만 사용할 것. 사실에 없는 것은 말하지 말 것. 모르면 모른다고 답할 것."** 을 명시한다.

### 3.3 출력 검증기 — 환각을 실제로 막는 장치

프롬프트만으로는 부족하다. **LLM 출력을 검사한 뒤 통과한 것만 소리로 낸다.**

| 검사 | 걸리면 |
|---|---|
| 사실 묶음에 없는 **버튼 ID**(B1~B4·EMO)가 등장 | 폐기 → 고정 문구로 대체 |
| 사실 묶음에 없는 **공구 이름**이 등장 | 폐기 → 고정 문구로 대체 |
| 길이 초과(2문장·60자 넘김) | 폐기 → 재생성 1회 → 실패 시 고정 문구 |
| 지시형 어미("누르세요"·"진행하세요") 사용 | 폐기 — 지시는 고정 문구 전담(§3.1) |

**폐기가 실패가 아니다.** 고정 문구로 내려앉으면 말이 밋밋해질 뿐, 틀린 말은 나가지 않는다.

### 3.4 말하기 규율

| 규칙 | 이유 |
|---|---|
| 우선순위: **경고 > 질의응답 > 안내 > 요약** | 급한 것이 먼저 |
| 경고가 오면 **말하던 것을 즉시 끊는다** | 안내를 끝까지 듣느라 경고를 놓치면 안 된다 |
| 같은 사건은 **10초 안에 다시 말하지 않는다** (초기값, 구현 계획에서 조정) | 같은 공구를 들었다 놨다 하면 계속 떠든다 |
| 한 번에 **1~2문장, 60자 이내** | 길면 작업자가 안 듣는다. TTS 시간도 짧아진다 |
| 조용할 때 앰프를 끈다(`SD` 핀) | 대기 잡음·전류 제거 |

## 4. 구조

```
       ┌──────────── 말한다 ──────────────────────────┐
       │                                              │
[글라스 XIAO ESP32-S3]                        [sop-pi-2 = 말하는 뇌]
   마이크 ──── 음성 32KB/s ────────────────→   호출어 검출 (openWakeWord)
   스피커 ←─── 음성 데이터 ─────────────────   STT (음성→글자)
   카메라 ──── 영상 ──┐                        Gemma 3 4B (문장 생성)
                      │                        Piper TTS (글자→음성)
                      ↓                              ↑
              [Pi#1 = 눈·판단]                       │
              YOLO(버튼·공구) + MediaPipe(손)        │
              + FSM + 인터록 ──── 사실 묶음 ─────────┘
                      │
                      └── 즉시 경고 신호 ──→ 글라스 (LLM 안 거침)
```

### 4.1 소리가 나가는 길이 둘인 이유

| | 경고 경로 | 비서 경로 |
|---|---|---|
| 무엇 | 순서위반·위험 | 공구 안내, 단계 안내, 요약, 질의응답 |
| 만드는 곳 | 미리 합성해 글라스에 저장 | sop-pi-2가 실시간 생성 |
| 보내는 것 | **신호 몇 바이트** ("3번 재생") | 음성 데이터 통째 |
| 지연 | **0.3초 이내** | 2~10초 |
| 보내는 주체 | Pi#1 | sop-pi-2 |

### 4.2 음성 전달 방식 — 스트리밍이 아니라 "받아놓고 재생"

ESP32 오디오에서 가장 흔한 실패는 **버퍼 언더런**(데이터가 늦게 도착해 재생이 굶어 딱딱거리는 현상)이다.

**우리는 이 문제를 만들지 않는다.** 라디오처럼 끝없이 흘려보낼 게 아니라 **문장 하나씩** 보내면 되기 때문이다.

- 문장 3초 = 96KB (16kHz·16bit·모노)
- XIAO ESP32-S3는 **PSRAM 8MB** 탑재 — 96KB는 문제가 되지 않는다
- **전부 받은 뒤 재생**하면 중간에 굶을 일이 없다

말이 시작되기까지 0.2초쯤 늘지만, 비서 경로는 어차피 2~10초짜리라 체감되지 않는다.

## 5. 단계 분해 — 세 덩어리로 나눠 만든다

한 계획서에 넣으면 어디서 막혔는지 알 수 없다. **각 단계는 그 자체로 시연 가능하다.**

| 단계 | 만드는 것 | 끝나면 볼 수 있는 것 | 실패 시 |
|---|---|---|---|
| **1 · 말하는 글라스** | 스피커·앰프 결선, ESP32 재생 펌웨어, Pi#1 즉시 경고 경로, 경고 음성 사전 합성 | 순서를 어기면 글라스에서 **"멈추세요"가 즉시** 들린다 | 🔴 2·3단계가 전부 무의미 → **여기가 관문** |
| **2 · 생각하는 비서** | sop-pi-2에 Gemma+Piper, Pi#1 사실 묶음 발신, 출력 검증기, 작업 요약 | 위반 후 **"B3가 먼저입니다"** 설명, 종료 후 요약 | 1단계는 그대로 쓸모 있음 |
| **3 · 듣는 비서** | 마이크 상시 전송, openWakeWord, STT, 질의응답 | **"가디언, 다음 뭐야?"** 에 답한다 | 1·2단계는 그대로 쓸모 있음 |

### 5.1 왜 1단계가 먼저인가

**오디오를 붙인 상태의 카메라 FPS가 이 기획 전체의 생사를 가른다.** 그건 1단계만 만들면 잴 수 있다.

LLM을 다 만들어놓고 *"글라스가 소리를 내면 영상이 끊긴다"* 를 발견하면 그 작업이 통째로 날아간다. 이 프로젝트는 **FPS 원인을 추측했다가 두 달을 쓴 이력**이 있다(§10.34 — 병목을 TCP 전송으로 단정했으나 실제로는 ESP32 내부 프레임 버퍼였고 펌웨어 3줄로 2.4배가 됐다). 이번엔 **측정을 앞에 놓는다.**

### 5.2 🔴 공구 안내는 `tool_v3`에 종속된다

2단계의 "무슨 공구인지 알림"은 **쓸 수 있는 공구 모델이 나와야 실체가 생긴다.**

- `tool_v1` — 시연 사용 불가(같은 렌치를 `wrench`/`spanner`/`driver`로 오간다, §10.38-(3))
- `tool_v2` — 폐기(§10.38)
- `tool_v3` — 학습 데이터 병합 완료(29,809장, §10.40-(1)), **학습은 에폭 30에서 중단**(§10.41)

**따라서 2단계는 공구 없이도 성립하도록 설계한다** — 버튼·단계 안내만으로 동작하고, 공구 이벤트는 자리만 비워둔다. 모델이 나오면 사실 묶음의 `검출공구` 항목이 채워지는 것으로 끝난다.

## 6. 부품 선정

### 6.1 앰프는 선택이 아니라 필수다

**ESP32-S3에는 DAC가 없다.** 구형 ESP32의 8비트 DAC 2채널은 **S3에서 실리콘 자체로 제거**됐다 — ESP-IDF에 드라이버가 없고 `dacWrite()`가 부를 대상이 없다.

| 방식 | 판정 |
|---|---|
| **MAX98357A** (DAC+Class D 앰프 일체) | ✅ **채택** — 칩 1개로 변환·증폭, 스피커 직결. 부품·배선 최소 |
| PCM5102A + 별도 앰프 | ❌ 기판 2장. 글라스에 과함 |
| 시그마-델타(SDM) + RC 필터 | ❌ 음질 조악, 음성 명료도 부족 |
| 압전 부저 | ❌ 말을 못 한다 |

**앰프 모듈은 핀 배열이 업계 표준**이라 스피커만 갈아 끼우면 된다. 1차 구매가 낭비되지 않는다.

**구매처** — 앰프: 파츠-파츠 DFR0954(18×18mm·PH2.0 커넥터) / 디바이스마트 SparkFun DEV-14809 / 가치창조기술. 스피커 1차: 디바이스마트 FQ-074 또는 파츠-파츠 PP-D488.

### 6.5 예상 음질 — 스마트폰 스피커폰 수준

> 나중에 *"왜 이 정도밖에 안 되지?"* 를 다시 묻지 않도록 근거를 남긴다.
> **결론: 스마트폰 스피커폰과 거의 같은 수준.** AM 라디오보다 낫고, **블루투스 이어폰(음악)은 물리적으로 불가능**하다.

**병목은 앰프가 아니라 스피커다.** MAX98357A는 동적 범위 105dB(A-가중)로 CD 수준을 넘는다. 음질을 결정하는 것은 **지름 10~16mm 진동판**이며, 이만한 크기로 밀 수 있는 공기의 양은 정해져 있다.

#### 재생 대역 (CMS-15118C-SP 데이터시트 400Hz~10kHz · f0 500Hz 기준)

| 구간 | 우리 구성 | 여기 있는 소리 |
|---|---|---|
| ~400Hz 이하 | 🔴 거의 안 나옴 | 남성 목소리의 굵은 울림, 베이스·드럼 |
| 400Hz~4kHz | ✅ 잘 나옴 | **말의 뜻이 담긴 대역** |
| 4k~8kHz | ✅ 나옴 | ㅅ·ㅊ 치찰음, 또렷함 |
| 8kHz 이상 | ⚠️ 잘림 | 악기의 반짝임, 공기감 |

전송 샘플레이트가 16kHz이므로 신호 자체도 8kHz까지만 담긴다(나이퀴스트).

**저음이 통째로 없다.** 남성 목소리의 기본 진동수는 100~150Hz인데 이것이 재생되지 않는다. 그래도 말은 알아들린다 — 사람 귀는 배음만으로 없는 기본음을 복원한다(missing fundamental). 다만 **목소리가 얇고 가볍게** 들린다(전화기 목소리와 같은 현상).

#### 비교

| 대상 | 우리 대비 |
|---|---|
| 유선 전화 통화(300Hz~3.4kHz) | 우리가 조금 낫다 — 위쪽이 더 열려 발음이 또렷 |
| AM 라디오 | 우리가 낫다 |
| **스마트폰 스피커폰** | ✅ **거의 동급 — 가장 정확한 비유** |
| 저가 블루투스 스피커 | 비슷하거나 약간 아래(그쪽은 통이 있어 저음이 조금 난다) |
| 블루투스 이어폰(음악) | 🔴 비교 불가 |

#### 이어폰과 비교가 안 되는 이유 = 밀폐

이어폰은 귓구멍을 막는다. 밀폐된 작은 공간이라 진동판이 조금만 움직여도 압력이 생겨 저음이 난다.

우리 스피커는 안경다리에서 **허공에 대고** 소리를 낸다. 진동판 앞뒤의 소리가 옆으로 돌아 상쇄되고(음향 단락), 저음일수록 잘 돌아가므로 **저음부터 사라진다.** 부품을 좋은 것으로 바꿔도 해결되지 않는 **구조의 한계**다.

→ 다만 안경다리 안에 넣으면 작은 통이 생겨 개선된다. **§6.3에서 두께 3mm급을 고른 이유가 이것이다** — 통을 만들 여유를 남기기 위해서다.

#### 🔑 우리에게 필요한 것은 음질이 아니라 명료도다

- **음질(hi-fi)** = 원래 소리와 얼마나 똑같은가 — 음악 감상의 기준
- **명료도(intelligibility)** = 무슨 말인지 알아들을 수 있는가 — **안내 방송의 기준**

지하철·기내 방송은 음질이 나쁘지만 말은 정확히 전달된다. **저음을 깎는 것이 오히려 명료도에 유리하다** — 저음은 웅웅거려 자음을 덮는다.

장비 소음 속에서 짧은 경고·안내를 전달하는 우리 용도에는 400Hz~8kHz만 잘 나오는 편이 맞다. **그래서 검증 관문을 음질이 아니라 §8.1 G2 「명료도」로 두었다.**

#### 더 좋게 하려면 (선택지와 대가)

| 방법 | 효과 | 대가 |
|---|---|---|
| 샘플레이트 16k → 24kHz | 위쪽이 12kHz까지 열려 조금 또렷 | 통신량 1.5배(48KB/s) — 여전히 영상의 8% |
| 안경다리에 밀폐 챔버 설계 | 저음 실제 개선 | 3D 외장 재작업 |
| 이어폰형·골전도 전환 | 확실히 개선 | 🔴 **"글라스 내부 스피커" 컨셉 이탈.** 골전도는 밀착 압력 필요, 전류·두께 증가 |

**권고 = 현 구성 그대로 가고 G2를 통과하면 멈춘다.** 시연에서 평가받는 것은 *"소리가 좋다"* 가 아니라 *"경고를 알아듣고 손을 멈췄다"* 이다.

## 7. 결선

### 7.1 기존 결선 (`dev/glass/결선_초안.md`)

```
USB-C ──→ [SZH-LIP001] ── B+/B− ── LiPo 450mAh
              OUT+ ──→ [MSL 슬라이드 스위치] ──→ XIAO 5V
              OUT− ─────────────────────────────→ XIAO GND
```

### 7.2 추가 후

**기존 결선은 한 군데도 끊지 않는다.** 이미 전선이 붙어 있는 두 지점에 한 가닥씩 더 얹는다.

```
              OUT+ ──1가닥──→ [스위치 공통]
                              [스위치 ON단자] ──┬─→ XIAO 5V      (기존)
                                                └─→ 앰프 Vin     ★ 새 전선
              OUT− ──┬─→ XIAO GND                                (기존)
                     └─→ 앰프 GND                                ★ 새 전선

   XIAO D0(GPIO1) ★──→ BCLK    (비트 클럭)
   XIAO D1(GPIO2) ★──→ LRC     (좌/우 구분 클럭)
   XIAO D2(GPIO3) ★──→ DIN     (소리 데이터)
   XIAO D3(GPIO4) ★──→ SD      (앰프 켜기/끄기)
                        SPK+ / SPK− ★──→ 8Ω 마이크로 스피커
```

| 단자 | 나가는 전선 |
|---|---|
| `OUT+` | 1가닥 (스위치로) — **변화 없음** |
| 스위치 ON단자 | **2가닥** (XIAO / 앰프) |
| `OUT−` | **2가닥** (XIAO / 앰프) |

갈라지는 지점이 **스위치 뒤**인 이유 — 스위치 앞에서 갈라면 전원을 꺼도 앰프에 전기가 흘러 배터리가 마른다.

### 7.3 전원 설계 판단

**① 앰프 전원을 XIAO `3V3`에서 뽑지 않는다.**

| XIAO 핀 | 정체 | 앰프 전원으로 |
|---|---|---|
| `5V` | 입력 핀 — 배터리 3.7V가 들어옴 | 전기적으론 가능, 물리적 이유로 비권장 |
| `3V3` | **내부 레귤레이터 출력** — MCU·카메라·WiFi의 젖줄 | 🔴 **금지** |

클래스 D 앰프는 소리가 날 때 전류를 순간적으로 크게 당긴다. MCU 레귤레이터에서 같이 뽑으면 전압이 주저앉아 **카메라 전송이 끊기거나 ESP32가 브라운아웃 재부팅**한다. 소리 낼 때마다 영상이 끊기는 증상은 원인 추적도 어렵다.

**② 스위치 단자에서 뽑는다(스타 결선).** `5V` 핀과 전기적으로 같은 마디지만, XIAO의 작은 패드에 전선 두 가닥을 겹치면 잘 떨어지고 앰프 전류가 XIAO 기판의 얇은 배선을 거쳐 돈다. 스위치 단자는 패드가 크고 앰프까지 최단거리다.

**③ 🔴 `SPK−`를 GND에 연결하지 않는다.** MAX98357A 출력은 **BTL(Bridge-Tied Load)** — 두 선이 서로 반대로 흔들려 낮은 배터리 전압에서도 음압을 낸다. `SPK−`는 0V가 아니며, GND에 대면 **출력단 단락으로 칩이 파손**된다.

스위치 정격이 부족하면 **① 펌웨어 음량 상한 제한**(권장 — 최대 음량은 청력상 어차피 못 쓴다) 또는 ② 1A 이상 스위치로 교체.

**배터리 지속시간** — 현재 약 2~3시간 → 오디오 추가 후 약 1.5~2.2시간(통상 소비 기준). 말하는 시간이 전체의 몇 %뿐이라 실제 감소는 이보다 작다. `SD` 핀으로 평소 앰프를 꺼두는 설계가 여기서 값을 한다.

| 신호 4가닥 (XIAO → 앰프) | 26~30AWG 연선 | 전류 거의 없음 |
| 스피커 2가닥 | 26AWG 연선 | **트위스트** — 안 꼬면 카메라 배선에 잡음을 실을 수 있다 |

**접합 = 납땜 + 열수축튜브.** 🔴 **WAGO·빵판 금지**(`결선_초안.md` §4의 기존 결정). 가장 작은 WAGO 221(2구)도 16.5×8.2×14.5mm로 앰프 모듈과 맞먹고, 안경다리 끝 무게는 글라스를 흘러내리게 해 **화각이 틀어지면 감지 성능에 직결**된다. 또 WAGO는 고정 배선용이라 반복 진동에 접점이 헐거워질 수 있고, 221은 24AWG 이상을 물어 26AWG는 규격 하한에 걸친다.

**분기 방법**: 두 가닥을 5mm쯤 함께 꼬아 주석 도금한 뒤 **한 번에 납땜**한다(접점 1개 = 가장 튼튼·최소 부피).

**시제품 단계 예외** — 시험 중 앰프를 자주 뺐다 꽂아야 하면 **JST PH 2.0mm**(약 8×5×6mm, DFR0954에 이미 달려 있음) 또는 JST SH 1.0mm를 쓴다. **전선을 길게 빼서 글라스 밖에서 연결해 시험하고, 음량·핀·FPS 확정 후 짧게 잘라 납땜해 외장에 넣는다.** 안경다리 안에서 납땜을 풀었다 붙였다 하는 것은 실패하기 쉽다.

### 7.6 핀 배정 주의

- 카메라(OV3660)는 **B2B 커넥터로 GPIO10~18**을 쓴다 — 노출 핀(D0~D10)과 **겹치지 않는다**
- ESP32-S3의 I2S는 **핀 고정이 아니다** — GPIO 매트릭스로 남는 핀에 배정 가능
- ⚠️ **D8·D9·D10은 피한다** — SD카드 슬롯과 겹친다는 자료가 있고 **자료마다 핀 번호가 엇갈린다.** 실물 확인 항목

### 7.7 Pi5 호환성 — 디버깅 순서를 단순하게 만든다

| | ESP32-S3 (글라스) | 라즈베리파이 5 |
|---|---|---|
| I2S | ✅ 2채널, 핀 자유 배정 | ✅ 내장 (GPIO18·19·21) |
| 로직 레벨 | 3.3V — 직결, 변환 불필요 | 3.3V — 동일 |
| MCLK | 불필요 | 불필요 |

**Pi5도 아날로그 오디오 출력이 없어 같은 모듈이 그대로 쓰인다.** 앰프+스피커를 **먼저 Pi에 물려 소리를 확인**한 뒤 글라스로 옮기면, 문제가 생겼을 때 **펌웨어 탓인지 부품 탓인지**를 가를 수 있다.

## 8. 검증 — 관문과 측정 규율

### 8.1 관문

> 🔴 **G1을 통과하지 못하면 2·3단계로 진행하지 않는다.** 구조를 "오디오 전용 ESP32 분리"로 되돌려야 한다.

| 관문 | 무엇을 재나 | 통과 기준 |
|---|---|---|
| 🔴 **G1 · FPS** | 오디오 재생 중 E2E FPS | **NFR-1 15fps 이상 유지**. 현행 대비 하락폭을 함께 기록 |
| **G2 · 명료도** | 정해진 문장 20개를 들려주고 받아쓰기 정확도 | 착용 상태·실제 소음 조건에서 판독 가능 |
| **G3 · 경고 지연** | 위반 판정 → 소리 시작까지 | **0.3초 이내** |
| **G4 · 배터리** | 연속 구동 시간 (오디오 포함) | **90분 이상** — 시연 1회분 여유. 미달 시 음량·발화 빈도부터 조정 |
| **G5 · 환각** | 사실 묶음에 없는 버튼·공구 언급률 | **0건** (검증기 통과분 기준) |

### 8.2 측정 규율 (CLAUDE.md §5 준수)

- 🔴 **단일 세션 값 금지** — 통합값으로 인용한다. 세션 간 편차가 크다
- 🔴 **조건을 반드시 병기** — 착용 구도·조명·소음·음량 설정이 없는 수치는 인용 금지
- 🔴 **`run_demo.sh` 실기동 확인을 검증에서 빼지 않는다** — import 검사로 못 잡는 런타임 오류가 있다
- 🔴 **"상한을 측정했다"와 "원인을 규명했다"를 혼동하지 않는다** — FPS가 떨어지면 자원 사용률부터 확인한다(§10.34의 교훈)
- 🔴 **새 측정은 §10.x에 기록하고 `[CURRENT]` 표도 함께 고친다.** 유효성 마커를 단다

# UI/UX 전면 수정 — 아이디어 수집 및 실현 가능성 판정 (2026-08-03)

> **목적**: UI/UX 전면 수정에 앞서 **사용자 머릿속에만 있던 아이디어를 원본 그대로 남기고**, 각각의 실현 가능성을 판정해 설계의 재료로 삼는다.
>
> **왜 이 문서가 따로 있나** — UI는 이 프로젝트에서 **설계 문서가 한 번도 없었다.** `specs/` 12개 중 UI를 다룬 것이 없고, 통합문서는 머리말에서 *"화면설계서 자리를 FSM·AI·공정 로직으로 대체"* 한다고 명시적으로 제외한다. 즉 지금 화면이 왜 그런 배치인지 적힌 곳이 없다. **이 문서가 UI에 대한 첫 기록이다.**
>
> **이 문서가 아닌 것**: 설계서가 아니다. 아이디어와 판정만 담으며, 실제 설계는 후속 spec이 담당한다.

## 1. 아이디어 원본 (사용자 제시, 2026-08-03)

> 아래는 사용자가 제시한 원문을 **다듬지 않고 보존**한다. 판정·해석은 §2 이후에 분리해 둔다.

- **UI 구조 변경**: Full Screen 실시간 영상(디스플레이 전체 화면을 실시간 영상으로 채우기, 만약 카메라 출력 해상도·비율과 디스플레이 해상도·비율이 다를 경우 레터박스를 넣지 않고 ui를 넣는다, ui는 미정)
- Full Screen 실시간 영상 위에 불투명 버튼 또는 ui 제작(레터박스 ui와는 다른 ui), (불투명 버튼 제작 이유는 ui 뒤로 Full Screen 실시간 영상이 희미하게 보이기 위함, **애플 글래스 UI 참고(모티브)**)
- 버튼과 버튼 입력 사이에 메인 작업(버튼 누르기)와 다른 **서브 작업**(예: 대기, 공구 찾기, 공구 들기) ui 제작(예: B1 버튼을 누른 후 30초~1분 대기(시연용 공정 시퀀스 PECVD 작업 중 진공도 또는 퍼지 대기) 후 B2 버튼 누르기, B2 버튼을 누르고 공구(스패너 또는 십자 드라이버) 찾고 손으로 집기)
- **대기 UI**: 30초~1분 대기를 표현할 채워지는 **게이지바** 대기 UI 제작
- 현재 UI/UX 기능 중 **상태(경고) UI(우상단 UI) 및 공정 단계 UI 개선**
- **레시피 로드 버튼 삭제, 작업 시작 버튼으로 변경**
- 한 화면에 모든 버튼을 넣지 말 것 **메뉴 버튼을 별도로** 만들어 메뉴 안에 캘리브레이션 또는 CCTV, 공정 단계, 설정, 종료 버튼 넣기
- **UI/UX 기능 전면 수정의 전제**는 현 UI/UX 기능은 콘솔 박스 디스플레이에 사용할 만한 UI/UX의 형태이지만, 이번에 수정한 UI/UX는 **스마트 글라스의 디스플레이라고 생각하고** 구현한다. 시연으로는 콘솔에 부착되어 있는 디스플레이로 UI/UX 화면이 보여지지만, **스마트 글라스 디스플레이 제작 한계로 인해** 콘솔에 부착한 디스플레이로 스마트 글라스 디스플레이에 보여지는 UI/UX라고 생각하고 구현한다.

### 추가 아이디어 (같은 날, 후속)

- 레터박스 자리에 **사이드바 UI는 넣지 않는다** — **검정 레터박스**로 채우고 **좌우 분할**로 비율을 맞춘다.
- 현재 우측에 있는 **로그도 메뉴 안으로** 넣는다.
- `"공정 시작"`이 아니라 **`"작업 시작"`** 으로 한다.
- Demo 실행 시 하는 **선 연결·카메라 연결 점검(1차)은 백그라운드**로 두고, **작업 시작 버튼을 누르면 2차 점검**을 한 번 더 한다.

### 화면 산수

높이를 꽉 채우면 영상은 **1440×1080**, 남는 폭이 **정확히 480px** → **좌우 240px씩 검정**.

### 서브 작업이 UI만의 문제가 아닌 이유

현재 레시피는 버튼 순서만 안다:

```json
{"order": 1, "button": "B1", "name": "클린·가스차단"}
```

대기를 넣으려면 **레시피 스키마 확장 + FSM 처리**가 필요하다. 현재 FSM 상태 6개(`IDLE`·`READY`·`PROCESS_RUN`·`MONITOR`·`WARNING`·`BLOCK`)에 대기가 없다.

🔴 **딸려 오는 안전 결정** — *대기 중에 다른 버튼을 누르면?*
→ **사용자 결정: 순서 위반 경고.** 근거: **"B1 누름(메인) + B1 후 대기(서브) = 하나의 B1 작업"** 이므로, 그 작업이 끝나기 전에 다른 버튼을 누르면 순서 위반이다.
→ 이 정의 덕분에 **FSM에 새 상태를 만들지 않고** *"B1 작업이 아직 안 끝났다"* 로 다룰 수 있어, 순서 위반 판정 논리가 현 구조 그대로 유지된다.

## 4. 성능 — 예상과 실측

### 4.1 처음의 경고 (예상)

Full Screen + 반투명 + FPS 상승이 **GUI 스레드 한 곳에 겹쳐** 부하가 3.5배가 되고, `_on_roi`가 GUI 스레드에서 `fsm.update_vision()`을 부르므로 **순서 위반 판정까지 밀릴 수 있다**고 경고했다.

### 4.2 🔴 실측 결과 — 그 경고는 과했다

> ⚠️ **이 수치는 예비 측정이다.** 조건이 붙으므로 **확정값이 아니며 통합문서 §10에 올리지 않는다.** 성능 주장에 인용 금지.
> 조건 = `QT_QPA_PLATFORM=offscreen` · 파이 유휴 상태 · 위젯 렌더링/이벤트/FSM 호출 미포함 · 2026-08-03.

| 연산 | 현재 | Full Screen | 배수 |
|---|---|---|---|
| 영상 스케일 (Smooth) | 2.62 ms | 6.67 ms | 2.5배 |
| 영상 스케일 (**Fast**) | — | **2.92 ms** | 현재와 동급 |
| 창 캡처 (녹화) | 2.11 ms | 5.25 ms | 2.5배 |

**초당 점유율** (1000ms 중 몇 ms를 쓰는가)

| 조건 | 점유율 |
|---|---|
| 현재 (11fps + 녹화15fps) | **6.0%** |
| Full Screen (11fps + 녹화) | **15.2%** |
| Full + FPS 25 (최악) | **24.5%** |
| Full + FPS 25 + Fast 스케일 | **15.2%** |

**최악이 24.5%다. 755ms가 남는다.** 큐가 쌓여 밀릴 상황이 아니다.

**배수 예측(2.7배)은 맞았고, "그래서 위험하다"는 판단이 틀렸다.** 절대 수준을 재지 않고 배수만으로 위험을 주장한 것이 원인이다 — 이 프로젝트 규칙(*"측정 전에는 결론이 아니다"*)에 스스로 걸린 사례다.

### 4.3 참고 — 배경 블러 (b)안

| 오버레이 크기 | 1회 | 25fps 기준 추가 |
|---|---|---|
| 400×200 | 1.68 ms | +4.2%p |
| 800×400 | 4.92 ms | **+12.3%p** |

블러는 무시할 수 없는 크기다. **(a)부터 하자는 판단이 여기서도 유효**하다.

### 4.4 이 측정이 못 잰 것

① 실제 HDMI 출력(컴포지터·화면 갱신) ② 다른 스레드와의 CPU 경합 ③ 위젯 렌더링·이벤트·FSM 호출 ④ FPS 25는 여전히 가정(통신 P-01 미판정) ⑤ **FSM 지연 실측** — 실제 스트림이 있어야 한다.

## 6. 설계에서 정할 것 (미결, 8)

지금 정하지 않아도 되는 것들. 후속 spec에서 다룬다.

- 오버레이에 **무엇을** 띄울지 — 항목과 배치
- 2차 점검이 **무엇을** 점검하는지
- 대기 시간·공구 종류의 실제 값 (시나리오 작업에서)
- 레시피 JSON의 서브 작업 표현 형식
- 메뉴를 **여는 방법** + 🔴 **Full Screen 탈출구**(메뉴가 안 열리면 종료 불가)
- 키보드 시뮬 입력(`1`~`4`·`E`) 유지 여부
- 녹화 정책 (1920 캡처 유지/축소/끄기)
- HW 없이 어디까지 검증할지 — 완료 기준

## 7. 채택하지 않은 것

**사이드바 UI** — 레터박스 자리(480px)에 정보 패널을 두는 안. 현재 우측 패널(384px)보다 넓어 기술적으로 유리했으나, **글라스 관점과 어긋난다**(글라스라면 정보가 영상 *위에* 떠야지 *옆에* 있으면 안 된다)는 이유로 **사용자가 검정 레터박스를 선택**했다. 모든 UI는 오버레이로 간다.

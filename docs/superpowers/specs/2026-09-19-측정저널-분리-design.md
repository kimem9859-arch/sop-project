## 1. 무엇을·왜

**통합문서 6,649줄 중 §12 갈래 저널이 5,141줄(77%)이다.** 나머지 전부를 합쳐도 1,508줄이다.

| 부분 | 줄 수 | 성격 |
|---|---|---|
| §1~§11 · §13~§16 | 1,211 | **현행 사실** — 지금 맞는 설계·사양 |
| §12 **머리**(갈래 색인 · `[CURRENT]` · 🔓 미결 · 🧱 절 구성 규약) | 297 | **현행 사실** — 지금 맞는 수치와 미결 |
| §12 **갈래 저널** ①~⑥ (측정 절 63개) | **5,141** | **시간순 기록** — 그때 그 조건에서 이렇게 나왔다 |

→ 저널만 떼면 통합문서는 **1,508줄**이 된다. `grep` 결과가 깨끗해지고, Read 도구로 여는 부담이 크게 줄며, 앞으로 §12 가 계속 커져도 본문이 밀리지 않는다.

🔴 **이것은 「사람이 읽기 좋게」 나누는 것이 아니다.** 이 문서는 **오로지 Claude Code 가 읽는다**(2026-09-19 사용자 확인 · 문서 첫머리 선언). 사람은 대화의 요약으로 본다(CLAUDE.md §2 「사용자 검토는 파일을 열게 하지 않는다」).

나누는 근거는 둘이다:
1. **성격이 다르다** — 현행 사실(R5: 사실은 한 곳에만)과 시간순 기록(R6: 갈래 끝에 새 절 + 마커)은 갱신 규약도 인용 방식도 다르다.
2. **Claude Code 의 읽기 비용** — `grep` 한 번에 저널 63개 절이 함께 걸려 현행 사실을 덮고, Read 도구로 여는 부담이 크며, 앞으로 §12 가 커질수록 나빠진다. 분량은 사람에게가 아니라 **기계에게** 제약이다.

## 2. 무엇을 어디로

```
docs/통합문서.md        1,508줄   §1~§16 + §12 머리(색인 · [CURRENT] · 🔓 미결 · 🧱 규약)
docs/성능검증-저널.md   5,141줄   §12 갈래 ①~⑥ — 측정 절 63개
```

**절단면** = `## 📂 갈래 ① 초기 검증·KPI` 직전. 그 위(297줄)는 전부 남고, 그 아래 6개 갈래 블록이 전부 나간다.

### 🔑 머리를 남기는 이유

`[CURRENT]` 표는 **「수치는 여기서 먼저 찾을 것」**의 자리다. 떼어내면 수치 하나 보려고 매번 다른 파일로 가야 한다. **머리는 정본, 저널은 창고**다.

## 3. 🔑 번호 체계는 한 글자도 바뀌지 않는다

`§12.34` 는 파일이 달라져도 **여전히 `§12.34`** 다.

- 참조 치환 **0곳** — 2026-09-18 재편에서 겪은 치환 사고(손상 7건)가 반복되지 않는다.
- 갈래 색인(`12.8 · 12.10 · …`)도 그대로 유효하다.
- `grep -r docs/` 로 두 파일이 함께 잡힌다 — Claude Code 의 읽기 방식이 바뀌지 않는다.

## 4. 규칙 개정 — R3

현행:
> **R3 쪼개는 축은 하나뿐** — 문서를 주제로 나누거나 사본을 만들지 않는다(grep 대상이 나뉘면 한쪽만 읽고 놓친다). **나누는 축은 「현행 / 폐기」 하나다** — 현행 = 이 문서 · 폐기 = `변경이력.md`. 같은 사실을 양쪽에 두지 않는다.

개정안:
> **R3 나누는 축은 셋뿐** — 문서를 **주제로는** 나누지 않는다(grep 대상이 주제로 갈리면 한쪽만 읽고 놓친다). 나누는 축은 **성격** 하나이고 갈래는 셋이다 — **현행 사실** = 이 문서 · **폐기된 사실** = [`변경이력.md`](변경이력.md) · **시간순 측정 기록** = [`성능검증-저널.md`](성능검증-저널.md). 같은 사실을 둘 이상에 두지 않는다. §12 **머리**(갈래 색인·`[CURRENT]`·🔓 미결)는 현행 사실이라 이 문서에 남는다.

→ **R2·R5·R6 은 고치지 않는다.** R6(§12 기록 규약)은 저널 파일에서 그대로 적용되고, R5 의 「측정 수치 = §12 `[CURRENT]`」도 머리가 통합문서에 남으므로 유효하다.

## 8. 버린 대안

- **§12 전체(머리 포함) 분리** — 수치 하나 보려고 매번 다른 파일로 가야 한다. `[CURRENT]` 는 「여기서 먼저 찾을 것」의 자리라 통합문서에 남아야 한다.
- **16장 전면 분할** — 얻는 것(장별로 열림)에 비해 grep 대상이 흩어지고, 2026-09-18 재편을 또 뒤집는다. **문제의 77%가 §12 하나**라 그것만으로 충분하다.
- **`§N.M` → `[[위키링크]]` 전환** — 백링크·그래프뷰를 쓰려면 1,282곳을 바꿔야 하는데 `§N.M` 체계가 Claude Code 의 grep 기반 읽기의 핵심이다. 치환 위험이 크고 얻는 것은 사람 쪽 편의뿐인데, **옵시디언을 쓰지 않기로 해 그 편의도 없어졌다**(2026-09-19 사용자).
- **갈래별 6개 파일로** — 갈래 간 참조(`§12.22` ↔ `§12.29`)가 파일 경계를 여섯 번 넘는다. 한 파일이면 그 안에서 끝난다.

## 10. 세 문서의 역할

파일이 갈리면 「어디에 쓸지」가 매번 판단거리가 된다. 각 문서 첫머리에 **한 줄 판별 규칙**을 박아 그 판단을 없앤다.

| 문서 | 담당 | 무엇에 답하나 | 갱신 방식 |
|---|---|---|---|
| `통합문서.md` | **현행 사실의 정본** | 「**지금** 무엇이 맞는가」 — 설계·사양·배경·HW(§1~§16) + §12 머리(갈래 색인 · `[CURRENT]` · 🔓 미결 · 🧱 규약) | **덮어쓴다**(R5) · 덮은 옛 사실은 `변경이력.md` 로(R2) |
| `성능검증-저널.md` | **측정 기록의 원장** | 「**언제 어떤 조건**에서 무엇이 나왔나」 — `§12.N` 본문 | **덧붙인다**(R6) · 지우지 않고 `⛔ SUPERSEDED-BY` 마커 |
| `작업로그.md` | **작업의 시간순 저널** | 「**누가 언제** 무엇을 했나」 — ✅/⏸/▶/🔗 | 블록을 쌓는다(`session-wrap`) |

🔑 **판별 규칙 한 줄** — **조건 없이 인용할 수 있으면 통합문서, 조건을 달아야 하면 저널.**

이 규칙은 이 프로젝트가 반복해서 물린 함정과 맞물린다 — 「감지율을 성능 상수로 쓰지 말 것 · 구도 조건을 함께 밝힌다」(CLAUDE.md §5). 조건이 필요한 값은 애초에 저널에 있고, 통합문서 `[CURRENT]` 표의 값은 조건이 표 안에 적혀 있다.

**적는 자리 3곳** — 통합문서 「📌 문서 안내」 · 저널 첫머리 · README 역할표. 문구는 위 표와 판별 규칙 한 줄.

🔑 **§5 의 상호 포인터와 같은 자리다** — 포인터(「저 파일에 무엇이 있다」)와 역할(「이 파일은 무엇을 담당한다」)을 **한 블록에 함께** 쓴다. 따로 두면 같은 자리에 두 번 손대게 된다.

## 11. 세 문서 동기 관문 — `work-close` 2.5

**문제** — 지금 2.3 은 「§12 새 절 + `[CURRENT]` 표 + 갈래 색인」을 **문장으로만** 요구하고, 기계 검사는 **색인 누락 하나뿐**이다. 파일이 갈리면 저널만 고치고 통합문서를 잊는 일이 실제로 일어난다.

「저널이 바뀌면 무조건 통합문서도 바뀌어야 한다」로 하면 **오타 정정·`⛔` 마커만 다는 변경**까지 걸린다. 거짓 경보가 잦은 관문은 사람이 무시하게 된다 — **같은 목표의 문서 훅이 이 프로젝트에서 세 번 실패한 이유**가 그것이다(CLAUDE.md §3). 새 절 추가는 「새 측정을 기록했다」와 정확히 같은 뜻이고, 그때만 `[CURRENT]`·색인 갱신이 반드시 따라온다.

### 작업로그(셋째 문서)는 기존 고리를 쓴다

새 장치를 만들지 않는다. 3단계 `session-wrap` 이 2단계 커밋 해시를 🔗 줄에 넣고, 빠지면 다음 세션 `/이어하기` 색인이 **부분기재**로 띄운다(2026-09-14 리뷰 I4). 이미 작동하는 고리라 2.3 에 「세 문서가 한 작업 단위에서 함께 갱신된다」는 문장으로 **연결만** 한다.

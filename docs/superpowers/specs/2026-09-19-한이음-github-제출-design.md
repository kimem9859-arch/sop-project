## 1. 무엇을·왜

한이음 드림업 공모전 **2차 평가에 GitHub 저장소 주소를 제출**한다. 가이드(노션 「☆공모전 GitHub 제출 가이드☆」, 2026-09-19 확인)가 정하는 것은 넷이다.

| 요건 | 가이드 원문 취지 | 현재 상태 |
|---|---|---|
| **Public** | 「꼭 Public 으로 생성하여 제출」 | ✅ `kimem9859-arch/26_HC248` 생성 완료(2026-09-19, size 0 · main) |
| **저장소명** | `github.com/<계정명>/<프로젝트 번호>` | ✅ 프로젝트 번호 `26_HC248` |
| **소스코드 업로드** | 「소스코드를 레포지토리에 업로드 한 후」 | ✅ 244개 파일 · 28MB(2026-09-19) |
| **README 필수 5항목** | 개요 · 팀원 소개(**소속 기재 금지**) · 시스템 구성도 · 작품 소개영상 · 핵심 소스코드 | ✅ 5항목 · 이미지·썸네일 실접근 확인(HTTP 200) |

🔑 **가이드가 개인정보에 대해 정하는 것은 「팀원 소개(소속 기재 금지)」 하나뿐이다**(2026-09-19 확인). 종전에 이 프로젝트가 들고 있던 「학교명·이름·소속 금지 · git 이력·계정명까지」는 **사용자 지시(2026-09-15)와 그로부터 나온 추론**이었고, 2026-09-19 사용자가 **가이드 요건만 따르기로** 정했다. 따라서 **git 이력 재작성은 하지 않는다.**

**조사 결과 — 소속은 이미 없다.** `.md` 전수에서 학교명·학과·지도교수 이름이 나오지 않는다(통합문서 §1 은 「지도교수 1명」처럼 **수만** 적는다). 가이드의 소속 금지는 사실상 충족돼 있어, 남은 일은 **저장소를 가이드 모양으로 만드는 것**이다.

## 2. 저장소 구성 — 새 저장소 하나

```
github.com/kimem9859-arch/26_HC248     Public · 제출용
  README.md                  필수 5항목
  Demo/ arduino/ scripts/    실행 코드·펌웨어   ← Rpi5
  dev/                       학습 코드·결선도   ← sop-project
  docs/통합문서.md · 성능검증-저널.md · 변경이력.md
  media/발표차트/            구성도·그래프 (README 가 인용)
```

**넣지 않는 것** — `작업로그.md` · `claude-code-작업로그.md` · `claude-code-작업문서.md` · `CLAUDE.md` · `docs/superpowers/`(spec·plan) · `정본검토-기록.md` · `정본검토-조사-*.md`. 전부 **내부 작업 메모**다. 근거 = 「제출 자료이므로 불필요한 문구(작업 경위·확인 날짜 같은 내부 메모)를 넣지 않는다」(2026-09-15 사용자).

🔑 **기존 두 저장소(`sop-project`·`Rpi5`)는 작업용으로 그대로 둔다.** 이름을 바꾸거나 공개로 돌리지 않는다 — 그렇게 하면 앞으로의 모든 작업 커밋이 공개되고 작업용과 제출용이 한 몸이 된다.

### 🔑 제출 저장소는 이력을 갖지 않는다

`26_HC248` 은 **현재 파일만** 담는다(단일 초기 커밋). 두 저장소의 이력을 합치려면 이력 재작성이 필요한데, 그것은 이번 범위 밖이고(§1) 얻는 것도 없다 — 평가자가 보는 것은 **지금 작동하는 코드와 README** 다.

## 5. 팀원 소개 — 비운 채로 만들고, 채운 뒤에 올린다

이름을 지어낼 수 없다. 사용자가 「있는 것만으로 진행」을 택했으므로:

- 표 **틀**과 **인원 구성**(총 8명 = 한이음 드림업 멘티 5 + 그 외 참여 3 · 멘토 1 · 지도교수 1 — 통합문서 §1 의 사실)만 만든다.
- 이름 칸은 비워 둔다. **「TBD」 같은 미완성 표시는 쓰지 않는다**(제출 자료는 완성형으로 — 2026-09-15 사용자).
- ✅ **결정(2026-09-19 사용자) — 틀만 만들고 칸은 공백으로 둔 채 올린다.** 종전 설계는 「이름을 받은 뒤 push」였으나 사용자가 빈 칸 그대로를 택했다. 이름이 생기면 표만 채워 다시 올린다.

## 6. 어떻게 올리나

`gh` CLI 가 이 파이에 없다(2026-09-19 확인). 저장소는 사용자가 웹에서 만들었고, 내용 채우기는 **`git` 만으로 된다**:

1. 작업 폴더(`/tmp/.../26_HC248`)를 만들어 파일을 모은다
2. `git init` → `git remote add origin https://github.com/kimem9859-arch/26_HC248.git`
3. 단일 커밋 → `git push -u origin main`

⚠️ **`git add -A` 는 제출용 저장소에서도 권한 설정이 막는다**(2026-09-19 실행 중 확인 — 훅은 저장소를 구분하지 않는다). 경로를 나열한다.

⚠️ 제출 저장소는 **작업 저장소가 아니다** — `sop-project`·`Rpi5` 의 원격 설정을 건드리지 않는다.

## 7. 지키는 것

- 🔴 **문서 본문은 복사하는 것이지 고쳐 쓰는 것이 아니다**(채점자 익명화 제외) — 통합문서·저널·변경이력은 원본 그대로 들어간다.
- 🔴 **소속 표기가 새로 들어가지 않는다** — README 를 쓰면서 학교·학과·지도교수 이름을 넣지 않는다.
- 수치를 README 에 옮길 때 **조건을 함께** 쓴다(「클린룸 형광등·모조 콘솔 조건에서」 등). 「검증 완료」 같은 조건 없는 단정 금지.
- 올린 뒤 **실제로 확인한다** — Public 여부 · README 렌더링(mermaid·썸네일) · 파일 수.

## 8. 버린 대안

- **`Rpi5` 를 `26_HC248` 로 개명** — 작업용과 제출용이 한 몸이 되어 앞으로의 모든 커밋이 공개된다.
- **빈 저장소에 README 만 두고 두 저장소를 링크** — 가이드가 「소스코드를 업로드한 후」라고 하므로 요건 미달 위험.
- **서브모듈로 연결** — 평가자가 코드를 바로 못 본다.
- **git 이력 재작성**(`filter-repo`) — 가이드가 요구하지 않는다(§1). 918건을 다시 쓰는 위험만 남는다.
- **제출본에서만 채점자 익명화** — 사본이 생겨 한쪽만 낡는다(R3).
- **작업로그까지 제출** — 내부 메모다(2026-09-15 사용자).

## 9. 약한 곳

- ⚠️ **README 가 통합문서와 갈라져 낡을 수 있다.** 같은 사실이 두 곳에 놓인다(R5 의 예외적 허용 — 독자가 다르다). 완화 = README 는 **결론과 조건만** 담고 세부는 `docs/` 를 가리킨다.
- ⚠️ **제출 저장소는 수동 동기화다.** 원본이 바뀌어도 자동으로 따라가지 않는다. 제출 직전 한 번 더 복사하는 것을 전제로 한다.
- ⚠️ **1차 시연영상이 2차 평가 시점의 완성도와 다를 수 있다** — 그 뒤로 음성비서·실콘솔 등이 들어갔다. 새 영상이 생기면 링크만 교체한다.

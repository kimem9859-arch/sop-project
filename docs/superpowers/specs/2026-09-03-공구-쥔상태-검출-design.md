# 공구 「쥔 상태」 검출 설계 — `tool_v4` + 판정 2조건

> 2026-09-03 · 대상 = 서브작업 `wait_tool`(공구 지참) · 관련 코드 = `Rpi5/Demo/tool_state.py`·`tool_gate.py`
>
> 🔴 **측정 수치는 여기 쓰지 않는다.** 기준선·실측은 전부 통합문서 **§10.54** 가 정본이고 이 문서는 포인터만 둔다.
> 앞선 설계 = `2026-08-14-공구입력-A2-design.md`(A-2 원설계) · 경위 = 통합문서 §10.44 · §10.54

## 1. 무엇을 고치나

**증상** — 데모에서 요구 공구를 손에 쥐어도 서브작업이 넘어가지 않는다.

**원인**(§10.54-(3) 에서 조건을 갈라 확정) — **공구를 쥐면 손이 공구를 가려 `tool_v3` 가 그 공구를 놓친다.** 같은 자리에 놓아두면 잘 잡히던 것이 쥐는 순간 사라진다. 「쥔 공구」 판정은 손과 공구가 한 프레임에 함께 잡혀야 성립하므로, 재료 자체가 없어 게이트가 열리지 않는다.

**원인이 아닌 것**(같은 절에서 배제)

- 손 검출 — 쥔 상태에서도 잘 잡힌다(§10.54-(3)).
- 판정 좌표(검지 끝) — 후보 8종을 같은 프레임에서 비교했고 검지 끝이 가장 잘 맞았다(§10.54-(4)). **좌표를 바꿀 근거가 없다.**
- 임계 — 검출된 것의 점수가 낮은 게 아니라 **박스가 아예 없다**(§10.54-(3)).

**따라서 처방은 하나다** — 모델이 **쥔 상태의 공구를 볼 줄 알게** 만든다. 그리고 이왕 「쥠」을 클래스로 배우게 하는 김에, 그 클래스를 **판정의 주 근거**로 쓴다.

## 2. 판정 — 메인 OR 보조

`tool_state.ToolState` 의 「쥠」 판정을 두 갈래로 만든다. 둘 중 하나만 성립해도 완료다.

| | 조건 | 근거 |
|---|---|---|
| **메인** | `{요구공구}-in-hand` 박스가 검출 **AND** 같은 프레임에 손 검출 | 모델이 직접 판정한 「쥠」 |
| **보조** | 검지 끝이 `{요구공구}` 박스 안 | 종전 규칙 그대로 |

### 설계 원칙 (바꾸지 않는 것)

- 🔴 **부재를 근거로 쓰지 않는다.** 두 조건 모두 **검출된 박스**가 근거다. 「안 보이니 넣은 것」 계열의 판정은 §10.44-(3)(8) 에서 오완료로 폐기했고, 여기서 되살리지 않는다.
- 🔴 **완료는 유지된다**(되돌아가지 않는다). 종전과 같다.
- ⚠️ 판정은 여전히 **Qt·카메라·config 에 의존하지 않는다** — 검출 결과와 손끝 좌표를 인자로 받는다. GUI 없이 시험할 수 있어야 한다.

### 메인 조건에 손 검출을 묶는 이유

`-in-hand` 박스 하나만으로 완료하면 **배경 오검출이 그대로 오완료**가 된다. 실제로 §10.54-(5) 에서 엉뚱한 공구를 요구 공구로 오검출하고 그 위에 손끝이 얹혀 완료가 난 사례가 있다. 손 검출을 함께 요구하면 **손이 없는 화면에서 난 오검출은 전부 걸러진다.** 쥔 상태의 손 검출률이 높다는 것이 §10.54-(3) 에서 확인됐으므로 비용은 거의 없다.

⚠️ **메인 조건은 손끝 좌표를 보지 않는다** — 「손이 화면에 있는가」만 본다. 좌표를 쓰는 것은 보조 조건의 몫이다. 둘을 섞으면 보조 조건을 두 번 쓰는 것이 된다.

### 오답 공구

`{다른공구}-in-hand` 이 잡히고 요구 공구 쪽 근거가 없으면 종전대로 그 공구 키를 돌려 `wrong_tool` 경고를 띄운다. **요구 공구 근거가 있으면 그쪽이 이긴다** — 「쥐지 않은 공구가 화면에 함께 보이는 것」은 정상이기 때문이다(설계 §4.3 의 원칙 유지).

### 클래스명 대조

모델 클래스 `wrench-in-hand` → 우리 키 `wrench`. **접미어 `-in-hand` 를 벗겨 대조**한다.
🔑 **`recipe.json` 은 고치지 않는다** — 요구 공구 3종(`driver`·`wrench`·`pliers`) 선택 기능(`overlay_menu.set_tools()` · `safety_console.py`)도 그대로 산다. **3종 전부가 요구 공구 자리에 설 수 있다**는 것이 이 설계의 전제다.

## 4. 관문 — 통과 못 하면 어떤 수치도 쓰지 않는다

### 관문 1 · 다양성 (학습 전, 폐기 가능)

`dataset_diversity.py` 로 in-hand 소스의 **출처 점유**를 잰다. ARCAD 식(장면 몇 편에서 뽑은 연속 프레임)이면 **그 자리에서 이 처방을 폐기**하고 판정 규칙 재설계로 되돌아간다.

근거 = §10.39. **실패의 주된 원인은 장수가 아니라 다양성**이었다. 이 데이터셋도 영상 프레임이라 같은 위험을 갖는다(앞부분 표본은 같은 장면 연속, 중간 표본은 다른 사람·다른 방이었다 — 전량을 재기 전에는 판정할 수 없다).
⚠️ 「출처 수」는 **실제 장면 다양성의 하한선**으로 읽는다(§10.40-(2)(5)).

### 관문 2 · 🔒 홀드아웃 (확정 후 1회만 개봉)

**우리 ESP32 영상**으로 만든다. 3종 모두 요구 공구가 될 수 있으므로 **3종 × 놓임·쥠 2조건 = 6세트**, 각 60초. 합격 판정이 두 조건의 대비로 이뤄지기 때문에 조건을 나눠 찍는다(§10.54-(3) 과 같은 구도).

🔴 **2026-09-03 촬영본은 쓸 수 없다 — 오버레이가 그려져 있다.** 그 영상은 「왜 안 잡혔는지」를 눈으로 보려고 손 랜드마크·공구 박스·HUD 를 그린 쪽이다. 그 위에 라벨을 달면 **시험지에 답이 인쇄된다.** 점검 스크립트가 추론용으로 만드는 **오버레이 없는 사본을 저장하도록 고쳐서 다시 찍는다**(렌치 포함 전량).

**작업 분담**

| 단계 | 담당 |
|---|---|
| ① 점검 스크립트에 원본(오버레이 없는) 프레임 저장 추가 | Claude |
| ② 촬영 6세트 (3종 × 2조건 × 60초) | 사용자 |
| ③ 프레임 추출 · 중복 제거 · Roboflow 업로드(**`test` 분할 명시**) | Claude |
| ④ **수동 라벨링** | 사용자 |
| ⑤ 내려받기 · 채점 스크립트 · `tool_v3` 기준선 채점 | Claude |

- **분량 = 조건당 40장 안팎, 합계 약 240장.** 60초에 100~120프레임이 나오는데 연속 프레임은 거의 같은 그림이라, 시간 간격을 두고 고르면 정보를 거의 잃지 않으면서 라벨링 부담이 준다.
- 🔴 **Roboflow 자동 분할을 쓰지 않는다** — 업로드 시점에 `test` 로 명시한다(`upload_roboflow.py` 머리 주석의 `console_v1` 실패 교훈).
- 🔴 **전량 수동 라벨.** 평가 대상 모델로 프리라벨을 만들면 채점이 순환논리가 된다.
- ⚠️ 업로드는 **외부 전송**이다. 무엇이 올라가는지 확인한 뒤 실행한다.

### 관문 3 · 합격 판정

같은 홀드아웃에서 `tool_v3` 대 `tool_v4` 를 **클래스별로** 비교한다. 운용 임계(config 값) 그대로, 파이프라인 그대로 잰다.

1. **쥔 상태 재현율이 3종 모두 오를 것** — 기준선 = §10.54-(3).
   🔴 **합격선의 구체 수치는 계획서에서, 홀드아웃을 개봉하기 전에 못 박는다.** 결과를 보고 정하면 어떤 값이든 합격이 된다.
2. **놓인 상태가 퇴행하지 않을 것** — §10.38 에서 남의 valid 점수는 오르고 우리 도메인이 무너진 전례가 있다. 회귀를 반드시 함께 본다.
3. `pliers` 만 미달이면 → **보강 촬영 / 시연 선택지 축소**를 그때 결정한다(지금 정하지 않는다). 세 in-hand 클래스 중 `pliers-in-hand` 의 장수가 가장 적다는 것을 알고 시작한다.

### 관문 4 · 중단 규칙

**어떤 조합으로도 쥔 상태 재현율이 오르지 않으면 이 처방을 폐기한다.** 그때는 판정 규칙 재설계(근접 후 소실 계열 등)로 돌아가되, 🔴 **부재를 근거로 쓰는 안은 여전히 금지**다.

## 6. 거부한 대안

| 대안 | 거부 사유 |
|---|---|
| 판정 좌표를 검지 끝에서 손바닥 중심 등으로 변경 | §10.54-(4) — 후보 8종 비교에서 검지 끝이 가장 잘 맞았고, 애초에 공구 박스가 없는 구간이 지배적이라 좌표로는 못 산다 |

| 「공구가 사라지면 쥔 것으로 본다」 | §10.44-(3)(8) — 부재를 근거로 쓰다 오완료가 났고 그래서 폐기한 길이다 |
| in-hand 을 별도 클래스로 두지 않고 같은 `wrench` 로 병합 | 검출률은 나아지지만 「놓임 vs 쥠」을 모델에게 물을 수 없다. 사용자 결정(2026-09-03) = 클래스를 나눈다 |
| 직접 촬영해 학습 데이터 구축 | 시간 제약. **홀드아웃 촬영(3종 각 60초)만** 남긴다 |
| 손 클래스 보유 데이터셋에서 겹침으로 in-hand 자동 파생 | 후보를 열어보니 합성 이미지이거나 공구 종류가 우리와 달랐다(§3) |

## 7. 미결 (이 설계 밖)

- 스트림 FPS 편차(§10.54-(1)) — 홀드아웃 촬영 품질에 영향은 주나 이 설계의 대상은 아니다.
- §10.54-(5) 의 배경 오검출 자체 — 손 검출 동반 조건이 완화하지만 없애지는 않는다. 네거티브 보강(§10.43)의 재평가 근거로 남긴다.

## 1. 목표 / 비목표

**목표** — 짧은 시연 영상 하나를 찍을 수 있는 최소 동작.

```
공구 지참 단계에서 →  "가디언"  →  띠링  →  "앞에 보이는 게 뭐야?"  →  "앞에 렌치가 보입니다."
```

**비목표 (🔴 이번에 안 한다)**

| 뺀 것 | 왜 | 언제 |
|---|---|---|
| **LLM 답변** | 시연 대본이 정형 1개라 이득이 안 드러나고, **첫 소리까지 5초**(§10.46)가 짧은 영상에서 치명적이다 | 제출 후 (B 갈래) |
| **openWakeWord 커스텀 호출어** | 새 모델 학습·검증을 이틀 안에 넣는 위험 | 제출 후 |
| **경고 안내 음성** | FSM 연동이 필요해 **GUI 를 건드린다** | 별도 과제 |
| 다화자·소음 환경·세션 반복 | 측정 갈래이지 구현 갈래가 아니다 | — |

## 3. 구조 — GUI 를 **0줄** 바꾸지 않는다

```
[글라스 ESP32-S3]  ── 무선 1개 ──→ (붙은 AP) ──→ [파이1]
   카메라 ── TCP 8888 ──→  safety_console  (기존 그대로)
                                  └ wait_tool 중 1초마다 → /dev/shm/sop_tool/resp.json
   마이크 ── TCP 8889 ──→  voice_assistant.py  (신규 · 별도 프로세스)
   스피커 ←─ TCP 8890 ──     VAD → STT → 호출어/의도 → 미리 만든 wav
   띠링   ←─ 명령 1바이트 ─   (펌웨어 내장 톤)
```

🔑 **음성비서는 GUI 와 완전히 분리된 프로세스다.** 공구 정보는 `tool_worker` 가 이미 쓰고 있는 `resp.json` 을 **읽기만** 한다. 한쪽이 죽어도 다른 쪽이 안 죽는다.

🔴 **ESP32 의 WiFi 는 하나다** — 카메라와 오디오가 경로를 따로 고를 수 없다. **같은 AP·같은 IP, 포트만 다르다.**

## 4. 네트워크 — 「ESP32 통신 경로 재설계」와의 관계

그 설계(`2026-09-06-esp32-통신경로-design.md`)는 **아직 구현 전**이고, 우리는 그 결과를 **따라가기만** 한다.

| 항목 | 우리 처리 |
|---|---|
| 접속 주소 | 🔴 **mDNS 쓰지 않는다**(그쪽 §6-②가 채택 철회). **`Demo/.camera_ip` 를 매번 읽는다** — 카메라와 같은 주소이므로 별도 관리가 없다 |
| SSID·우선순위 | **우리가 안 건드린다.** 우리 스케치도 `wifi_credentials.h` 를 **심볼릭 링크**로 쓰므로 그쪽 변경이 자동 반영된다 |
| 폴백 | iptime(1순위) → 폰(2순위) → 파이1 AP(3순위) 어디로 가도 **IP 를 파일에서 읽으므로 그대로 동작**한다 |
| 도달성 | 오디오는 카메라와 같은 링크라 **그쪽 G3(무선↔유선 도달)가 통과하면 자동으로 보장**된다. 별도 관문 불필요 |

⚠️ **오늘 시점 실제 경로는 `Eung Min`(폰)** 이다 — iptime 전환이 아직 안 됐다. 코드 변경 없이 나중에 따라간다.

🔴 **두 과제가 같은 HW 3종과 같은 펌웨어를 쓴다.** 스케치가 갈라져 drift 하지 않도록, 우리 합본은 **카메라 부분을 손대지 않고 오디오만 덧붙이고 추가분을 주석으로 표시**한다(9/4 `cam_audio_batt_test` 와 같은 방식). 통신경로 과제가 카메라 쪽을 고치면 **그 diff 만 옮긴다.**

## 5. 펌웨어 — `camera_stream_tcp` + 오디오(무선)

기존 카메라 코드는 **한 줄도 바꾸지 않는다.** 덧붙이는 것:

1. **TCP 8889 — 마이크 업링크**(단방향 스트림). 16kHz·16bit·모노 = 32KB/s.
2. **TCP 8890 — 명령·스피커**. 🔑 **기존 오디오 다리 프로토콜(`W`/`P`/`R`/`D`)을 그대로** 쓴다. 전송 계층만 `Serial` → `WiFiClient` 로 바꾼다 — 설계가 `Stream` 으로 추상화해 둔 자리다(§10.51-(1)).
3. **내장 「띠링」 톤** — 명령 1바이트로 즉시 재생. wav 를 보내면 0.3초가 더 붙는데, **호출 응답은 즉각적이어야** 한다.

🔴 **왜 포트를 둘로 나누나** — 상시 업링크와 요청-응답 프로토콜을 한 연결에 섞으면 파싱이 깨진다.

🔴 **PDM 은 DC 오프셋(1000~1600)을 함께 낸다** — 빼지 않으면 STT 가 못 알아듣는다(2026-08-26 실측).

## 6. 왜 오디오도 TCP 인가

통일하려는 것이 아니라 **성격이 맞아서**다.

| | 일반 실시간 음성 | 우리 |
|---|---|---|
| 지연 요구 | 수십 ms | **초 단위**(말이 끝난 뒤 STT) |
| 재생 | 흘러오는 대로 | 🔑 **"받아놓고 재생"** — 설계 §8.2 확정 |
| 손실 영향 | 잠깐 지직 | 🔴 **STT 가 단어를 틀리게 받아쓴다** |

게다가 **검증된 프로토콜이 이미 있다**(체크섬 왕복·흐름 제어·226KB/s). UDP 로 가면 순서·손실·MTU 분할을 처음부터 다시 만들어야 한다. 대역은 마이크 32 + 스피커 43KB/s = **링크의 약 1%** 라 제약이 아니다.

⚠️ **TCP 의 대가 하나는 대비한다** — 링크가 나빠지면 재전송으로 오디오가 뒤로 밀린다. → **업링크는 「최신 우선」**: 파이가 밀린 오디오를 발견하면 **오래된 것을 버린다**(카메라의 `CAMERA_GRAB_LATEST` 와 같은 처방).

## 7. 파이 음성 데몬 — `Rpi5/Demo/voice_assistant.py` (신규 1파일)

```
오디오 수신 → DC 오프셋 제거 → 에너지 VAD → 발화 구간만 STT
   ├ 「가디언」 계열이 있으면 → 띠링 명령 + 청취 상태(8초 타임아웃)
   └ 청취 중 의도 매칭 → resp.json 조회 → 답변 wav 전송·재생
```

- 🔑 **실행 파이썬은 `~/env/tts/.venv`** (3.13, `sherpa-onnx` 1.13.7). `tool_worker` 가 `~/env/rfenv` 를 쓰는 것과 같은 방식이다. `Demo/config.py` 는 `os` 만 import 하므로 어느 venv 에서도 읽을 수 있다.
- **STT 스레드는 2개** — 4개면 Hailo·MediaPipe 와 CPU 를 다툰다.
- **핫워드 가중치 3.0** 적용(§10.52) — 도메인 용어 7/9.
- 🔑 **호출어 허용 목록 = `가디언 · 가디건 · 가디얀 · 가디현`** — §10.51 에서 실제로 관측된 오인식을 그대로 넣는다. 인식률 3/4 → 사실상 4/4.
- 🔑 **한 문장 발화도 받는다** — *"가디언, 앞에 보이는 게 뭐야?"* 를 한 번에 말해도 동작한다. **상태기계가 어긋났을 때의 폴백**이라 촬영 중 재시도를 줄인다.

## 8. 답변 — 미리 합성해 둔다

템플릿이라 **문장이 유한하다**(공구 3종 + 없음 + 단계 아님 = 5개).

| 상황 | 문장 |
|---|---|
| `driver` | 앞에 드라이버가 보입니다. |
| `wrench` | 앞에 렌치가 보입니다. |
| `pliers` | 앞에 플라이어가 보입니다. |
| 검출 0개 | 지금은 공구가 보이지 않습니다. |
| `wait_tool` 아님 | 지금은 공구를 확인하는 단계가 아닙니다. |

**미리 wav 로 만들어 두면** ①응답이 0.4초 빨라지고 ②🔑 **명료도를 미리 들어보고 나쁘면 다시 만들 수 있다** — ⛔ 미판정으로 남은 §10.49 위험을 시연 범위에서만 덮는다. ③런타임 TTS 를 아예 안 띄워도 되어 메모리·CPU 가 빈다.

⚠️ **이것은 「유연한 LLM 답변」 방향을 바꾸는 것이 아니다.** A 안에서만 성립하는 최적화이고, B 로 갈 때 런타임 TTS 로 되돌린다.

🔴 **공구 추론은 `wait_tool` 서브 작업 동안에만 돈다**(`camera_thread.py:242`). 그래서 **시연 대본을 공구 지참 단계에 맞춘다.** 다른 단계에서 물으면 위 표의 마지막 줄로 답한다 — **모르는 것을 지어내지 않는다.**

## 10. 거부한 대안

| 대안 | 왜 안 골랐나 |
|---|---|
| **두 보드로 분리**(카메라 / 오디오) | 검증 위험은 낮지만 **실제 제품 구성과 다르다**(사용자 판단 2026-09-06) |

| 음성 데몬이 카메라 프레임을 따로 받아 자체 추론 | 🔴 **카메라 TCP 는 클라이언트 1개만** 받는다(새 연결이 이전 것을 닫는다). 펌웨어를 더 뜯어야 하고 대역이 2배 |

| 오디오 UDP | §6 — 우리 오디오는 지연 민감이 아니고 손실에 약하다 |

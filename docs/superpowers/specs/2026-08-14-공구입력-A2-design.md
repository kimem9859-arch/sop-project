## 1. 무엇이 막혀 있나

`SubTask.can_advance` 는 **시간 AND 공구**다. 그런데 `SubTask.set_tool()` 을 **부르는 코드가 하나도 없다**. 그래서 2단계 「N2 퍼지」에서 「다음 단계 진행」이 **정상 경로로는 영원히 켜지지 않는다.**

`recipe.json` 의 2단계는 아직 `spanner` 를 요구하는데 `tool_v3` 의 클래스는 `driver`·`wrench`·`pliers` 다 — **키가 어긋나 있다.**

## 3. 구조

```
[GUI 프로세스 — 시스템 파이썬]              [워커 프로세스 — rfenv 파이썬]
                                            tool_worker.py
CameraThread._process_frame                   · tool_v3.pt 로드 (기동 시 1회)
  └ 스캔 켜짐 + 1초 경과 →                    · req 폴링 → 추론 → resp 기록
      tool_gate.request(frame, 손끝, 손보임) ──jpg──▶
                                      ◀──json──  {"seq":N, "dets":[{cls,score,box}...]}
  └ tool_signal.emit(판정결과)
       │
SafetyConsole._on_tool
  └ tool_state 로 3마디 판정 → SubTask.set_tool()
  └ _update_sub_view()
```

**주고받는 곳** = `/dev/shm/sop_tool/` (메모리 위 파일 — SD카드를 쓰지 않는다)
GUI 가 `req_<seq>.jpg`, 워커가 `resp.json`(같은 `seq` 포함). **seq 가 어긋나면 GUI 가 버린다** — 지난 프레임 결과를 잘못 쓰는 것을 막는다. 초당 1회라 소켓·재접속·프로토콜이 통째로 불필요하다.

**워커 수명** — GUI 시작 시 함께 띄우고(모델 로딩 수 초) 종료 시 내린다.
🔴 **워커가 못 뜨면**(rfenv·모델 없음) `hand_tracker` 처럼 **조용히 비활성**된다. 단 **로그에 눈에 띄게 남긴다** — 이 경우 2단계 게이트가 영영 안 열리므로 조용히 넘어가면 원인을 못 찾는다.

## 4. 판정 규칙

### 4.1 언제 스캔하나

`wait_tool` 서브 작업 **시작 시 켜고, 「다음 단계 진행」 시 끈다.** 30초는 제한 시간이 아니라 **최소 대기 시간**이다 — 시간이 다 차도 공구를 안 넣었으면 서브 작업은 계속 대기하고 스캔도 계속 돈다.

**주기 = 1초 1회** (추론 약 0.5초의 2배 여유).

### 4.2 두 마디 (2026-08-16 개정)

```
① 찾기  ─ 아직 요구 공구를 쥐지 않음
   │       (손끝이 요구 공구 박스 안에 들어옴)
   ▼
② 쥠    ─ 🔒 확정 = 완료. 「다음 단계 진행」은 시간까지 차면 열린다
           (한 번 확정되면 유지 — 되돌아가지 않는다)
```

⚠️ **유지는 선택이 아니라 필수다.** 공구를 쥐고 「다음 단계 진행」을 누르러 가는
동안 손끝은 공구 박스를 벗어난다. 매 프레임 재판정하면 완료가 풀려 버튼을 누를
수 없다. 대신 **잘못 확정되면 서브 작업 리셋으로만 복구된다.**

### 4.3 ① → ② 쥠 판정

손끝 좌표가 어느 공구 박스 안에 있는가로 본다. 버튼의 `zone_at_point` 와 같은 원리이되 **링/안쪽 2단계 구분 없이 박스 안이면 쥔 것**으로 단순화한다.

| 손끝이 닿은 곳 | 판정 |
|---|---|
| 요구 공구 박스 | ② 로 진행 = **완료**(`set_tool(want_tool)`) |
| 다른 공구 박스 | 🔴 "다른 공구입니다" 경고 (`SubTask.wrong_tool`) |
| 아무 박스도 아님 | ① 유지 |

🔑 **화면에 3종이 다 보이는 것이 정상이다.** 종류별 1개씩이 시나리오이고, 같은 클래스가 둘 잡히면 그것은 오분류다. **"보이는 것 중 최고 점수" 규칙은 폐기했다** — 판정 대상은 보이는 것이 아니라 **쥔 것**이다.

### 4.4 ⛔ 「넣음」 판정 — **폐기됨 (2026-08-16). 다시 꺼내지 말 것**

종전 설계는 **「손은 보이는데 요구 공구가 화면 어디에도 없다」가 연속 3회**면 지정 공간에 넣은 것으로 봤다. 손 미검출 시에는 세지 않아(일시정지) 고개를 돌려도 오완료가 나지 않게 했다.

🔴 **실HW 검증에서 오완료가 실제로 발생했다**(통합문서 §10.44-(3)). **손이 사라지는 쪽은 설계대로 정확히 보류됐다** — 무너진 것은 다른 축이다. **쥔 공구를 모델이 놓친 프레임**이 「없음」으로 세어져 완료가 났다.

```
설계 가정:  손 보임 + 공구 안 보임  =  공구를 넣었다
실제 상황:  손 보임 + 공구를 못 잡음 =  아직 쥐고 있는데 오판
```

🔑 **근본 문제는 부재를 증거로 쓴 것이다.** 존재는 검출로 확인되지만, 부재는 "정말 없다"와 "못 봤다"가 구별되지 않는다. 손을 증인으로 세워 **카메라가 그 자리를 보고 있다**는 것까지는 담보할 수 있어도, **모델이 그 공구를 잡을 수 있다**는 것은 담보할 수 없다. 검출률이 100%가 아닌 한 이 판정은 성립하지 않는다.

⚠️ **임계 조정으로 고칠 수 없음이 측정으로 확인됐다** — 미검출 프레임의 일부는 `conf` 를 0.40 까지 낮춰도 안 잡힌다(§10.44-(5)).

**덤으로 얻은 것** — 「지정 공간에 넣었다」의 판정 기준을 정할 필요가 사라졌다. 관통 구멍·소실 여부·손 자세를 따지던 조건이 전부 없어졌다.

🔴 **되살리려면** 부재가 아닌 근거가 필요하다(예: 콘솔 구멍 자체를 클래스로 학습해 **공구가 그 안에 들어간 것을 검출**). 종전 방식 그대로는 안 된다.

### 4.5 `SubTask` 접합 — `set_tool()` 호출 시점을 옮긴다

`SubTask` 에는 "넣음" 개념이 없다. **로직을 고치지 않고 부르는 시점으로 맞춘다.**

| 시점 | 호출 | 결과 |
|---|---|---|
| 아무것도 안 쥠 | `set_tool(None)` | 경고 없음, 게이트 닫힘 |
| 오답 공구를 쥠 | `set_tool("driver")` (요구가 렌치일 때) | `wrong_tool` → 경고 배너 |
| **정답 공구를 쥠** | **`set_tool("wrench")`** | `tool_ok` → 시간까지 찼으면 게이트 열림 |

⚠️ `SubTask._tool` 의 의미가 **"지금 놓여 있는 공구"(원래) → "지정 공간에 넣은 공구"(2026-08-14) → "손으로 쥔 공구"(2026-08-16)** 로 바뀌었다. `sub_task.py` 의 주석을 이에 맞게 고친다(**로직은 두 번 다 그대로**).

### 4.6 추론 지연 처리

추론에 약 0.5초가 걸려 결과가 돌아왔을 때의 손 위치는 이미 다르다.
→ **요청 시점의 손끝 좌표와 「손이 보였는지」를 함께 기억**해 두고, 결과가 오면 **그 시점 값과 짝지어** 판정한다. 지금 손 위치와 1초 전 공구 박스를 섞지 않는다.

### 4.7 임계 (`config.py` 신설)

| 상수 | 값 | 근거 |
|---|---|---|
| `TOOL_CONF` | 0.65 | §10.42 에서 3종이 잘 잡힌 구간 |
| `TOOL_SCAN_INTERVAL_SEC` | 1.0 | 추론 약 0.5초의 2배 여유 |
| ~~`TOOL_PLACED_COUNT`~~ | ~~3~~ | ⛔ **2026-08-16 삭제** — §4.4 폐기로 셀 것이 없어졌다 |

🔑 **쥠은 1회 스캔으로 즉시 확정한다**(연속 확인 없음, 2026-08-16 사용자 결정). 실HW 검증에서 쥠 오확정은 관측되지 않았고, 반응 속도를 우선했다. 배경 오검출이 손과 겹쳐 오확정이 나기 시작하면 그때 연속 확인을 넣는다.

`TOOL_CONF` 는 버튼의 `YOLO_CONF_HIGH` 와 값이 같지만 **따로 둔다** — 목적이 달라, 묶으면 한쪽을 조정할 때 다른 쪽이 딸려간다(도구가 config 를 안 따라 네 번 물린 전례의 반대 축).

## 9. 남는 위험

> 🔑 **2026-08-16 개정으로 종전 위험 3건이 사라졌다** — 전부 §4.4 「넣음」 판정에 딸린 것이었다(쥔 채 가려져 오완료 / 손 자세에 따라 판정이 빨라짐 / 넣은 뒤 손을 치우면 완료 지연). 그중 첫 번째가 실제로 발생해 이 개정을 불렀다(§10.44).

- 🔴 **공구를 쥐지 않고 손이 그 위를 지나가기만 해도 확정된다.** 손끝이 박스 안이라는 것과 쥐었다는 것은 다르다. 시연 절차로 완화한다.
- 🔴 **잘못 확정되면 되돌릴 수 없다** — 완료는 유지되므로 서브 작업 리셋으로만 복구된다(§4.2).
- ⚠️ **배경 오검출이 그대로 남아 있다**(§10.42-(2)(4) — 키보드→`wrench` 0.79 등). 요구 공구와 같은 클래스로 오검출된 박스에 손끝이 들어가면 **쥐지 않았는데 완료**될 수 있다. 개정 전에는 이 오검출이 「완료 지연」 방향이었으나, 이제 **오완료 방향으로 바뀌었다** — 배경 오검출의 위험도가 올라간 것은 이 개정의 대가다(§10.43 네거티브 보강의 재평가 근거).
- ⚠️ **요구 공구를 아예 못 잡으면 완료가 나지 않는다**(오완료가 아니라 진행 불가). §10.44 에서 확인된 미검출 조건(화면 가장자리·작음·손에 가림)에서는 공구를 **카메라 중앙에 크게** 보여줘야 한다 — 시연 절차에 반영한다.

## 1. 실행 순서 — 재플래시 횟수를 최소화한다

펌웨어를 굽는 것이 이 작업에서 **가장 비싼 단위**다(USB 연결·빌드·재부팅·WiFi 재접속). 따라서 **한 번 구울 때 최대한 많은 항목을 관찰**하도록 묶는다.

| 차수 | 하는 일 | 판정되는 항목 | HW 필요 |
|---|---|---|---|
| **0차** | 계측만 넣은 펌웨어 1회 굽기 + 파이 수신 로그 추가 → **30초 관찰** | **P-08 · P-03 · P-15**, 그리고 **P-01의 판정 근거** | ✅ |
| **1차** | 0차 결과를 보고 **1인자만** 바꿔 재측정(예: `fb_count`) | **P-01** | ✅ |
| **2차** | 운용 중 AP를 끊었다 붙이며 관찰 | **P-09 · P-10 · P-04 · P-14** | ✅ |
| **상시** | 코드 확인만으로 끝나는 것 | **P-02 · P-06 · P-07 · P-13 · P-16 · P-17** | ❌ 이미 확정 |

> ⚠️ **0차의 "계측 추가"는 수정이 아니다.** 동작을 바꾸지 않고 값을 찍기만 한다. 판정 전에 동작을 고치면 무엇이 효과를 냈는지 갈라낼 수 없다 — CLAUDE.md 「임계 효과는 임계를 실제로 바꿔가며 파이프라인 그대로 측정한다」.

### 0차에서 찍을 값 (한 번에 전부)

**ESP32 측**
- 프레임당 JPEG 바이트 (`fb->len`) — 평균·최소·최대
- `esp_camera_fb_get()` 소요 ms / `send()` 소요 ms — 구간 분리
- `send()` 반환값이 요청보다 작은 횟수 (`partial` 카운터)
- `xQueueSend` 실패 횟수 (= 큐 탈락으로 버린 프레임 수)

**파이 측**
- 프레임 도착 간격 ms
- `_latest_raw` 덮어쓰기 횟수 (= 수신했으나 처리 못 하고 버린 프레임 수)
- 재연결 발생 시각·횟수

이 다섯 줄이 A군 4건과 P-03·P-15의 판정을 **동시에** 끝낸다.

## 2. 🔴 계측 선행 — P-08이 다른 판정의 전제다

**프레임 바이트 수를 모르면 아무것도 판정할 수 없다.**

- P-03(부분 전송)은 "프레임이 `SO_SNDBUF` 32KB를 넘는가"에 달려 있다.
- P-01(`fb_count`)은 전송 시간을 알아야 캡처 시간과 분리된다.
- 화질 정책(JPEG 품질·해상도)은 "품질을 올리면 대역폭이 얼마나 느는가"를 모르면 정할 수 없다.
- 통합문서 §10.6의 **"TCP 경로 병목은 하드웨어 한계이며 소프트웨어 최적화로 해결 불가"** 라는 판정 자체가 이 값 없이 내려졌다.

→ **P-08을 가장 먼저 잰다.** 다른 순서는 없다.

#### P-01 🟡 `fb_count = 1`이라 캡처와 전송이 직렬로 돈다

| 구분 | 내용 |
|---|---|
| **증상 예상** | 코어를 0/1로 나눠도 FPS가 오르지 않는다. 캡처 시간 + 전송 시간의 **합**이 프레임 주기가 된다 |
| **근거** | `camera_stream_tcp.ino:258` — `config.fb_count = 1`. 프레임버퍼가 하나뿐이라 `sendTask`가 `esp_camera_fb_return()`을 부를 때까지 `captureTask`의 `esp_camera_fb_get()`이 막힌다. 코어 분리(`.ino:264-266`)에도 불구하고 파이프라인이 성립하지 않는다. 캡처 ~40ms + 전송 ~40ms ≈ 80ms = 12.5fps로, §10.11의 실측 12.5와 맞는다 |
| **확신도** | 🟡 가설 — **구조는 확정, 시간 배분은 미측정**. 자릿수가 맞는 것이 우연일 수 있다 |
| **영향** | NFR-1(15fps) 미달의 주원인일 가능성. FPS는 곧 허용 눌림 속도라 감지 성능에 직결(통합문서 §10.29⑥) |
| **✅ 확인 절차** | 1. 0차 계측으로 캡처 ms·전송 ms를 분리해 얻는다<br>2. 두 값의 **합**이 프레임 주기와 일치하는지 본다<br>3. 1차에서 `fb_count = 2`로만 바꿔 재측정(PSRAM 사용 중이라 메모리 여유 있음) |
| **판정 기준** | 캡처+전송 합 ≈ 프레임 주기(±10%)이면 직렬 확정 / `fb_count=2`에서 FPS가 오르면 원인 확정 · 안 오르면 **기각**하고 다른 원인을 찾는다 |
| **예상 해결 결과** | 직렬이 병렬로 바뀌면 프레임 주기가 `캡처+전송` → `max(캡처, 전송)`이 된다. 두 값이 비슷하다면 산술적으로 **약 2배**가 되나, 실제로는 WiFi 편차·PSRAM 대역·센서 상한에 걸려 그보다 낮게 착지할 것으로 본다. **NFR-1(15fps) 도달 가능성이 실재하는 유일한 항목**이다. 다만 이 수치는 어디까지나 산수이며, 측정 없이 인용해서는 안 된다 |

| 구분 | 내용 |
|---|---|
| **증상 예상** | 대역폭이 병목인지 아닌지 **판단할 방법이 없다** |
| **근거** | `bench_detector.py`·`camera_thread.py`·펌웨어 전체에 프레임 크기 로깅 0건(`grep`). raw 세션 43개의 `manifest.json`에도 없다 |

#### P-09 🔴 WiFi가 끊기면 영구 먹통이 된다

| 구분 | 내용 |
|---|---|
| **증상 예상** | 운용 중 AP가 끊기거나 재부팅되면 **ESP32는 스스로 복구하지 못한다.** 시리얼에 `WiFi=NG`만 5초마다 찍히고, 사람이 RESET 버튼을 눌러야 살아난다 |
| **근거** | `.ino:267` — `connectWiFiByPriority()`가 `setup()`에서 **단 한 번** 호출된다. `loop()`(`.ino:282~`)는 `RESET_WIFI` 명령 처리와 상태 출력만 하고 **재연결 로직이 없다** |
| **확신도** | 🔴 확정 (코드에 재연결 경로가 존재하지 않음) |
| **영향** | 🔴 **이 문서에서 가장 위험한 항목.** 시연·발표 중 발생하면 복구에 물리적 접근이 필요하다. 글라스는 착용 상태이고 3D 외장이 씌워져 있어 RESET 버튼 접근이 쉽지 않다 |
| **✅ 확인 절차** | 2차: ①정상 스트리밍 확인 → ②AP(핫스팟)를 끈다 → ③30초 대기 → ④AP를 다시 켠다 → ⑤시리얼과 파이 로그를 관찰 |
| **판정 기준** | AP 복구 후 **60초 안에 스트림이 자동 재개되면 기각** / 재개되지 않으면 확정 |
| **예상 해결 결과** | `loop()`에서 `WiFi.status()`를 주기 점검해 끊기면 `connectWiFiByPriority()`를 다시 부르는 것으로 해결된다(수십 줄). 해결되면 **AP 재부팅·전파 음영·장소 이동을 사람 개입 없이 넘긴다.** 파이 쪽 재연결(3초 주기 무한 재시도)이 이미 있으므로, ESP32만 복구되면 **양쪽이 알아서 다시 붙는다.** 시연 안정성에서 이 문서 전체를 통틀어 **가장 값이 큰 수정**으로 본다 |

#### P-03 🟡 `send()`의 부분 전송을 오류로 처리한다

| 구분 | 내용 |
|---|---|
| **증상 예상** | 정상 상황인데도 연결이 끊기고 재연결이 반복된다. FPS가 들쭉날쭉해진다 |
| **근거** | `.ino:91`·`.ino:98` — `send()` 반환값이 요청 바이트보다 작으면 즉시 `close()`. 그런데 `.ino:129-130`에서 `SO_SNDBUF`를 **32,768바이트**로 잡아 두었고, VGA q15 프레임은 25~45KB로 추정돼 **버퍼를 넘길 수 있다**. lwIP 블로킹 소켓이 부분 전송을 반환하는지가 관건 |
| **확신도** | 🟡 가설 — 부분 전송이 실제로 발생하는지 미확인 |
| **영향** | 발생한다면 **끊김의 숨은 원인**이자 FPS 저하 요인. 발생하지 않는다면 무해한 방어 코드 |
| **✅ 확인 절차** | 0차: `send()` 반환값 < 요청 바이트인 횟수를 카운터로 찍고 30초 관찰. 동시에 파이 쪽 재연결 로그 시각과 대조 |
| **판정 기준** | `partial` 1회 이상 = 확정 / 0회 = 기각 (단, 프레임 크기가 32KB를 넘지 않았다면 **조건 미달로 미판정**이지 기각이 아니다 — 품질을 올려 재시험) |
| **예상 해결 결과** | 부분 전송을 루프로 이어 보내도록 고치면(`while (sent < len)`) **끊김이 사라지고 재연결로 낭비되던 시간이 회수**된다. 부수적으로 **JPEG 품질을 올릴 여지가 생긴다** — 지금은 품질을 올리면 프레임이 커져 이 버그를 더 자주 밟게 되므로, 화질 개선의 **숨은 걸림돌**이기도 하다 |

#### P-04 🟡 `client_sock`에 경쟁 조건이 있다

## 4. 예상 해결 결과 — 종합

> ⚠️ 아래는 전부 **미측정 예상**이다. 어떤 항목도 "달성"·"개선됨"으로 인용해서는 안 된다.

### 4.1 무엇이 얼마나 나아지나 (예상)

| 영역 | 지금 | 관련 항목 | 예상되는 변화 |
|---|---|---|---|
| **FPS** | 11.0 (HOI 포함) · NFR-1 미달 | P-01·P-08·P-03 | P-01이 확정되고 `fb_count=2`가 통하면 **NFR-1(15fps) 도달 가능성이 실재**한다. 기각되면 FPS는 **하드웨어 교체 논의로 넘어간다**. 어느 쪽이든 **처음으로 근거 있는 판정**이 된다 |
| **끊김 복구** | WiFi 끊기면 수동 RESET | P-09·P-10·P-03 | 사람 개입 없이 자동 복구. 시연 중 사고 확률이 크게 줄어든다 |
| **끊김 인지** | 화면이 멈춘 채 그대로 | P-14 | 운영자가 "감지가 멈췄다"를 **즉시 안다**. 안전 오해 제거 |
| **IP 관리** | 장소 바뀌면 USB 연결 필요 | P-07·P-16·P-17 | mDNS가 동작한다면 **케이블 없이 자동 접속** |
| **원인 추적** | FPS가 낮은 이유를 못 댄다 | P-15·P-08·P-13 | 촬영→전송→수신→처리 4단 손실표로 **병목 위치가 특정**된다 |
| **화질 실험** | 인자 하나 바꾸려면 재플래시 | P-06 | 한 번 굽고 여러 조건 측정 → **화질↔속도 곡선**을 실제로 그릴 수 있다 |

### 4.2 서로 맞물리는 관계 — 따로 고칠 필요가 없는 것들

- **P-13 + P-15**: 헤더에 **시퀀스 번호** 하나를 넣으면 어긋남 검출과 드롭 계수가 **동시에** 해결된다.
- **P-07 → P-16 · P-17**: mDNS가 동작하면 IP 관련 나머지 두 건이 **자동 소멸**한다. 그래서 P-07을 먼저 판정한다.
- **P-09 → P-04 · P-10**: 재연결이 드물어지면 경쟁 조건을 밟을 기회도, 워치독이 발동할 일도 함께 줄어든다.
- **P-03 → 화질**: 부분 전송을 고쳐야 **JPEG 품질을 올릴 여지**가 생긴다. 화질 논의의 선행 조건이다.
- **P-01 + P-02**: 한 몸이다. `fb_count`를 정하면 큐 크기도 따라 정해진다.

즉 **14건이 아니라 사실상 6~7개의 덩어리**다.

### 4.3 🔴 해결되지 않는 것 — 기대를 미리 깎아 둔다

- **카메라 화질(선명도 16.3)은 이 목록의 어떤 항목으로도 개선되지 않는다.** OV3660 센서와 렌즈의 문제이며, JPEG 품질 상향은 압축 손실만 줄일 뿐이다.
- **손 검출 실패율(팜 미검출 21.8% · 랜드마크 저score 27.5%, §10.21)** 은 통신 문제가 아니다. FPS가 올라도 이 비율 자체는 바뀌지 않는다.
- **FPS가 올라도 사전 감지율이 그만큼 오른다는 보장은 없다.** §10.29⑥은 FPS가 "허용 눌림 속도"를 결정한다고 했을 뿐, 선형 관계를 말한 것이 아니다.
- **가장 촉박한 눌림(선행시간 min 0.02s, §10.21)** 은 FPS를 올려도 원리적으로 못 잡을 수 있다.

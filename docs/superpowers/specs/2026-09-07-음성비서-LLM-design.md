## 1. 왜 여는가 — 사용자 제기

> *"시연 영상으로는 LLM 없이도 가능한 기능으로 보여져. 같은 말을 하여도 다른 대답이 나와야 LLM 을 사용하여 AI 가 답한 것처럼 보일 것 같아."*

**맞는 지적이고, 실제로 그렇다.** A 갈래의 답변은 **6갈래 열거형 → 미리 합성한 wav 6개**다. 같은 공구를 보이면 **소리 파형까지 100% 같다.** 「녹음을 틀었다」는 인상은 착각이 아니라 사실 그대로다.

🔑 **다만 다양성만으로는 LLM 이 증명되지 않는다** — 템플릿 5개를 무작위로 골라도 「같은 말에 다른 대답」은 된다. 관객이 *"AI 가 답했다"* 고 믿는 지점은 **대본에 없는 질문에 답하는 것**이다. 그래서 이 설계의 목표는 **다양성이 아니라 범위**다.

## 2. 목표 / 비목표

**목표** — 작업 세션 상태에 근거한 자유 질의응답.

```
「가디언」 → 띠링 → 「이번 단계에 무슨 공구 필요해?」
                  → (사실 카드 + LLM) → 「2단계에 필요한 공구는 렌치입니다.」
```

받을 질문의 범위 (사용자 지정, §10.62-(7) 에서 재료 확인 완료)

| 질문 | 근거 |
|---|---|
| 지금 보이는 공구 | 실시간 검출(`resp.json`, 3초 신선도) |
| **이 단계에 필요한 공구** | `recipe.json` — **정적이라 어느 단계에서든 답한다** |
| 다음 입력 버튼 | `SafetyFSM.correct_roi` |
| 현재·다음 작업 단계명 | `SafetyFSM` + `recipe.json` |
| 작업 완료 후 결과 | `SessionStats.finish()` |

🔴 **「지금 보이는 공구」와 「이 단계에 필요한 공구」는 다른 것이다.** A 갈래는 이 둘을 구분하지 않았다. 전자만 `wait_tool` 동안에 매인다.

**비목표 (🔴 이번에 안 한다)**

| 뺀 것 | 왜 |
|---|---|
| **범위 무제한 응답** | §10.53-(4) 의 7유형이 그대로 노출된다. 심사용 영상에 한 번 나오면 증거로 남는다 |
| **의도 판정을 LLM 에게** | 지금 0ms 인 판정에 1.4초가 들어오고, 실HW 에서 접두 매칭으로 어렵게 안정화한 것(§10.61)을 되연다 |
| **토큰 스트리밍** | 사용자 결정(2026-09-06) 유지 |
| **2단 답변(즉답+보강)** | 고정 음성과 생성 음성이 이어 붙어 *"앞부분은 녹음이네"* 가 오히려 드러난다 |
| openWakeWord · 경고 안내 음성 | A 갈래 비목표 그대로 |

## 4. 구조 — 무엇이 새로 생기나

```
                       ┌──────────────── 신규 ────────────────┐
ESP32 마이크 ─TCP─▶ voice_assistant.py                        │
                     ① find_utterance   VAD          (그대로) │
                     ② transcribe       STT          (그대로) │
                     ③ is_wake          호출어       (그대로) │
                     ④ 사실 카드 수집 ◀── /dev/shm/sop_tool/resp.json  (기존)
                     │                ◀── /dev/shm/sop_state/state.json 🆕
                     │                ◀── recipe.json                  (기존)
                     ⑤ LLM 호출  ──HTTP──▶ pi2 ollama gemma4:e2b  🆕
                     ⑥ 재생 직전 검산                             🆕
                     ⑦ 런타임 TTS(sherpa)  ← A 갈래의 사전합성을 되돌림
                     ⑧ Speaker.send      전송        (그대로)
                       └──────────────────────────────────────┘
                                    ──TCP──▶ ESP32 스피커
```

**①②③⑧ 은 손대지 않는다.** 실HW 에서 통과한 부분이다(§10.61).

## 5. 사실 카드

질문을 알아들은 순간, 세 곳에서 모아 만든다.

```
[사실]
작업: PECVD 정비(PM) 시퀀스 · 전체 4단계 · 진행 중 (경과 3분 12초)
현재 진행 중인 단계: 2단계 「펌프/퍼지」 · 지금 눌러야 할 버튼 B2
상태: 정상 (경고 없음, 차단 없음)
그 다음에 올 단계: 3단계 「전극 냉각」 · 버튼 B3
2단계의 서브작업: N2 퍼지 10초 · 2단계에 필요한 공구 = 렌치
카메라에 지금 보이는 공구: 렌치 (신뢰도 0.44)
지금까지: 완료 1단계 · 순서 위반 0회 · 차단 0회
```

**🔴 라벨 규칙 — 축약하지 않는다.**

`현재:` / `다음:` 으로 줄여 썼을 때 모델이 **다음 단계를 현재로 답했다**(§10.62-(6)). 카드 내용은 같았고 **라벨 문구만** 달랐다. 그래서:

- `현재 진행 중인 단계:` · `그 다음에 올 단계:` 처럼 **끝까지 풀어 쓴다**
- 항목마다 **어느 단계의 것인지 숫자를 붙인다**(`2단계의 서브작업:`)
- **공구는 두 줄로 나눈다** — `2단계에 필요한 공구`(정적) 와 `카메라에 지금 보이는 공구`(실시간)

**부재의 표기** — 없는 것은 **빼지 않고 없다고 적는다.**

| 상황 | 카드에 적는 것 |
|---|---|
| `resp.json` 이 3초보다 낡음 | `카메라에 지금 보이는 공구: 확인 중이 아님 (이 단계에서는 공구를 인식하지 않는다)` |
| 상태 파일 없음(GUI 미기동) | `작업: 시작되지 않음` |
| 서브작업 없는 단계 | `4단계의 서브작업: 없음` |

🔑 **비면 LLM 이 지어낸다.** §10.53-(4) 유형 ①②⑤ 는 전부 **「모른다」고 말하지 못하는 문제**다. 부재를 명시하는 것이 그 대응이다(`tool_state.py` 와 같은 원칙).

## 6. 프롬프트 계약

시스템 프롬프트는 **고정**이다. 🔴 **바꾸면 ollama 가 모델을 다시 올린다**(§10.62-(4) 측정 함정).

```
너는 반도체 PECVD 장비 정비(PM) 작업자를 돕는 음성 비서다.
작업자는 장갑을 끼고 화면을 보지 않는다. 반드시 한국어로 답한다.

[규칙]
- 아래 [사실] 에 적힌 것에만 근거해 답한다.
- [사실] 에 없는 것을 물으면 "확인할 수 없습니다" 라고 말한다.
- 수치·부품명·상태를 추측하거나 지어내지 않는다.
- 작업을 진행해도 되는지 묻는 질문에는 스스로 허가하지 않는다.
- 두 문장을 넘기지 않는다.
```

**규칙마다 막는 유형이 있다**(§10.53-(4)).

| 규칙 | 막는 유형 | 확인 |
|---|---|---|
| 사실에만 근거 / 지어내지 않는다 | **① 수치 지어냄** · ② 모르는 상태를 안다고 함 | ✅ §10.62-(5) 「규정 토크」 → *"확인할 수 없습니다"* |
| 스스로 허가하지 않는다 | **⑤ 상태 모르면서 허가함** | ⏸ 미확인 — 관문 G3 |
| 두 문장을 넘기지 않는다 | **⑥ 묻지 않은 위험 행동 제안** | 🔴 풀었을 때 실제로 붙었다(§10.62-(4)) |

⚠️ **④(결론 맞고 이유 틀림)는 프롬프트로 못 막는다** — 카드 라벨(§5)이 대응이다.

## 7. 시간축 — 스냅샷 한 번, 재생 직전 검산

🔴 **LLM 이 5~7초를 먹으므로, 답이 나올 때 세상은 이미 바뀌어 있을 수 있다.**

```
t=0.0   발화 끝
t=0.14  STT 완료 → 질문 인정
        ★ 사실 카드 스냅샷 (여기 한 번)
t=0.2   ┌ LLM 호출 시작 (배경 스레드)
        └ 「확인 중」 wav 전송 ← 사람이 기다리는 줄 알게 한다
t≈2     「확인 중」 재생 끝 (LLM 은 계속 돈다)
t≈5~7   LLM 완료 → 런타임 TTS
        ★ 검산 — 변하는 항목만 다시 읽는다
t≈7     재생
```

🔴 **「확인 중」 재생과 LLM 호출은 반드시 겹쳐야 한다.** 명령 채널이 하나뿐이라(`Speaker`) 재생 완료를 기다리는 동안 메인 루프가 막힌다. **순서대로 하면 재생 2초가 지연에 그대로 더해진다.** LLM 호출을 배경 스레드로 먼저 띄우면 그 2초가 LLM 시간에 흡수된다.

🔴 **기존 `ack.wav`(「네, 말씀하세요」)를 쓰지 않는다.** 그것은 **호출에 대한 응답**이지 **생각 중 표시**가 아니다 — 질문을 이미 받은 뒤에 「말씀하세요」라고 하면 어긋난다. `make_answers.py` 에 **「확인 중」 문구를 새로 만든다**(예: *"확인해 보겠습니다."*).

**검산을 TTS 뒤에 두는 이유** — 재생에 가장 가까운 시점일수록 판단이 정확하다. TTS 0.6초를 버리게 되지만, **어긋난 답을 내보내는 것보다 싸다.**

**왜 「계속 만들기」가 아닌가** — LLM 은 스냅샷으로 이미 문장을 굳혔다. 뒤에 카드를 새로 만들어도 나올 말이 안 바뀐다. 새 카드로 다시 태우면 **또 5~7초가 가고 그 사이 또 바뀐다 — 끝나지 않는다.** 카드 읽기는 1ms 라 미리 만들 이득도 없다.

**검산 대상 — 변하는 것만**

| 항목 | 변화 주기 | 검산 |
|---|---|---|
| 카메라에 지금 보이는 공구 | **초 단위** | 🔴 필수 |
| 차단·경고 여부 | 이벤트 | 🔴 필수 |
| 현재 단계 | 버튼 누를 때 | ⚠️ 함께 본다 |
| 필요 공구·단계 이름(`recipe.json`) | 정적 | ✅ 불필요 |

**불일치 처리**

```
같다   → 생성 문장을 재생
다르다 → 🔑 생성 문장을 버리고, 새 상태에 맞는 고정 wav 로 답한다
```

LLM 을 다시 안 태우는 이유는 위와 같다. 고정 wav 는 0.4초라 어긋날 틈이 사실상 없다.
🔑 **이러면 A 갈래의 고정 wav 6개가 죽은 코드가 아니라 이 구조의 필수 부품이 된다.**

## 8. 상태 공개 — `/dev/shm/sop_state/state.json` (GUI 변경)

A 갈래의 *"GUI 를 0줄도 안 건드린다"* 는 여기서 **깨진다.** 상태 기반 질의응답을 하려면 GUI 가 상태를 내보내야 한다.

**`tool_worker` 방식을 그대로 베낀다** — 이미 검증된 패턴이다.

| | 방식 |
|---|---|
| 쓰는 쪽 | GUI(`safety_console`) — 상태가 바뀔 때만 `.tmp` 에 쓰고 `os.replace`(원자적 교체, `tool_gate.py:129-136` 과 같은 방법) |
| 읽는 쪽 | `voice_assistant` — **읽기만** 한다 |
| 파일 없을 때 | 🔑 **「작업 시작되지 않음」으로 동작한다** — GUI 없이도 음성비서가 그대로 돈다 |

담을 것 = 세션 여부·경과·현재 단계(번호·이름·버튼)·다음 단계·FSM 상태(정상/경고/차단)·완료 단계 수·위반·차단 횟수·(완주 시) `SessionStats.finish()` 요약.

🔴 **GUI 는 이 파일 쓰기가 실패해도 계속 돌아야 한다** — 음성비서 때문에 콘솔이 죽으면 본말전도다. 예외는 삼키고 로그만 남긴다.

## 9. 깨어남 규칙

```
「가디언」 → 띠링 (언제나 — 상태와 무관)
   ├─ 작업 시작 전  → 고정 wav 「아직 작업이 시작되지 않았습니다」  0.4초 · LLM 안 탐
   └─ 작업 중        → 사실 카드 + LLM                              5~7초
```

**호출어를 상시로 두는 근거** = §10.62-(1). 상시 부하는 코어 1개의 2.80% 이고, 무거운 STT 는 발화 때만 돈다.

**작업 전에 LLM 을 안 태우는 근거** — 카드가 비어 있어 **LLM 이 할 말 자체가 없다.** 5~7초를 기다릴 이유가 없고 없는 상태를 지어낼 위험만 생긴다(유형 ⑤).

⚠️ **깨어난 20초 창 안에서는 호출어 없이도 질문이 먹힌다**(A 갈래 설계 그대로). 실촬영에서 12발화 중 4건이 그 경로였다(§10.61). **LLM 에서는 그 4건이 각각 5~7초를 쓴다** — 계측에 남겨 다음 판단의 근거로 삼는다.

## 13. 거부한 대안

| 대안 | 왜 안 하나 |
|---|---|
| 시연 파이에서 LLM 구동 | e2b 3.9GB + PyTorch 공구워커 + Hailo + STT/TTS 가 7.9GB 를 나눠 쓴다. CPU 경쟁으로 **NFR-1(FPS)이 흔들린다.** 모델도 4.3GB 내려받아야 한다(§10.62-(8)) |
| 더 작은 모델로 지연 단축 | §10.53-(3) 이 닫은 길이다 — LFM2.5 는 품질 최하위·안전 X 4건/3명 |
| 답변 길이를 줄여 지연 관리 | **최소가 3.4초**라 아낄 것이 2~4초뿐이다(§10.62-(4)). 사용자 결정도 품질 우선 |
| 카드를 배경에서 계속 갱신 | LLM 이 이미 문장을 굳혔다(§7). 비용만 늘고 지연은 안 준다 |
| 템플릿 여러 개를 무작위 선택 | 「같은 말에 다른 대답」은 되지만 **대본 밖 질문을 못 받는다** — 목표가 다양성이 아니라 범위다(§1) |

## 3. 처리 2단계 (D13)

### 3.1 1단계 뒤에도 남는 막힘

- 한 장의 처리 = 받기(별도 스레드) → 풀기 → 방향 보정 → 버튼 추론 → 손 추론(손바닥 · 손 관절 두 번) → 추적 · 판정 → 그리기 → 화면으로. 처리 스레드 하나가 이 순서를 한 줄로 돈다.
- Hailo 추론 세 번(버튼 · 손바닥 · 손 관절)과 1초에 한 번 공구 추론이 **추론하는 동안 파이썬 자물쇠(GIL)를 쥔다** → 그동안 받기 스레드 · 화면 스레드가 멈춘다.
- 손 모델(blaze · 저장소 밖 `~/lab/hoi/blaze_app_python`)은 추론할 때마다 추론 통로(InferVStreams)를 **새로 만들고 닫는다** — 매 장 두 번.

### 3.2 2a — Hailo 호출을 InferModel 방식으로

- 새 모듈 `Demo/hailo_infer.py` — 공유 장치(`hailo_device`, 이미 ROUND_ROBIN 스케줄러)에서 모델 하나를 InferModel 로 올리고, 입출력 버퍼를 한 번 만들어 재사용한다. 호출 = 「이름 → 배열」 사전을 넣으면 「이름 → 배열」 사전을 돌려준다. 입력 UINT8 · 출력 FLOAT32(지금 방식과 같은 역양자화 값).
- 버튼 검출기 `detector.HailoDetector`(공구 모델도 이 클래스) — 스위치를 켜면 `hailo_infer` 로 추론한다. NMS 출력(클래스마다 「개수 + 상자 값」이 이어진 평평한 배열)을 풀어 **지금과 같은 상자 목록**을 만든다.
- 손 검출기 `hand_tracker` — blaze 소스는 고치지 않는다(저장소 밖). blaze 가 쓰는 추론 통로 자리를 같은 모양(`with … as p: p.infer(사전)`)의 대역으로 바꿔 끼운다. 대역은 `hailo_infer` 로 추론한다.
- 🔴 한 장치에 **network group 방식과 InferModel 방식을 섞지 않는다** — 스위치를 켜면 시연의 모든 모델(버튼 · 손바닥 · 손 관절 · 공구)이 InferModel 로 간다. 섞어 올려도 되는지는 확인하지 않았다.
- 관문(집 · 실제 Hailo · **확정 값**) — 녹화된 안경 원본으로 지금 방식과 새 방식의 출력을 비교한다: 버튼 상자 좌표 · 점수 · 손끝 좌표가 같아야 한다(점수는 소수점 6자리 안). 「같은 입력 → 같은 출력」이라 학교 값이 달라질 이유가 없다 — 학교에서는 같은 비교 도구를 그날 원본으로 한 번 더 돌릴 수 있다(§7).

### 3.3 2b — 처리를 두 단으로 겹침

- **앞단 스레드(새)** — 받은 바이트 → 풀기 → 방향 보정 → 「한 칸 우편함」에 넣는다. 우편함은 최신 한 장만 두고, 뒷단이 아직 안 꺼낸 장은 새 장으로 덮는다(지금 받기 스레드의 「최신 한 장」 규칙과 같다).
- **뒷단(지금의 처리 스레드)** — 우편함에서 꺼내 → 추론 · 추적 · 판정 · 그리기 · 화면으로.
- 각 장의 받은 시각 · 받은 누적 수 · 풀기 시간 · 보정 시간을 장과 함께 넘긴다 → **측정 기록 형식은 그대로**다(`frames.csv` 칸 뜻도 같음).
- 재연결 — 연결 세대 번호가 바뀌면 우편함을 비운다(끊기기 전 장을 새 연결에서 쓰지 않는다 · 지금 규칙과 같다). 종료 — 앞단 스레드를 멈추고 기다린다.
- 기대 — 한 장 간격이 「앞단 + 뒷단」에서 「둘 중 긴 쪽」으로 준다. 2a 가 없으면 추론 중 자물쇠 때문에 겹침이 작다 → **2b 는 2a 와 함께 켤 때 효과**를 본다.
- 관문 — (집 · 확정) 한 장씩 차례로 넣는 시험에서 두 단 경로의 판정 사건 · 상자가 한 줄 경로와 같다 · 재연결 · 종료 · 오류 장 처리 시험. (집 · 임시) 가짜 카메라로 처리 fps.

### 3.4 스위치와 비교 조합

| 스위치(환경변수) | 기본 | 켜면 |
|---|---|---|
| `SOP_INFER_MODEL` | 끔(`0`) | 2a |
| `SOP_PIPELINE2` | 끔(`0`) | 2b |

- 두 값을 `session.json` 「설정」과 세기 ④ 조건 줄에 남긴다(1단계 스위치와 같은 방식).
- 학교 비교 조합 — 1단계(지금 기본) / 1단계 + 2a / 1단계 + 2a + 2b. 각 2번씩 번갈아(세션 사이 편차가 크다 · 상위 설계).
- 환경변수를 손으로 치지 않게 **측정 실행기가 「처리 설정」을 번호로 묻는다**(Enter = 기본). 번호와 조합은 진행표(§9)에 있다.

### 3.5 이번 범위가 아닌 것

- fps 가 오르면 「프레임 수」로 정한 설정(`YOLO_MAX_MISS` 등)의 시간 뜻이 바뀐다 — 값은 바꾸지 않고 세기 결과에 같이 적는다. 다루는 곳 = 판정 기준 작업(상위 D1 순서).

## 4. 안경 펌웨어 손질 (D14 · D20 · D22)

### 4.1 바꿔 볼 것

| 후보 | 지금 | 바꿔 볼 값 | 기대 | 위험 |
|---|---|---|---|---|
| JPEG 품질(`jpeg_quality` · 숫자가 클수록 더 압축 · 화질 ↓) | 15 | 20 · 25 | 한 장이 작아져 보내는 시간이 짧아짐 → 받는 속도 ↑ | 검출이 나빠질 수 있음 |
| 사진 버퍼(`fb_count`) | 2 | 3 | 보내는 동안 찍은 장을 덜 버림 | 메모리 · 지연이 한 장 늘 수 있음 |

- 해상도(XGA)는 바꾸지 않는다 — 검출 입력과 보정 파일이 바뀐다(§12).

### 4.2 빌드 옵션(소스 하나)

- `arduino/glass_voice/glass_voice.ino` — 두 값을 「빌드 때 넘기지 않으면 지금 값」인 상수로 바꾼다(`GLASS_JPEG_QUALITY` 기본 15 · `GLASS_FB_COUNT` 기본 2).
- `arduino/flash_esp32.sh` — `--jpeg-quality N` · `--fb-count N` · `--build-only` 를 받는다. 옵션 없이 = 지금과 같은 펌웨어. `--build-only` = 컴파일만(보드 · 포트 없이 · 집에서 쓴다).
- 굽기 경로의 보호(시리얼번호로 보드 고르기 · 8MB 백업 + 그 자리 대조)는 지금 스크립트 그대로다.

### 4.3 집에서 할 것

- 변형 세 개(품질 20 · 품질 25 · 버퍼 3)를 `--build-only` 로 빌드해 컴파일이 되는지 확인한다(확정).
- 녹화된 안경 원본을 더 압축해 다시 저장하고 검출 결과를 비교한다 — **방향만 보는 임시 값**이다. 파이의 JPEG 압축과 카메라 칩 안의 압축은 품질 숫자의 뜻이 달라 같은 결과를 보장하지 않는다 → 결과와 상관없이 **학교 필수**(§7.4).

### 4.4 학교에서 할 것

- 순서 = 처리 비교(§3.4)를 지금 펌웨어로 끝낸다 → E1 · E2(원인 확인 · 1단계 계획 Task 6) → 변형을 하나씩 굽고 같은 장면에서 비교 → 결정 → (바꿨으면) 고른 처리 설정을 새 펌웨어로 한 번 더(2번).
- 같은 장면 비교 = 안경을 거치대에 고정(콘솔을 향함)하고 정해진 손 동작(버튼 위로 손 넣고 빼기 10번)을 하는 60초 · 측정 기록 켬. 볼 값 = 받은 fps(받은 누적 수 기준) · 한 장 크기 · 버튼 확정 비율 · 손끝 보인 비율.
- 채택 기준(Claude 제안 · 결정은 사용자 D22) — 받은 fps 가 2 이상 오르고 · 버튼 확정 비율과 손끝 보인 비율이 지금 펌웨어보다 2%p 넘게 떨어지지 않을 때.
- 되돌리기 — `flash_esp32.sh main`(옵션 없이) 또는 굽기 직전 백업 이미지 되쓰기(명령은 진행표 · 변수 대처표).

## 6. 카메라 → 파이 지연 측정 (상위 D12 · D19)

- 새 도구 `Demo/test/lamp_latency.py` — 시연을 끈 상태에서(카메라 · 인터락 연결을 이 도구가 쓴다):
  1. 인터락에 램프 명령 정상(RUN) ↔ 경고(WARN)를 번갈아 보낸다(1.5초 안팎 · 간격을 조금씩 흔들어 장 간격과 맞물리지 않게). 처음 6번은 램프 자리 찾기용, 그 뒤 24번이 측정.
  2. 같은 시간 안경 영상을 직접 받는다(받은 시각 기록).
  3. 처음 6번의 「켬 평균 장 − 끔 평균 장」에서 가장 많이 바뀐 덩어리를 램프 자리로 잡는다.
  4. 명령마다 그 자리 밝기가 절반 넘게 바뀐 첫 장을 찾아 「그 장을 받은 시각 − 명령 보낸 시각」을 낸다 → 중앙값 · 90% 값.
- 이 값에는 아두이노 처리 · 램프 켜짐 · 카메라 노출 · 압축 · 무선 · 받기가 모두 들어간다 → **위쪽 끝(상한) 값**이다. 명령 응답(ack) 시각을 같이 적어 아두이노 쪽 몫을 뺄 수 있게 한다.
- **대안(`--screen`)** — 램프가 안경 화면에 안 보이면 같은 도구가 콘솔 화면 전체를 검정 ↔ 흰색으로 바꿔 같은 방법으로 잰다. 값에 모니터 표시 지연이 섞인다고 결과에 적는다.
- 집 확인(도구 정확도 · 확정) — 가짜 카메라의 「램프 흉내」 모드(가짜 인터락 명령을 받으면 정한 지연 뒤 밝은 장면을 보냄)로 도구가 그 지연을 맞히는지 본다(허용 = 한 장 간격). **실제 지연 값은 집에서 없다 → 학교 필수.**

## 7. 집 리허설과 학교 짝 (D15 · D16)

### 7.1 가짜 장치와 같은 명령 원칙

- **가짜 카메라** `Demo/test/fake_camera.py` — 안경과 같은 형식(포트 8888 · 4바이트 길이 + JPEG)으로 녹화된 원본 폴더를 정한 속도(기본 19.5장/초)로 되풀이해 보낸다. 「램프 흉내」 모드(§6)를 가진다.
- **가짜 안경 소리** — 이미 있는 `Demo/test/fake_glass.py`(8889 마이크 · 8890 명령).
- **가짜 인터락** — 가상 시리얼(pty)로 인터락 아두이노처럼 명령에 응답한다(램프 도구 · 리허설용).
- **키 누름 흉내** — 시연의 시험 키(1~4 · E)를 리허설 스크립트가 대본 시각대로 넣는다.
- 🔑 **집과 학교의 차이는 입력 장치 주소뿐이다** — 카메라 주소를 환경변수 `SOP_CAMERA_HOST` 로 덮는다(없으면 지금처럼 `.camera_ip`). 실행기 · 시연 · 진행 도우미 · 세기 · 분석 도구 · 램프 도구는 집과 학교에서 **같은 파일 · 같은 인자**로 돈다. `.camera_ip` 파일은 리허설이 건드리지 않는다.

### 7.2 리허설 스크립트

- `Demo/test/rehearse.py` — 학교 절차를 하나씩 자동으로 돌리고 결과표 `~/lab/리허설/<시각>/결과.md` 를 쓴다. 집 측정은 **같은 것을 2번** 돌린다(흩어짐 확인).

| # | 학교 절차 | 집 리허설이 돌리는 것 | 집 값의 종류(§7.3) |
|---|---|---|---|
| R0 | 사전 점검 | 사전 점검 도구(§8.2)를 가짜 장치로 | 흐름 |
| R1 | ⑤음성 측정 | 실행기 → 시연 → 진행 도우미 → 가짜 안경 소리 → 세기 | 흐름(인식률은 학교 값) |
| R2 | 3판 판 1 재확인 | 같은 대본 · 같은 순서 | 흐름 |
| R3 | 처리 비교(1단계 · +2a · +2a+2b) | 처리 설정 번호마다 실행기 → 시연 60초 → 세기 ④ 조건 줄 · fps | 임시(fps) · 확정(2a 출력 동일 · 2b 사건 동일) |
| R4 | E1 · E2 | `cam_grab.py` 를 가짜 카메라에 | 흐름 |
| R5 | 펌웨어 | 변형 세 개 `--build-only` · 재압축 검출 비교 | 확정(빌드) · 임시(재압축) |
| R6 | 램프 지연 | 램프 흉내 + 가짜 인터락 · `--screen` 은 오프스크린 | 확정(도구 정확도) |
| R7 | 근거 측정 | 대본 · 안내 띠 · 분석 도구(10/11 세션 재현 포함) | 흐름 · 확정(분석 재현) |
| R8 | 되돌리기 | 스위치 끄기 · 백업 이미지 찾기 · 되돌리기 명령의 시험 실행(실제 굽기 없음) | 흐름 |

### 7.3 집 값의 세 종류

| 종류 | 뜻 | 예 | 학교에서 |
|---|---|---|---|
| 확정 | 같은 입력 → 같은 출력이라 장치가 바뀌어도 답이 같다 | 2a 출력 동일 · 2b 사건 동일 · 분석 도구의 10/11 재현 · 램프 도구의 흉내 지연 맞힘 · 펌웨어 빌드 | 학교 짝 명령으로 그날 원본에 한 번 더 돌릴 수 있다(선택) · 판정이 ⚠️ · ❌ 면 필수 |
| 임시 | 조건이 학교와 달라 숫자가 그대로 옮겨지지 않는다 | 가짜 카메라 fps · 추론 시간 · 재압축 검출 비교 | **학교 값이 본 값** — 짝 명령으로 반드시 잰다. 집 값은 「예상」 칸에만 쓴다 |
| 흐름 | 절차가 끝까지 도는지만 본다 | 실행기 답 · 진행 도우미 안내 · 세기 | 학교에서 실제로 진행하며 확인 |

- 🔴 **집 값을 학교 값처럼 인용하지 않는다** — 결과표 · 작업로그에 「집 · 가짜 카메라」 조건을 붙인다.

### 7.4 애매 · 이상 판정 규칙(기계로)

리허설 스크립트가 항목마다 자동으로 판정해 결과표 「판정」 칸에 이유와 함께 적는다.

| 판정 | 조건(하나라도) | 학교에서 |
|---|---|---|
| ❌ 이상 | 물리적으로 안 되는 값(처리 fps > 받은 fps · 0 · 음수 · 빈칸) · 판 수 · 누름 수가 대본과 다름 · 오류 · 예외 로그 · 확정 비교에서 하나라도 다름 · 끝까지 못 돎 | **필수** + 출발 전에 원인을 먼저 고친다 · 못 고치면 진행표에서 그 단계를 대안 절차로 바꾼다 |
| ⚠️ 애매 | 2번 잰 값의 차이 > 10% · 기대 범위 밖(항목마다 결과표에 적음 — 예: 1단계 처리 fps 14.5~17 · 상위 설계) · 표본 부족(fps 창 30장 미만 · 장면 표본이 대본 횟수의 80% 미만) · 경고 출력 · 효과가 서로 안 갈림(예: 2a 와 2a+2b 의 차이가 흩어짐보다 작음) | **필수** — 진행표 「꼭 잴 것」 목록에 자동으로 오른다 |
| 🟡 임시 | 위에 안 걸리지만 종류가 「임시」 | 학교 값이 본 값(어차피 잼) |
| ✅ 확정 | 위에 안 걸리고 종류가 「확정」 | 선택 |

- 결과표의 「학교 짝 명령」 칸 = 학교에서 그대로 칠 명령(집과 다른 것은 `SOP_CAMERA_HOST` 가 빠지는 것뿐).

## 9. 방문 진행표

- 파일 = 계획서의 「학교 진행표」 부록(계획서와 함께 쓴다). 한 단계마다 **칠 명령 · 실행기 답(번호) · 예상 시간 · 끝나면 Claude 가 볼 것(세기 번호 · 판정) · 막히면 대처표 번호**를 한 줄씩 담는다.
- 맨 앞 = 준비물(USB 케이블 · 안경 충전기 · 거치대 · 버튼 콘솔) · 맨 끝 = 되돌리기 모음(§8.3).
- 순서와 이유:

| 순서 | 단계 | 예상 | 이유 |
|---|---|---|---|
| 0 | 사전 점검(§8.2) · 버튼 하나씩 눌러 확인 | 10분 | 변수를 측정 전에 걸러낸다 |
| 1 | ⑤음성 측정(15판) | 20분 | 처리 설정과 무관 · 오래 미뤄진 일 |
| 2 | 3판 판 1 재확인 | 5분 | 같음 |
| 3 | 처리 비교 — 종전 · 1단계 · 1단계 + 화면 덜 그리기 · +2a · +2a+2b 각 2번(번갈아) | 45분 | 지금 펌웨어로 처리 효과만 가른다(펌웨어를 먼저 바꾸면 효과가 섞인다) |
| 4 | E1 · E2 | 10분 | 송출 저하 원인 확인 → 펌웨어 손질이 맞는 처방인지 |
| 5 | 펌웨어 변형 굽고 비교 → 결정(D22) → 바꿨으면 고른 처리 설정을 새 펌웨어로 2번 | 40분 | 받기 상한 자체를 올려 본다 |
| 6 | 램프 지연 | 10분 | 그날 쓸 펌웨어로(사진 버퍼 수가 지연을 바꿀 수 있다) |
| 7 | 근거 측정 + 그 자리 확인 + 모자란 장면 다시 | 15분 | 그날 고른 처리 · 펌웨어로 |
| 8 | 결과표의 「학교 필수」 중 남은 것 | 가변 | §7.4 |
| 9 | 마무리 — 되돌릴 것 확인 · 원본 · 세션 폴더 확인 | 10분 | — |

- 안경 배터리 — 시작 전 완충 · **완충 한 번 = 1시간으로 잡는다**(사용자 — 소리 · 마이크 · 촬영 · 녹화 쓰임에 따라 달라 정할 수 없어 1시간 기준) · 1시간을 넘기기 전에 단계 사이에서 충전한다. 펌웨어 굽는 동안은 USB 로 충전된다. 비교 세션은 무선(배터리) 조건으로 잰다(측정 설계 D23).
- 하루가 길어지면(V23) 7 을 5 · 6 보다 앞당긴다.

## 11. 오후까지 준비 순서

출발 시각은 정하지 않았다 — **전부 한다**(사용자 「할 수 있는 건 다하자」). 그래도 순서는 이대로다: 출발이 앞당겨지면 **아래부터** 빠지고, 1~3 은 빠지지 않는다(차질 방지의 바닥).

1. 출발 전 태그 `학교1012-전` · 가짜 카메라 · `SOP_CAMERA_HOST` · 가짜 인터락
2. 리허설 틀 + 이미 있는 절차(R1 · R2 · R3 의 1단계 비교 · R4) + 판정 규칙(§7.4)
3. 사전 점검 도구 · 실행기 「처리 설정」 · 「몇 판부터」 · 되돌리기 모음 · 진행표
4. 근거 측정 대본 · 「안내」 칸 · 분석 도구
5. 램프 지연 도구(+ `--screen`)
6. 펌웨어 빌드 옵션 · 재압축 비교
7. 2a(InferModel)
8. 2b(두 단 겹침)
9. 전체 리허설 2번 · 최종 리뷰 · 고침 · 출발 태그

- 빠진 항목은 진행표에서 지운다 — 학교에서 만들지 않는다(S1).

## 12. 버린 대안

| 대안 | 버린 이유 |
|---|---|
| 안3(받기 · 풀기 · 보정을 별도 프로세스로)을 먼저 | 2a + 2b 가 더 작고, InferModel 실험으로 스레드 겹침의 근거가 생겼다 → 예비로 둔다 |
| 버튼 찾기를 몇 장마다 건너뛰기 | 판정 입력이 바뀐다(D21) |
| 안경 해상도 낮추기(XGA → SVGA) | 검출 입력 · 보정 파일이 바뀐다 |
| 펌웨어 변형을 파일로 따로 두기 | 어긋난다 · 되돌리기가 복잡해진다(D20) |
| 집에서 실제 안경에 굽기 | 원인(E1 · E2) 확인 전에 굽지 않는다(D14) |
| 집 값을 학교 값 대신 쓰기 | D16 — 집 값은 「예상」 칸에만 |
| 리허설을 사용자가 손으로 | D15 |
| 카메라 지연을 안경 시계 도장으로 재기 | 안경과 파이의 시계를 맞춰야 한다 · 펌웨어를 바꿔야 한다 |
| 사전 점검이 문제 프로세스를 자동으로 끄기 | 다른 작업을 끌 수 있다 — 명령만 보여 준다 |

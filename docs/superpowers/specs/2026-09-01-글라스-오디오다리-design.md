# 글라스 오디오 다리 (V1.5) — 설계

## 1. 무엇이 막혀 있나

음성비서 갈래가 **두 곳에서 같은 이유로 멈춰 있다 — 파이와 ESP32 사이에 오디오가 오갈 길이 없다.**

| 막힌 것 | 필요한 방향 | 왜 필요한가 |
|---|---|---|
| **명료도 판정** (§10.49 ⛔) | 파이 → ESP32 | 합성음을 **글라스 스피커**로 들어야 판정이 된다. 모니터·노트북 청취는 판정이 아니다 |
| **STT 정확도 판정** (§10.50 ⛔) | ESP32 → 파이 | 지금 CER 은 **우리가 만든 합성음** 기준이라 오류를 STT 와 TTS 로 가를 수 없다 |

V0(`mic_speaker_test`)는 「녹음 → 바로 재생」까지만 만들었다. **ESP32 안에서 소리가 나고 ESP32 안에서 끝난다.**

## 2. 요구사항 (사용자 제시, 2026-09-01)

1. 🔴 **세 기능이 한 ESP32 안에서 자원을 다툰다** — 카메라 실시간 통신 · 마이크 · 스피커. 서로 영향을 주면 안 된다.
2. 🔴 **지금은 유선(USB), 실제 운용은 무선.** 무선이 유선과 같을 수는 없으나 **근접한 성능**이어야 한다.
3. 🔴 **포트 번호를 장치에 고정하지 않는다.** `ttyACM0`/`ttyACM1` 중 무엇이 될지 정해져 있지 않고, 오디오가 무선으로 옮겨간 뒤 두 포트는 **인터록·디스플레이 터치**가 나눠 쓸 예정이다. 그때도 안 깨져야 하고, 오디오가 유선으로 되돌아올 여지도 남아야 한다.

## 3. 자원 충돌 분석 — 대역폭은 제약이 아니다

> 출처 = 통합문서 **§10.34**. **조건: `Eung Min` AP · 640×480 JPEG q15 · 손 없는 정지 장면 · 300프레임.**
> 아래 초당 전송량은 그 실측값에서 **유도한 계산값**이며 새 측정이 아니다.

| 흐름 | 초당 전송량 | 72Mbps 링크 대비 |
|---|---|---|
| 영상 (프레임 10.1KB · 간격 36ms) | 242~280 KB/s | 3.1% |
| 마이크 업링크 (16kHz·16bit·모노) | 32 KB/s | 0.4% |
| 스피커 다운링크 (22.05kHz·16bit·모노) | 43 KB/s | 0.5% |
| **동시 최악** | **355 KB/s** | **4.0%** |

**오디오는 영상의 약 1/8**이고, 영상은 상시·오디오는 발화 시에만 흐른다.

> 📌 **상위 설계 §8.2 의 추정치를 정정해야 한다** — 거기 적힌 *"영상 400~600KB/s, 음성은 그 6%"* 는 실측 전 추정이었다. 실측 기준 영상은 **242~280KB/s**, 음성은 **약 12%** 다. 결론(대역폭은 제약이 아니다)은 유지된다.

**메모리** — PSRAM 8MB 중 오디오 10초 버퍼(480KB) + 카메라 JPEG 프레임버퍼 2개. 한 자릿수 %.

### 3.1 🔴 확인되지 않은 것 — 페리페럴 충돌

구형 ESP32 는 **카메라가 I2S0 을 쓴다.** 그렇다면 PDM 마이크(I2S0 전용)와 **정면 충돌**한다.
ESP32-**S3** 는 전용 `LCD_CAM` 페리페럴이 따로 있어 겹치지 않는 것으로 알려져 있으나, **파이에 코어 라이브러리 소스가 없어 코드로 확인하지 못했다.**

→ ⚠️ **단정하지 않는다.** 셋을 한 스케치에서 동시에 초기화해 보는 것이 유일한 확답이며, **이 설계의 범위 밖**(다음 A작업)이다. 여기서 막히면 보드 분리까지 갈 수 있다.

### 3.2 🔴 진짜 위험 — 이미 미규명인 것과 뒤섞인다

대역폭·메모리가 여유인데도 경계하는 이유는 성능이 아니라 **원인 규명 불가**다.

- §10.34-(6): **최저 5.1fps 구간이 남아 있고 원인 미규명**
- ⏸ **ESP32 링크 요동 미규명** — 가설 5개를 세워 5개 다 기각됨

오디오를 얹은 뒤 FPS 가 흔들리면 **오디오 탓인지 원래 있던 요동인지 못 가른다.**
⚠️ CLAUDE.md §5 의 **「상한을 측정했다 ≠ 원인을 규명했다」와 같은 계열**이다.

→ **대응**: 동시 가동 검증 때 **오디오를 켜기 전에 카메라 단독 FPS 를 같은 세션·같은 자리에서 먼저 잰다.** 다른 날 값과 비교하지 않는다(세션 간 편차 — CLAUDE.md §5).

## 4. 구조 — 세 겹

```
[3] 응용     재생 / 녹음 / 덤프                ← 전송을 모른다
[2] 프레이밍  헤더 한 줄 + 원시 PCM + 체크섬     ← 전송을 모른다
[1] 전송     Stream&  ─┬─ USB CDC   (지금)
                       └─ WiFiClient (나중)
```

### 4.1 전송 계층 — 왜 `Stream` 인가

| 안 | 방식 | 판정 |
|---|---|---|
| **A** | **아두이노 `Stream` 상속을 그대로 쓴다** | ✅ **채택** |
| B | 전송 인터페이스를 직접 정의(가상 클래스·함수 포인터) | ❌ 이미 있는 것을 다시 만든다 |
| C | 유선판·무선판을 각각 구현 | ❌ 요구사항 2 위반 — 프로토콜이 두 벌로 갈라진다 |

`Serial`(USB CDC)과 `WiFiClient` 는 **둘 다 `Stream` 을 상속**한다. 펌웨어가 `Stream& link` 하나만 보고 읽고 쓰면 **전송 교체가 변수 하나 교체**가 된다. 새 추상화를 발명하지 않고, 무선 전환 시 [2]·[3] 은 **한 줄도 바뀌지 않는다.**

⚠️ `Stream::readBytes` 의 타임아웃 의미가 `WiFiClient` 에서 다르므로 **타임아웃을 명시적으로 설정**한다.

### 4.2 프로토콜

```
파이→ESP32   "W <샘플수> <레이트>\n" + int16LE 페이로드 + 체크섬4B    적재
             "P\n"                                                   재생
             "R <초>\n"                                              녹음
             "D\n"                                                   덤프 요청
ESP32→파이   "D <샘플수> <레이트> <체크섬>\n" + int16LE 페이로드       덤프 응답
```

V0 명령(`r`·`p`·`1~5`·`i`)은 **그대로 둔다** — V0 검증 절차가 살아 있어야 한다.

- 페이로드는 **정확히 N바이트를 블로킹으로 읽는다.** 그래서 오디오 안에 `r`·`p` 바이트가 섞여도 명령으로 오해되지 않는다.
- 🔴 **체크섬은 선택이 아니다.** 잘린 전송도 그럴듯한 소리를 내므로, 없으면 *"STT 가 나쁘다"* 로 오진한다. **불일치 시 측정을 중단**시킨다.

### 4.3 샘플레이트 — 리샘플링하지 않는다

헤더의 레이트대로 **펌웨어가 스피커 I2S 를 다시 연다.** 파이에서 16kHz 로 줄여 보내면 *"뭉개진 것이 스피커 탓인가 리샘플링 탓인가"* 를 못 가른다 — §3.2 와 같은 계열의 교란이다.
마이크는 I2S0, 스피커는 I2S1 로 포트가 분리돼 간섭하지 않는다.

→ **되돌림**: 레이트 변경 초기화가 실패하면 파이에서 16kHz 로 줄여 보내는 쪽으로 후퇴한다.

### 4.4 🔑 무선에서 근접 성능이 나오는 이유

상위 설계 §8.2 의 **「스트리밍이 아니라 받아놓고 재생」**을 그대로 지킨다. 이 선택이 곧 요구사항 2 의 답이다.

| WiFi 가 흔들릴 때 | 스트리밍이면 | **받아놓고 재생이면** |
|---|---|---|
| 지터 20ms | **소리가 끊긴다**(버퍼 언더런) | 시작이 20ms 늦을 뿐 **소리는 멀쩡** |
| 성능 의존 항목 | 지터 | **총 전송량뿐** |

무선 전환 시 늘어나는 것은 **시작 지연 0.1~0.2초**뿐이고, §10.49 가 밝힌 대로 **지연의 지배 항목은 「말하는 시간」**이라 그 안에 묻힌다.

⚠️ 무선에서는 소켓이 둘이 된다 — **영상은 Pi#1, 오디오는 sop-pi-2**(상위 설계 §8.2). 에어타임을 나눠 쓰므로 동시 가동 검증에서 실측한다.

### 4.5 포트 — 번호를 쓰지 않는다

커널이 이미 안정적인 이름을 만든다:

```
/dev/serial/by-id/usb-Espressif_USB_JTAG_serial_debug_unit_<MAC>-if00 → ttyACM0
```

`Demo/serial_ports.py` 가 `/dev/serial/by-id/` 를 훑어 **USB 제조사·시리얼로** 장치를 고른다. 꽂는 순서·개수와 무관하고, 나중에 인터록·디스플레이 터치가 두 포트를 나눠 써도 깨지지 않는다.

🔴 **지금 이미 틀려 있다** — `Demo/config.py` 의 `INTERLOCK_PORT = "/dev/ttyACM0"` 는 **현재 ESP32 를 가리킨다**(인터록 Arduino 미연결). 이 상태로 데모를 띄우면 인터록 명령이 ESP32 로 간다.

⚠️ **인터록 쪽은 조심해서 손댄다** — Arduino UNO R4 가 연결돼 있지 않아 그 USB 신원을 읽을 수 없다. 해석 실패 시 **기존 경로로 폴백 + 경고**만 한다. **검증하지 못한 것을 기본 경로로 만들지 않는다.**

## 6. 검증 관문 — 통과 못 하면 어떤 소리도 판정에 쓰지 않는다

1. 🔴 **`PSRAM=opi` 로 굽는다.** 기본값이 `Disabled` 라 빠뜨리면 `ps_malloc` 이 NULL 을 낸다. 펌웨어가 **할당 실패를 소리 내어 알린다.**
2. **1kHz 순음 재생** → 1kHz 로 들리면 레이트 처리가 맞은 것. 아니면 중단.
3. **왕복 시험** — 녹음 → 덤프 → wav 저장 → 길이·RMS 가 ESP32 보고값과 일치. **체크섬 불일치면 중단.**
4. 🔴 **두 가지 청취를 섞지 않는다** — 이름이 비슷하지만 **다른 것을 잰다**(CLAUDE.md §5 「지표 이름 혼용 금지」).

   | | **마이크 청취** | **합성음 청취** |
   |---|---|---|
   | 무엇을 재나 | **마이크가 얼마나 잘 담았나** | **TTS 가 얼마나 또렷하게 말하나** |
   | 재생할 것 | 폰 녹음본 · ESP32 PDM 녹음본 | `kss_*.wav` 4개 |
   | 무엇을 가르나 | §10.50 CER 이 **마이크 탓인가 STT 탓인가** | §10.50 CER 이 **TTS 탓인가 STT 탓인가** |
   | 정본 | §10.50-(4) | §10.49 (⛔ 명료도) |

   둘 다 **FQ 스피커·귀 옆 5cm** 에서 듣는다. 순서는 **마이크 청취 먼저**(사용자 결정 2026-09-01) — 내일 첫 작업이다.

5. **STT 재측정** — ESP32+폰 나란히 녹음 → `dev/tts/stt_bench.py`(입력만 교체하면 합성음 회차와 같은 잣대).

⚠️ 2~5 는 **HW 가 눈앞에 있어야 한다**(스피커 소리를 사람이 들어야 한다). 1 은 무관.

## 1. 배경 — 왜 지금 이것인가

카메라 착용 구도에 따라 사전 감지율이 **61~99%로 흔들린다**(§10.26·§10.29). 종전 대응은 「카메라 착용 기준 확립」이었으나, 이 프로젝트의 대상은 **작업자가 착용하는 스마트 글라스**다. 착용 위치를 거치·정렬로 고정하는 방식은 제품 형태와 맞지 않는다.

따라서 방향을 바꾼다: **버튼이 보이는 자세라면 어떤 구도에서든 일정 성능이 나오게 판정 로직을 고친다.**

### 1.1 탐색으로 확인한 것 (2026-07-27, `test/hoi.db` 재질의, 새 촬영 0회)

**① 런타임에는 「눌림 직전 한 프레임 판정」이 없다.**
`fsm.py:120-166`의 실제 동작은 ⓐ정답 ROI에서는 비전이 아무 역할도 안 하고(`press_button`이 확정) ⓑ오답 ROI에서 체류 0.3초 + 박스 안일 때만 WARNING이며 ⓒ갭메우기 0.3초가 **이미 창(window)으로 작동**한다.
→ 「직전 한 프레임 판정」은 **오프라인 측정 도구(`dwell_probe`)의 정의**였지 런타임 동작이 아니었다.

**② 도구마다 정의가 달라 수치가 서로 비교되지 않는다.**
`dwell_probe`는 눌림 직전 프레임 하나로 판정하고, `hoi_import` docstring의 SQL 예시는 직전 15프레임 창을 쓴다. 두 값의 격차가 세션에 따라 **0%p~17%p**로 벌어진다.

**③ 창을 늘려도 무릎점이 없다 — 지표의 의미만 변질된다.**
창 N을 1→45프레임으로 늘리면 사전 감지율이 완만히 계속 오른다. N=45(약 4.5초)는 「눌리기 직전에 감지했다」가 아니라 「손이 그 근처에 있었던 적이 있다」를 재게 된다.

**④ 팜 미검출은 연속으로 잘 일어나지 않는다.**
GPIO 눌림 기록은 「그 순간 손이 물리적으로 버튼 위에 있었다」는 정답이다. 눌림 프레임에서 팜 검출 실패는 절벽 제외 구간에서 5.9%인데, 창 5프레임에서는 「5프레임 내내 전멸」이 0.66%로 떨어지고 **9프레임에서 0%**가 된다.

**⑤ 절벽(버튼 y ≥ 337)은 창으로 못 고친다.**
절벽 구간의 사전 감지율은 창 5·9프레임에서 **동일하게 38.3%**이고, 창 200프레임(약 20초)에서도 2건이 끝까지 안 잡힌다. 손바닥이 프레임 밖이라 찾을 대상이 없다. 반면 타 버튼 혼입은 창을 늘리면 똑같이 2배가 된다.

**⑥ 🔴 병목은 감지가 아니라 체류 요구일 가능성이 크다.**
위반 눌림 183건의 능력 상한(창 5프레임)은 통합 89.6%다. 그런데 §10.23이 같은 데이터 일부(37건)에서 실제 경고 발화로 잰 값은 57%였다. 격차 약 30%p = **손은 봤는데 체류 0.3초를 못 채운 경우**다. 원인은 §10.23에 이미 있다 — 사람이 버튼을 누르는 데 걸리는 시간이 0.39~0.40초(3회 재현)인데 0.3초를 **연속으로** 요구하면 여유가 0.1초뿐이고, 검출이 한 번만 끊겨도 타이머가 리셋된다.

> ⚠️ ⑥의 30%p는 **서로 다른 도구로 잰 두 수치의 비교**라 정밀하지 않다. 같은 도구로 다시 재는 것이 §4(시뮬레이터)의 첫 과제다.

> **모든 결과 보고에 ①절벽 포함 전체 ②절벽 제외 두 값을 반드시 병기한다. "80% 달성" 같은 주장에는 전체값을 쓴다.**

### 2.4 성공 기준

| 지표 | 현재 | 목표 |
|---|---|---|
| 사전 감지율 — 능력 상한 (창 N=5, 위반 통합) | 탐색값 89.6% | 유지 |
| **위반 사전 차단율** (시뮬레이터) | 약 57%¹ | **≥ 80%** |
| **E2E 오경보** (정상 세션, 분당) | **미측정** | 측정 후 기준 설정² |
| 세션별 최저 차단율 | 미측정 | **≥ 80%** |

¹ §10.23의 값. 다른 도구로 잰 것이라 시뮬레이터 재측정이 1단계.
² 지금 기준을 정하면 근거 없는 숫자가 된다. 현행 로직의 오경보를 먼저 재고 **「현행 대비 악화 없음」**을 잠정 기준으로 삼는다.

## 3. 사전 감지율 정의 단일화

### 3.1 정의

**사전 감지율 = (감지 성공한 눌림 수) ÷ (전체 눌림 수).** 단위는 **눌림 1건**이며 프레임이 아니다.

**두 값을 항상 병기한다.**

| | **능력 상한** | **런타임 거울** |
|---|---|---|
| 묻는 것 | 비전이 **볼 수 있었나** | 런타임이 **실제로 알았나** |
| 판정 | 창 안에 `zone_label == 눌린 버튼`인 프레임이 **하나라도** 있으면 성공 | `fsm.py` 로직을 그대로 재생해, 눌림 시점에 FSM이 그 ROI를 관측 중이었으면 성공 |
| 산출 | DB 질의 (수 초) | 시뮬레이터 (§4) |
| 성격 | 고정 — 런타임이 바뀌어도 안 변함 | 런타임을 따라 변함 |

**두 값의 격차 = 판정 로직이 버리는 양**이며, 개선 여지의 크기를 직접 알려준다. 격차가 0이면 카메라·모델 문제이고, 격차가 크면 판정 로직 문제다. 한 값만 보면 어느 쪽인지 알 수 없어 §10.24~§10.26에서 원인을 세 번 잘못 짚었던 함정에 다시 빠진다.

### 3.2 고정 파라미터

| 항목 | 값 | 근거 |
|---|---|---|
| **창 길이 N** | **5프레임** | §10.29⑥의 계단 위치. N=9는 감지 +0.7%p에 타 버튼 혼입 +26%p로 교환비 약 37:1 열세 |
| 창 범위 | `눌림프레임 − 5 ~ 눌림프레임` (총 6프레임) | 눌림 순간 포함 |
| 팜 임계 | **0.5 고정** | §10.27·§10.28. 변수를 섞지 않는다 |
| 링 폭 | **25px 고정** (`config.HAND_ROI_RING_PX`) | §10.22의 무릎점 |
| 구역 단계 | 능력 상한은 **링 포함**(level 1·2) / 런타임 거울은 **런타임 규칙 그대로** | 능력 상한은 "봤나"를 묻고, 발화 조건은 런타임 몫 |

### 3.3 🔴 단일 출처 — `Demo/test/hoi_metrics.py` 신설

정의가 지금 세 군데에 흩어져 있다(`dwell_probe.py` 코드 · `hoi_import.py` docstring의 SQL 예시 · 세션마다 즉석으로 쓰는 질의). 값이 서로 안 맞았던 원인이 이것이다.

- **DB에서 읽어 지표를 계산하는 파이썬 함수**로 둔다. SQL은 정의를 담을 수 없다(`roi_zones.py`를 SQL로 못 옮겼던 것과 같은 이유 — `2026-07-26-HOI-DB-design.md`).
- `dwell_probe.py`는 자체 계산을 버리고 이 모듈을 호출한다.
- `hoi_import.py` docstring의 SQL 예시에는 **「참고용 — 정본은 `hoi_metrics.py`」**를 명시한다. 지우지 않는다(§10.30이 그 질의로 나왔으므로 재현 경로로 남긴다).

`roi_zones.py`(판정 규칙 단일 출처)와 같은 패턴이며, 그때 *"런타임·측정도구가 같이 import — 복제 drift 구조적 차단"*으로 효과를 봤다.

## 4. FSM 오프라인 시뮬레이터

### 4.1 핵심 원칙 — 재구현하지 않는다

**시뮬레이터는 실제 `SafetyFSM`을 import해서 프레임을 먹이는 얇은 껍데기다.** 체류·갭메우기·발화 규칙을 시뮬레이터에 다시 쓰면 정본이 둘이 되고 측정이 런타임을 대표하지 못한다. 도구가 config를 안 따라 **네 번 물렸던** 전례(§10.23)의 근본 해결이다.

```
palm_frames (프레임 순서) ──┐
                          ├─→ SafetyFSM.update_vision(zone_label, ts, zone_level)
presses (눌림 프레임) ──────┘   SafetyFSM.press_button(button, ts)
                                      │
                          on_state_change 콜백 → 상태 전이 기록
```

### 4.2 DB 스키마 추가 2건

| 테이블 | 컬럼 | 출처 | 이유 |
|---|---|---|---|
| `palm_frames` | **`ts`** (초) | `hoi_import.py:226`의 `times` dict — **이미 읽고 있고 버리는 중** | 체류는 초 단위 연산. FPS가 7.7~11.3으로 흔들려 `프레임÷fps` 추정 불가 |
| `presses` | **`expected_button`** | `_VIOLATION_RULE`이 `is_violation` 계산에 이미 쓰는 값 | FSM 기대 단계를 GPIO 로그에 맞춰 고정. 상태를 눌림으로 굴리면 한 번 어긋날 때 이후가 전부 오염된다 |

팜 추론 캐시(`hoi_probe_batch.py`, 22세션 약 40분)는 **건드리지 않는다** — `hoi_import.py`만 고치고 재구축하면 수 초다. 2단계 분리가 여기서 값을 한다.

### 4.3 시뮬레이션 정책 — 실제 운용과 다른 점

1. **BLOCK 진입 시 즉시 `release_block()`** — 촬영 당시 GUI를 안 돌렸으므로 해제 조작 기록이 없다. 해제하지 않으면 첫 위반 이후 모든 눌림이 평가에서 빠진다.
2. **WARNING도 즉시 `release_warning()`** — 같은 이유.
3. **기대 단계는 `expected_button`으로 매 눌림 직전 설정** — 위 1·2의 자동 해제가 기대 단계를 흔들지 않게 한다.

이 셋은 **시뮬레이션 편의이며 실제 운용 동작이 아니다.** 산출 문서에 반드시 병기한다.

### 4.4 산출 지표 3종

| 지표 | 정의 |
|---|---|
| **런타임 거울 사전 감지율** | 눌림 시점에 FSM이 그 ROI를 관측 중이었나 |
| **위반 사전 차단율** | 위반 눌림 **전에** WARNING이 떴나 |
| **E2E 오경보** | 정상 세션에서 발생한 WARNING 수 / 분 |

세 번째는 **한 번도 잰 적이 없다.** CLAUDE.md의 *"E2E 오경보는 DB로 안 된다"*는 정확히는 **SQL로 안 된다**는 뜻이었다 — 파이썬으로 `palm_frames`를 프레임 순서대로 읽으면 체류 시뮬레이션이 되고, 팜 추론이 이미 캐시돼 있어 재추론이 불필요하다.

### 4.5 🔴 검증 관문 — 통과 못 하면 어떤 수치도 쓰지 않는다

**§10.23의 두 세션(`violation-press` 20건 · `violation-press-slow` 17건)에서 체류 0.3초·0.5초의 사전 차단율을 재현해야 한다.** 알려진 값은 **0.3초 57% · 0.5초 14%**.

재현되지 않으면 시뮬레이터가 틀린 것이므로 원인을 찾기 전까지 §5로 넘어가지 않는다. `hoi.db` 때 *"검증은 코드가 아니라 결과로"* 방식으로 `_VIOLATION_RULE` 버그를 잡았고, **그 버그는 통합 지표로는 안 보이고 세션별 대조로만 드러났다.**

### 4.6 파라미터 스윕

시뮬레이터가 돌면 다음을 **재촬영·재추론 없이** 비교할 수 있다: 체류 임계(현행 0.3초) · 갭메우기(현행 0.3초) · **창 기반 누적의 M/N**(§5) · 링 폭(현행 25px).

## 5. 창 기반 체류 누적 (런타임 변경)

### 5.1 무엇을 바꾸나 — 조건 하나

`fsm.py:136-141`의 갭메우기 조건만 바꾼다. **체류·발화·링 규칙은 손대지 않는다.**

| | 현행 | 변경 후 |
|---|---|---|
| 직전 관측을 유지하는 조건 | `now − last_seen ≤ 0.3초` | **최근 N프레임 중 M회 이상 그 구역에서 관측됨** |
| 유지할 값 | 직전 실제 관측의 `roi`·`level` | 동일 (변경 없음) |

**`level`은 창에서 투표하지 않고 직전 실제 관측값을 그대로 쓴다** — 링에서 발화하지 않는다는 C1 설계(§10.22)를 흔들지 않기 위해서다.

### 5.2 왜 이것이 1.1⑥의 격차를 겨냥하나

현행은 **시간 기준**이라 FPS가 7.7~11.3으로 흔들리면 실제 창이 2.3~3.4프레임으로 같이 흔들린다. 게다가 검출이 **끊긴 직후부터** 시간을 재므로 끊김이 잦으면 유지 자체가 안 된다.

창 기준은 **관측 횟수**를 보므로 "5프레임 중 M번 봤으면 계속 있는 것으로 친다"가 되어 드문드문 끊기는 패턴에 강하다. §10.29⑥이 *"경계는 시간이 아니라 프레임 수"*라고 결론낸 것과도 정렬된다.

### 5.3 파라미터

> ⚠️ **이름이 겹치는 두 개의 창을 혼동하지 말 것.** §3.2의 창 N은 **지표가 눌림 직전 몇 프레임을 되돌아보는가**(측정용, 고정)이고, 여기 `HAND_WINDOW_N`은 **런타임이 직전 관측을 몇 프레임까지 유지하는가**(동작용)다. 값을 둘 다 5로 두는 것은 §10.29⑥의 계단이라는 **같은 근거**를 쓰기 때문이며, 서로 독립적으로 바뀔 수 있다.

| 이름 | 값 | 비고 |
|---|---|---|
| `HAND_WINDOW_N` | **5** | §3.2와 같은 근거(§10.29⑥), 별개 파라미터 |
| `HAND_WINDOW_M` | **스윕으로 결정** (1~5) | M=1이 가장 느슨, M=5가 가장 엄격 |
| 롤백 스위치 | **`HAND_WINDOW_N = 0` → 기존 갭메우기로 복귀** | `HAND_ROI_RING_PX=0`이 도넛 롤백 스위치였던 것과 같은 방식 |

M은 시뮬레이터로 정한다 — **감지율과 오경보를 같이 놓고** 무릎점을 찾는다(도넛 링 폭을 25px로 정할 때와 같은 방법).

## 7. 미결 사항

- **M 값** — 시뮬레이터 스윕으로 결정. 설계 시점에 정하지 않는다.
- **오경보 허용 기준** — 현행 로직의 오경보를 재기 전까지 정하지 않는다(§2.4 각주 2).
- **절벽 구간** — 본 설계 범위 밖. 「카메라 착용 기준 확립」 과제로 남는다.
- **1.1⑥의 30%p 격차** — 서로 다른 도구로 잰 값의 비교라 정밀하지 않다. §4.5 검증 관문 통과 후 시뮬레이터로 다시 잰다.

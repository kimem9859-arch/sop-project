# ESP32 통신 경로 재설계 — 폰을 영상 경로에서 뺀다

> 2026-09-06 · 세션 `73cfe23a-62da-4c88-a4d4-f125e8d44723`
> 상태 = **설계 확정, 구현 전** (HW 사용 불가로 검증 보류)
> 🔴 **이 설계의 근거가 되는 2026-09-05 실측이 아직 통합문서에 기록되지 않았다** — §9 참조.

---

## 1. 배경 — 두 문제가 곱해지고 있다

FPS 저하는 하나의 문제가 아니라 **두 개가 곱해진** 결과다.

| | 무엇 | 상태 |
|---|---|---|
| **갈래 B** | FPS 가 대역폭이 아니라 **왕복 횟수**에 매여 있다 — 처리량 ≈ 송신 윈도 ÷ RTT | ✅ **규명됨** (§10.56) |
| **갈래 A** | 그 RTT 를 올리는 것이 무엇인가 | 🔶 **폰 AP 로 좁혀짐** (2026-09-05 실측, 미기록) |

2026-09-05 에 가설 6개가 기각됐다 — ESP32 신호 약함 · AP 채널 이동 놓침 · 보드 개체 · 파이 전원절약 · 파이 링크 품질 · 우리 트래픽. **남은 것은 폰 AP 안쪽이고, 우리는 그것을 고칠 수 없다.**

🔑 **그래서 방향을 바꾼다 — 원인을 고치지 말고 경로에서 빼낸다.**

그리고 현재 구조는 **프레임이 공중을 두 번 지난다**(ESP32 → 폰 → 파이). 홉을 하나 줄이면 갈래 B 의 왕복 부담도 절반의 지연 위에서 돌게 된다. **한 번의 변경이 두 문제를 동시에 친다.**

## 2. 목표 / 비목표

**목표**
- 영상 경로에서 **폰을 완전히 제거**한다.
- 무선 홉을 **2 → 1** 로 줄인다.
- **파이의 인터넷을 유지**한다 — Claude Code 로 개발·측정하려면 필요하다.
- 시연 장소가 바뀌어도 선다(**이동성**).

**비목표 (🔴 이 설계는 여기에 손대지 않는다)**
- **전송 방식 개선** — UDP 전환 · 프레임을 송신 윈도 아래로 · TCP 2연결(§10.56-(8)). 효과는 있지만 **원인을 남긴 채 완화**하는 쪽이고 코드 변경이 크다. 이 설계가 통과하면 **별도 과제**로 남긴다.
- 파이 런타임 로직. **0줄** 바꾼다.
- 갈래 A 의 완전 규명 — 폰 AP 안에서 무슨 일이 나는지는 답하지 않는다. **경로에서 빼면 답할 필요가 없어진다.**

## 3. 🔴 확정 제약 — 장비를 사지 않는다

> **여행용 라우터 구매는 하지 않는다. 예산이 없다.**(2026-09-06 사용자 확정)

따라서 **모든 폴백은 이미 가진 것으로만** 구성한다. 이 제약이 §5 폴백 구성을 결정했다.

## 4. 구조

```
[폰 핫스팟] ──무선──→ 파이1 wlan0        인터넷 전용 (Claude Code)
                                         🔴 영상은 이 길을 지나지 않는다

[메인 ESP32] ──무선 1홉──→ [iptime 공유기 · 콘솔 내부] ──랜선──→ 파이1 eth0
                                        │
                                        └──랜선──→ 파이2 (음성비서)
```

**왜 되는가** — 파이에는 통로가 둘이다. 무선(wlan0)은 인터넷, 랜포트(eth0)는 ESP32. 서로 다른 장치라 하나가 바빠도 다른 하나는 멀쩡하다. 2026-09-04 에 이 구조가 실제로 도는 것을 확인했다(조건·수치 = §9).

**얻는 것**
1. 폰이 영상 경로에서 빠진다 — 폰이 느려도 영상은 안 느려진다
2. 무선 2홉 → 1홉
3. 채널이 갈린다 — 공유기와 폰이 다른 채널

## 5. 폴백 3단 (전부 추가 비용 0)

| 순위 | 구성 | 어떻게 발동하나 | 상태 |
|---|---|---|---|
| **1 (주)** | iptime 공유기 경유 | ESP32 `WIFI_CREDS` 1순위 | 2026-09-04 에 구조 확인 |
| **2 (자동)** | 폰 핫스팟 | 🔑 우선순위 배열이 **공짜로** 제공 — 1순위가 안 잡히면 2순위로 자동 | 현행 방식 |
| **3 (예비)** | **파이1이 AP** | 수동 전환 | 🔴 **미검증** |

🔑 **2번이 이 설계의 안전판이다.** 펌웨어가 이미 「1순위가 없으면 2순위」로 동작하므로, 시연장에서 공유기가 안 서면 **코드 변경 없이 지금 방식으로 되돌아간다.**

🔑 **3번이 「라우터 구매」 자리를 대신한다.** **시연 중에는 인터넷이 필요 없으므로** 파이1 을 순수 AP 로 쓸 수 있고, 그러면 AP+STA 동시 동작의 대역 제약(§8)도 성립하지 않는다. 개발할 때는 AP 를 끄고 평소대로 폰으로 인터넷을 받는다 — **무선이 하나여도 시간으로 나누면 된다.**

### 7.1 ⭐ G4 성능 합격선 — 개봉 전 확정

> **`link_probe` 3라운드 · 각 45초**
> - **3라운드 전부** FPS **≥ 15** (NFR-1)
> - **3라운드 전부** 스트리밍 중 ping 평균 **< 15 ms**

**「전부」인 이유** — 이 문제의 본질은 평균이 아니라 **나쁜 구간이 있다는 것**이다. 평균으로 재면 그 구간이 묻힌다.

**ping 을 함께 보는 이유** — §10.56 이 확정했듯 FPS 는 RTT 의 함수다. 장면이 단순하면 프레임이 작아져 FPS 가 좋아 보이므로, **FPS 만 보면 링크를 잘못 판정한다.**

🔴 **조건을 반드시 병기한다** — 메인 보드 · 배터리 전원 · 안경 착용. 2026-09-04 측정은 **서브 보드·USB 전원·책상**이라 조건이 다르다(§9).

### 7.2 🔴 중단 규칙

> 공유기 경유에서도 **3라운드 중 하나라도 15fps 미만**이면 이 설계로는 목표에 못 미친 것이다.
> → AP 를 바꾸는 갈래를 접고 **전송 개선(§10.56-(8))** 으로 방향을 튼다. 그 경우 이 문서의 §2 비목표가 다음 과제가 된다.

## 8. 위험

**① 🔴 공유기 무선의 현재 상태를 모른다**
2026-09-04·09-05 에는 켜져 있었고 ESP32 가 실제로 붙었다. 그러나 2026-09-06 현재 확인할 수단이 없다(HW 부재). **G1 이 이 위험의 관문이다.**

**② ⚠️ 공유기를 설정할 수 없다** — 빌린 장비이고 관리자 비밀번호를 모른다.
- 채널 고정 불가 → 받아들인다(폰보다는 낫다)
- DHCP 고정 할당 불가 → IP 가 바뀔 수 있다. 복구는 `read_esp32_ip.sh`(§6-2). ipTIME 은 같은 기기에 같은 IP 를 오래 유지하므로 실무상 드물게 일어난다
- 개방망(비밀번호 없음) → 시연장에서 외부인이 붙을 수 있으나 **기능에는 지장 없다.** 기록만 한다
- 📌 반납 요구는 프로젝트 종료까지 없다(2026-09-06 확인)

**③ ⚠️ 공유기가 콘솔 내부에 있다**
전파가 갇힌다. 다만 ESP32 와의 거리는 **1m 이하**이고 사이에 있는 것은 **MDF 합판**(목재라 2.4GHz 감쇠가 작다). 2026-09-04 에 이 경로로 실제 스트리밍이 됐다.
⚠️ 그때는 ESP32 가 **책상 위**였고 시연은 **머리 착용·움직임**이다 → **G2 가 이 차이를 본다.**

**④ ✅ 안경 프레임의 안테나 가림 — 해소됨**
안테나를 프레임 밖으로 뺄 수 있음이 확인됐다(2026-09-06). §10.42-(7) 이 남긴 의심 후보 하나가 닫힌다.

**⑤ 🔴 검증 기회가 제한적이다**
HW 3종이 동시에 필요한데 최근 며칠 그런 날이 드물었다. **폴백 2가 코드 변경 없이 동작하므로**, 검증을 못 해도 시연이 막히지는 않는다 — 다만 그 경우 성능은 현행 그대로다.

**⑥ 🔴 이 파이에서 `.local` 이름이 인터넷 IP 로 해석된다 — mDNS 를 쓰지 않는 이유**

`/etc/nsswitch.conf` 가 `hosts: files mdns4_minimal [NOTFOUND=return] dns` 인데, mDNS 가 답하지 못하면 **DNS 로 새고** ISP 의 DNS 가 **아무 이름에나 안내 서버 IP 를 돌려준다.**

```
$ getent hosts definitely-no-such-host-xyz123.local   → 218.38.137.27
$ getent hosts Rpi1.local        (파이 자기 이름)      → 218.38.137.27
   (파이의 실제 로컬 IP 는 192.168.45.221)
```

🔴 **`esp32cam.local` 을 쓰면 ESP32 가 꺼져 있어도 파이가 인터넷의 엉뚱한 서버로 TCP 접속을 시도한다.** 「연결 실패」로 끝나지 않는다.
→ **고정 IP 를 유지한다**(§6-2). `nsswitch.conf` 를 고쳐 막는 길도 있으나, **검증할 HW 가 없는 시점에 이름해석 설정까지 건드리는 것은 위험 대비 이득이 작다.**
📌 §10.55-(6) 이 지적한 **mDNS 이름 충돌** 문제도 mDNS 를 안 쓰면 함께 사라진다.

## 10. 거부한 대안

| 안 | 내용 | 거부 사유 |
|---|---|---|
| **여행용 소형 라우터** | 파이는 랜선, ESP32 는 그 AP 에 무선 | 🔴 **예산 없음**(§3 확정 제약). 기능적으로는 가장 견고했다 |
| **파이1 AP + STA 동시** (주안으로) | 파이가 인터넷을 받으면서 동시에 ESP32 용 AP | 칩이 지원하나(`managed 1 + AP 1`) **`#channels <= 1`** 이라 AP 가 인터넷 AP 와 **같은 채널에 묶인다.** → 폰을 2.4GHz 로 고정해야 하고, 폰이 5GHz 로 바뀌면 **ESP32(2.4GHz 전용)가 못 붙어 영상이 조용히 죽는다.** 인터넷 대역과 영상 링크가 한 몸이 되는 결합이 싫다. **폴백 3으로는 남긴다**(시연 중에는 인터넷이 없어 이 결합이 성립하지 않으므로) |
| **USB 무선 동글로 AP** | 라디오를 물리적으로 분리 | 위 결합이 사라지고 라우터보다 싸지만 **여전히 구매**다(§3) |
| **전송 개선을 먼저** | UDP·프레임 축소·2연결 | 원인을 남긴 채 완화한다. 코드 변경이 가장 크고(파이 수신부까지) 마감이 가깝다. **이 설계가 실패하면 그때 간다**(§7.2) |
| **mDNS 이름(`esp32cam.local`)** | IP 가 바뀌어도 안 깨지는 주소 | 🔴 이 파이에서 `.local` 이 **DNS 로 새어 인터넷 IP 로 해석된다**(§8-⑥). 고치려면 `nsswitch.conf` 를 건드려야 하는데 검증 수단이 없는 시점에 위험 대비 이득이 작다 |
| **폰 핫스팟 유지 + 설정 조정** | 채널 고정 등 | 폰 핫스팟은 채널을 자동 선택하고 **사용자가 지정할 수 없다** |
